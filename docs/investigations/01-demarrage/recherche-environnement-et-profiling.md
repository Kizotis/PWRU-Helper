# P1 — Environment & profiling research: why an unsigned 178 MB single-file WPF exe can burn 6–10 s before its first window

_Phase 1 · `01-demarrage/` · Author: **Mary (BMAD Analyst)** · Date: **2026-09-06** · Baseline commit `4759712` (main, v0.14.0)_

---

## Scope

This document answers the **external / environmental** half of P1. It does **not** re-analyse PWRU Helper's own code — Phase 0 already established (`00-annexe-demarrage-et-reseau.md` §1.7) that before the first frame the app performs **no network, no registry, no WinRT, no WMI, no font enumeration**. The owner's answer **(a)** narrows the case further: on the slow machines the 6–10 s pass **before any window appears**, on **personal machines with Windows Defender only** and fast hardware.

That leaves exactly four candidate owners of that time:

1. the **security stack** between `ShellExecute` and the first instruction of `Main` (Defender real-time protection, Block at First Sight, SmartScreen AppRep, Smart App Control);
2. the **.NET single-file host** (self-extraction of native libraries to `%TEMP%\.net`, JIT, assembly loading);
3. **WPF's own cold path** (BAML, render tier, D3D device, DPI);
4. **file-availability layers** (OneDrive Files On-Demand, roaming/redirected `%APPDATA%`, cold file cache).

## Method

- Massive web research, biased towards Microsoft Learn, `dotnet/*` GitHub repos and Defender product documentation; blogs and forums used only where no first-party source exists, and graded as such.
- Every claim carries a URL and a date (the `ms.date` / `updated_at` of the page where available, otherwise "accessed 2026-09-06").
- Four **local measurements** were taken on the dev box (read-only, no admin, no build, no `dotnet`) and are tagged `M1`–`M4`. They are reproducible and therefore graded CONFIRMED.

## Source-grading legend

| Grade | Meaning |
|---|---|
| **CONFIRMED** | Stated in first-party documentation (Microsoft Learn, `dotnet/*` design docs, product docs), or measured here reproducibly. |

## Executive answers — the 10 most decision-relevant facts

1. **Block at First Sight holds the file closed while it queries the cloud, and the default hold is 10 s, extensible to 60 s.** "By default, Block at first sight blocks the file for 10 seconds while waiting for a cloud determination. You can add up to 50 seconds, for a maximum time-out period of 60 seconds." — MS Learn, `ms.date` 2026-09-02 [[2]](https://learn.microsoft.com/en-us/defender-endpoint/configure-cloud-block-timeout-period-microsoft-defender-antivirus). **This is the only documented Windows mechanism that produces exactly a several-second, machine-dependent, pre-window stall, and 6–10 s sits inside its 10 s default window.**
2. **The cloud query can be synchronous — the file does not open until a verdict arrives.** "Can be synchronous or asynchronous. For synchronous, the file doesn't open until the cloud renders a verdict." + "BAFS can delay the opening of a file momentarily until a verdict is reached." — MS Learn, 2025-10-20 / updated 2026-09-01 [[3]](https://learn.microsoft.com/en-us/defender-endpoint/cloud-protection-microsoft-antivirus-sample-submission).
3. **BAFS is gated on Mark-of-the-Web.** "Block at first sight only uses the cloud protection backend for executable files and nonportable executable files that are **downloaded from the Internet, or that originate from the Internet zone**." — MS Learn, 2026-09-02 [[1]](https://learn.microsoft.com/en-us/defender-endpoint/configure-block-at-first-sight-microsoft-defender-antivirus). **Testable prediction: the MSI-installed build (written into Program Files by `msiexec`, no `Zone.Identifier`) should NOT show the stall; the downloaded portable exe should.**
4. **EV certificates no longer buy instant SmartScreen reputation.** "EV certificates no longer bypass SmartScreen. … Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." — MS Learn, `ms.date` 2026-05-04 [[12]](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation). Signing still helps, but **via certificate-level reputation that accumulates across releases** — which is exactly what an unsigned app, whose hash changes every release, can never build.
5. **The measured local environment already proves the mechanism is armed and can be long.** `M1` (dev box, 2026-09-06, no admin): `DisableBlockAtFirstSeen = False`, `CloudBlockLevel = 2`, **`CloudExtendedTimeout = 50`** → a **60-second** maximum cloud hold on this machine. A per-machine `Get-MpPreference` capture is therefore the single highest-value datum to collect from the slow machines.
6. **The single-file bundle extracts native DLLs to `%TEMP%\.net\PWRUHelper\<bundle-id>\` — and the bundle-id is random per build.** _[CORRECTED by the orchestrator 2026-09-06: the extracted set is the **5 WPF native DLLs, 7.8 MB** (`D3DCompiler_47_cor3`, `PenImc_cor3`, `PresentationNative_cor3`, `vcruntime140_cor3`, `wpfgfx_cor3`) — measured in the real `%TEMP%\.net\PWRUHelper\<id>` folder after Amelia-QD's fresh build. The 18-DLL / 24.4 MB figure below (M2) counts the native DLLs of the pre-bundle publish tree; `coreclr`, `clrjit`, `hostfxr`, `hostpolicy`, `mscordaccore`, etc. are statically linked into the .NET 8 single-file host and are NOT extracted.]_ `M2`/`M3` (local, reproducible) + dotnet/designs `extract.md` [[23]](https://github.com/dotnet/designs/blob/main/accepted/2020/single-file/extract.md) + dotnet/runtime #3601, still open in the "Future" milestone [[25]](https://github.com/dotnet/runtime/issues/3601). **Every new release re-extracts and re-scans those 24 MB once**, then reuses them.
7. **A self-contained WPF app's cold start being 2–3 s vs 250–300 ms warm is a documented, Defender-attributed community finding**, with ETW evidence of per-assembly load times inflating under real-time protection — dotnet/runtime #78379, closed "not planned", Nov 2022 [[29]](https://github.com/dotnet/runtime/issues/78379). This is the closest published analogue to the owner's 3.9–8.9 s cold vs ~1.2 s warm.
8. **Smart App Control blocks unsigned code outright, it does not merely delay it** — and it only ever exists on a clean install of Win11 22572+ [[13]](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview). `M4`: on the dev box `VerifiedAndReputablePolicyState = 0` (off). SAC is therefore a **weak** suspect for a *delay* symptom, but must still be read on each slow machine (a "0" answer eliminates it in one line).
9. **The Defender operational event log will NOT show a clean BAFS wait.** There is no event ID for "held file N ms, then allowed". 2010 = cloud intelligence used; 2050 = sample uploaded; 1116/1117 = detection/action [[5]](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus). **Per-file scan durations only exist in the `Microsoft-Antimalware-Engine` ETW stream**, surfaced by `New-MpPerformanceRecording` / `Get-MpPerformanceReport` (admin) [[6]](https://learn.microsoft.com/en-us/defender-endpoint/tune-performance-defender-antivirus).
10. **Azure Artifact Signing (ex-Trusted Signing) is now open to self-employed individuals, from $9.99/month, no hardware token, CI-friendly** [[12]](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)[[19]](https://techcommunity.microsoft.com/blog/microsoft-security-blog/trusted-signing-is-now-open-for-individual-developers-to-sign-up-in-public-previ/4273554) — a cheaper, faster alternative to the pending SignPath route, which is free but constrained to OSI-licensed projects with no proprietary component [[21]](https://signpath.org/terms).

> **Reading of A1.13.** The dev box is Azure-AD-joined, so `CloudExtendedTimeout=50` there is very likely policy-pushed and **not representative of the users' personal machines** — but it proves the field is real, non-default in the wild, and readable without admin. **Verdict on A1: Block at First Sight is the prime suspect and remains so after research.** It is the only documented mechanism that (i) blocks process start, (ii) for seconds not milliseconds, (iii) only for unknown/low-prevalence executables, (iv) only for files carrying MOTW, (v) only when the machine's Defender is cloud-connected — which reproduces "6–10 s, before any window, only some machines, personal + Defender only" without needing any other cause.

> **Decision-relevant synthesis for A4.** Signing does **not** buy an instant fix. It buys (i) elimination of SAC's "unsigned ⇒ blocked" path outright, (ii) a stable publisher identity so reputation **accumulates across releases** instead of resetting at every tag, and (iii) a stronger signal in the BAFS metadata payload. For PWRU Helper the *specific* pathology is that **an unsigned binary with a new hash every release can never leave the low-prevalence bucket** — each release re-enters it. That is the argument for signing, and it is independent of whether EV or OV is chosen (they are now equivalent for SmartScreen). Cheapest correct move: **Azure Artifact Signing at $9.99/month**, with SignPath Foundation as the free-but-slower alternative already drafted.

### The three experiments that split the matrix

1. **MSI vs portable on the same slow machine.** A1.5 predicts the MSI-installed exe (no `Zone.Identifier`, written into `Program Files` by `msiexec`) **skips the BAFS cloud backend entirely**, while the downloaded portable exe does not. If MSI is fast and portable is slow → **H1 confirmed, H2 partially**. If both are equally slow → H1 is out and H2/H5 own the case. (Caveat: MSI adds `MediaTemplate EmbedCab` decompression at *install* time, not at launch — that is not a confound for launch timing.)
2. **`Unblock-File` on the portable exe** (A3.5). Same file, same hash, MOTW removed. Fast afterwards → H1/H3. Unchanged → H2/H5.
3. **Airplane mode** (C9.4). Fast offline, slow online → a cloud-reputation stall (H1/H3). Equally slow both ways → a local-scan / IO stall (H2/H5).

Run all three on **one** slow machine before instrumenting anything. Two of the three are single commands.

# Recommended measurement recipe

## Tier 0 — no admin, end-user friendly (do this first, on every affected machine)

1. **Environment snapshot** — the 12 no-admin probes of D14, emitted as one JSON blob. Verified to work unelevated (M1, M3, M4). Key fields: `CloudExtendedTimeout`, `CloudBlockLevel`, `MAPSReporting`, `DisableBlockAtFirstSeen`, `VerifiedAndReputablePolicyState`, `SmartScreenEnabled`, MOTW present, `%TEMP%\.net` size, exe attributes, OS build, install kind.
2. **Timing harness** — 7 iterations of `t0 → Start-Process -PassThru → poll MainWindowHandle @10 ms`, reporting **`StartTime − t0` (pre-process)** and **`t1 − t0` (total)**, median/min/max. This alone answers "how much of the 6–10 s is before the process even exists" — the single most decisive number in the case (D12.1, D13.11, D13.12).
3. **The three splitting experiments** (above): MSI vs portable · `Unblock-File` · airplane mode. 7 iterations each.
4. **One in-process trace** with `DOTNET_EnableEventPipe=1` + `DOTNET_EventPipeOutputPath` (D13.7). No admin, no tooling install; the user just sends back a `.nettrace`.
5. **Defender operational log excerpt** — filter the Windows Defender/Operational channel for IDs **2010, 2050, 1116, 1117, 3002** around the launch timestamp (D12.5). A **2050 naming `PWRUHelper.exe`** is the smoking gun for the escalated BAFS-with-upload path (D12.6). Event Viewer reading of this channel does not require admin on most consumer configurations — verify per machine and fall back to Tier 1 if it does.

## Tier 1 — admin, on one cooperative slow machine

6. **`New-MpPerformanceRecording -RecordTo pwru.etl`** → launch → **`Get-MpPerformanceReport -Path pwru.etl -TopFiles 10 -TopScansPerFile 10 -TopProcesses 10`**, plus a CSV export of `-TopScans 1000` (D12.3, D12.4). This gives **per-file Defender scan durations with a reason and a `SkipReason`** — it will name `PWRUHelper.exe` and the 18 extracted native DLLs if Defender owns the time. **This is the single best measurement to run on a slow machine.**
7. **WPR** only if step 6 comes back empty: `wpr -start GeneralProfile -start CPU -start FileIO -start DiskIO -filemode -recordtempto C:\Temp\` → launch → `wpr -stop C:\Temp\pwru.etl`. In WPA, read `ProcessStart` (Generic Events, `Microsoft-Windows-Kernel-Process`) → first foreground activation (Windows In Focus) (D13.1, D13.2, D13.5).
8. **Process Monitor** with the **Duration** column and a `PWRUHelper.exe` filter, to time the `%TEMP%\.net` extraction and the `%APPDATA%` reads individually (D13.10). Use `Tools → File Summary` for the aggregate.

## Tier 2 — actions to evaluate only after Tiers 0–1 attribute the time

- **If BAFS/reputation owns the time:** sign every release with a **stable publisher identity** (Azure Artifact Signing $9.99/mo, EU-eligible, no token, CI-friendly — A4.6/A4.7/A4.8; or the already-drafted free SignPath Foundation route — A4.10). Expect **weeks, not days** for reputation to accumulate (A4.4), and expect no benefit from choosing EV over OV (A4.1).
- **If the `%TEMP%` extraction owns a material share:** set `DOTNET_BUNDLE_EXTRACT_BASE_DIR` to a stable per-user `%LOCALAPPDATA%` path (B5.12) *before* considering dropping `IncludeNativeLibrariesForSelfExtract` (B5.11 — likely a net loss for a downloaded portable build).
- **If hydration owns it:** document "keep PWRU Helper outside OneDrive-backed folders, or mark it *Always keep on this device*" in the README (C8).
- **Do not touch:** `ScanAvgCPULoadFactor` (A2.6), the JIT/tiering knobs (B6.2), ReadyToRun (banned, measured worse), or single-file compression (removed for RAM in v0.14.0).
