# Story E6.S5: Test a key without spending quota

Status: **review** · _OQ-d and OQ-f are answered — ruling **E6-b**, and the recommended defaults were taken with one
correction: **both** probes go through `HttpProviderCore`, not just Azure's (see the Completion Notes)_

_Epic E6 (F) — Bring your own key: Azure · increment 5 · **Release B.1** · the owner's Phase-4 go was given
2026-09-06 (`README.md` § Phase 4)._

> **AC 3 is the honest part, and it has an answer neither document has.** `ux-mode-degrade.md` §3.7 assumes a
> non-billing validation exists — *"DeepL `/usage`, Azure `/languages` or an equivalent"*. **DeepL's is real**:
> `GET /v2/usage` is authenticated, free, and returns the character count — it validates the key *and* answers
> the quota row of §3.7 in one call. **Azure's is not**: `GET /languages?api-version=3.0` is a **public**
> endpoint that takes no subscription key, so a 200 from it proves the internet works and nothing about the
> user's key or region. There is no documented free authenticated probe on the Translator plane.
>
> AC 3 already wrote the escape hatch, and it is the right one: *"where none exists, the button label becomes
> `Test key (uses a few characters)` — the copy must not claim a free check that is not free."* So the shipped
> shape is **asymmetric on purpose**: DeepL's button says `Test key`, Azure's says
> `Test key (uses a few characters)`. Verify the two endpoint facts before you commit to it (T1) — but do not
> "solve" it by testing Azure against `/languages` and calling that a key check. That would be the exact lie the
> AC forbids, told the other way round.

## Story

As a player who just pasted a key,
I want to know immediately whether it works,
So that I find out now rather than during a raid.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E6.S5. Do not weaken._

1. **Given** UX-DR13 and OQ-6
   **When** `Test key` is pressed
   **Then** the button is disabled and reads `Testing…` while in flight, the result lands **in the status line and
   never in a `MessageBox`**, and a failed test **does not clear the key**.
2. **Given** the nine result strings of `ux-mode-degrade.md` §3.7
   **When** each outcome occurs
   **Then** the exact sentence is used, including the distinct wrong-region case naming the region the user typed,
   and the `no internet` case.
3. **Given** OQ-6 is unanswered in the architecture (see the readiness report, gap R-1)
   **When** this story is implemented
   **Then** the validation uses a **non-billing** endpoint where one exists (DeepL `/usage`, Azure `/languages` or
   an equivalent) and, where none exists, the button label becomes `Test key (uses a few characters)` — the copy
   must not claim a free check that is not free.
4. **Given** I11
   **When** the test runs
   **Then** the key never reaches the log.

## The nine strings (`ux-mode-degrade.md` §3.7), verbatim

| Provider | Result | String on `DeepLStatus` / `AzureStatus` |
|---|---|---|
| DeepL | ok | `✓ Key works — DeepL is used for what you write.` |
| DeepL | invalid | `✕ DeepL refused this key. Check you pasted all of it (free keys end in :fx).` |
| DeepL | quota out | `⚠ The key works, but the DeepL quota is used up — the free engines are used until it resets.` |
| Azure | ok | `✓ Key works ({region}) — Azure is used for what you write.` |
| Azure | invalid key | `✕ Azure refused this key. Check the key, and that the region matches your resource.` |
| Azure | wrong region | `✕ Azure did not accept the region "{region}". Pick the one shown on your Azure resource.` |
| Azure | quota out | `⚠ Your 2 million free characters for this month are used up — resets on the 1st.` |
| either | no network | `Could not check the key — no internet connection.` |
| cleared | — | `○ No key — using the free engines (Google, Edge).` |

**UX-DR19 / hint 11: each of these exists exactly once in the codebase.** They go in
`Services/UserMessages.cs` (ruling GAP-4), parameterised on `{region}`, and a source scan asserts no ad-hoc
re-phrasing at a call site. That is what the ten strings E1–E10 cost this project.

**Two of the nine carry claims this story does not own.** The Azure quota row states *"2 million free
characters"* and *"resets on the 1st"* — both **subject to E6.S1 (U4)**, which has never been verified on a real
resource, and the reset day is not verified at all. **If U4 is still open when this ships, drop the reset
clause** and keep the sentence to what is known. E6.S1's copy table is the register.

## Two questions for Winston (with recommended defaults, so nothing is blocked)

- **OQ-d / gap R-1 — "can a key be validated without spending quota?"** *Recommended answer:* **DeepL yes
  (`/v2/usage`), Azure no.** Ship the asymmetric labels of AC 3. The alternative — one honest label for both —
  is tidier and slightly dishonest about DeepL, which really is free to check.
- **OQ-f — does the `Test key` request go through `HttpProviderCore` (and therefore consult and report to the
  gate) or around it?** The test plan raises it and nobody has answered: *"Decides whether a user testing a wrong
  key three times pauses their own provider."*
  *Recommended answer:* **through the core for the Azure translate probe, around it for the DeepL `/usage`
  probe.**
  - Azure's probe **is** a real translate request: routing it around the core would send while the gate is open,
    which is the one thing E2 exists to prevent, and it would lose the redaction and the log line. That three
    wrong keys open the user's own Azure gate is **correct behaviour** — ruling **E2-a**: *"No state may lock the
    user out without a way back"*, and the way back is E6.S3's `ClearAuthBlock` on the next Save.
  - DeepL's `/usage` is not a translation, spends nothing and must answer **even while the gate is open** — a
    user diagnosing a paused provider is exactly who presses this button. Send it on the shared client with the
    same auth header, and give it its own redaction (T6).
  Whichever Winston rules, **record it in the code beside the send**, because the next reader will ask.

### Completion Notes List

**T1 - the two endpoints, settled in writing (AC 3).** Both facts verified against the vendors' own documentation
before any code, and both are now recorded outside this story (`architecture-cible.md` §15, immediately above
§15.2, and the readiness report's **R-1**, closed):

- **DeepL - a real free check.** `GET {host}/v2/usage`, same `Authorization: DeepL-Auth-Key {key}` header and the
  same `:fx` host selection as the translate call (`DeepLTranslator.FreeKey`). It is authenticated, spends no
  quota, and answers `{"character_count":...,"character_limit":...}` — which settles **two** §3.7 rows in one
  call: the key is accepted, and the quota is (or is not) spent. That second half matters more than it looks:
  DeepL answers **456 only on the translate path**, so a key whose allowance is gone would otherwise test
  perfectly healthy and then fail mid-raid.
- **Azure - no free check exists.** `GET /languages?api-version=3.0` is the **public** metadata endpoint: it takes
  no subscription key, so a 200 from it proves the internet works and nothing about the user's key or region.
  There is no documented authenticated free probe on the Translator plane. AC 3's own escape hatch is therefore
  the shipped answer: one five-character real translation (`"hello"`, `en->ru`) through the normal path, and the
  button reads `Test key (uses a few characters)` with a tooltip saying why.

**OQ-f - both probes go through `HttpProviderCore`, and that is one step further than the story recommended.**
The story's default was "through the core for Azure, around it for DeepL", so that a `/usage` probe could answer
while DeepL's own gate was open. Ruling **E6-b** decides it the other way — *"a paused provider's test says it is
paused"* — and it is the better answer for a second reason the story only half-states: a probe sent on the bare
client has **no scrubber and no §10.1 line**, and E1.S5's review found a credential leak (`auth_key=` inside an
HTML error body) on exactly this class. Going through the core buys the redaction, the log line and the gate
consult in one. The accepted cost is stated in the code beside the send: this probe cannot diagnose a provider
while that provider's own window is open — it says "paused" instead, which is at least true.

**A test never clears a gate (E2-i).** Nothing on this path calls `TranslationChains.OnKeySaved` or
`ProviderGate.ClearAuthBlock`; the way out of a refused key is still the **Save** button. Pinned twice — by a
behaviour case (a 401 test, then a second press that is refused with zero requests and finds the `AuthFailed` row
still there) and by a source scan asserting neither provider file names either method, `AppSettings` or
`SettingsService`.

**Deviations from §3.7, all deliberate, all flagged in the story text before implementation.**

1. **The wrong-region row is NOT shipped.** Azure answers a wrong region with the same 401 and the same
   `{"error":{"code":401000,...}}` envelope as a wrong key — the envelope's `code` does not distinguish them, and
   the typed pipeline this story is required to key off (T5) carries only a `TranslationErrorKind`. The story's
   own instruction covers this case: *"if the two are genuinely indistinguishable, say so in a Completion Note
   and ship the combined `invalid key` sentence"*, which already names the region as a thing to check. Inventing
   a distinction the response does not carry would be worse than the merged sentence. **AC 2 is therefore met for
   eight of the nine rows**; the ninth is unreachable through the classifier, and re-reading status codes beside
   the button to fake it would break T5 and E1.S3.
2. **The Azure quota row drops "- resets on the 1st".** The reset day is verified nowhere and the monthly
   allowance itself is still **[UNKNOWN] U4** (E6.S1 has never been run against a real resource). The story's
   instruction was explicit: drop the clause and keep the sentence to what is known.
3. **DeepL's usage sentence claims no period at all** — `"183,053 of 500,000 characters used."`, not "used this
   month". DeepL's current free plan is **1,000,000 characters in total, non-resetting** (`benchmark...` §5.3), so
   a monthly claim would be false for the very users this button exists for. Same reasoning as (2), applied to
   the other vendor.

**Two rows of §3.7 were already shipped and are not re-added** (UX-DR19: exactly once): the "cleared" row is this
app's existing per-engine resting copy — `UserMessages.AzureNoKeyStatus()` and `UpdateDeepLStatus`'s
`○ Using Google (free, no key needed)`. Pressing **Test key** over an empty box renders those and sends nothing,
which is both honest and free.

**One sentence §3.7 does not have, added under ruling E6-b:** `⚠ Not checked - {P} is paused right now.
Try again in {t}.` The `{t}` is rendered by `MainWindow.CountdownText` — the same one the LIVE loop and read-once
use — from a NUMBER of seconds counted in `Services/` (I2: no duration is ever formatted there).

**The in-flight state (T3), which the story called the quiet failure mode.** `RunKeyTestAsync` captures
`button.Content` *before* relabelling and restores it in a `finally`, so the two different labels come back as
themselves; the button is its own re-entrancy flag; and the whole call is bounded by a 12 s
