# Story E6.S5: Test a key without spending quota

Status: **ready-for-dev (Phase 4 — owner's go given)** · _two questions for Winston below (OQ-d, OQ-f), each with
a recommended default so the story is not blocked_

_Epic E6 (F) — Bring your own key: Azure · increment 5 · **Release B.1** · the owner's Phase-4 go was given
2026-09-06 (`README.md` § Phase 4)._

> **AC 3 is the honest part, and it has an answer neither document has.** `ux-mode-degrade.md` §3.7 assumes a
> non-billing validation exists — *"DeepL `/usage`, Azure `/languages` or an equivalent"*. **DeepL's is real**:
> `GET /v2/usage` is authenticated, free, and returns the character count — it validates the key *and* answers
> the quota row of §3.7 in one call. **Azure's is not**: `GET /languages?api-version=3.0` is a **public**
> endpoint that takes no subscription key, so a 200 from it proves the internet works and nothing about the
> user's key or region. There is no documented free authenticated probe on the Translator plane.
>
> AC 3 already wrote the escape hatch, and it is the right one: *"where none exists, the button label becomes
> `Test key (uses a few characters)` — the copy must not claim a free check that is not free."* So the shipped
> shape is **asymmetric on purpose**: DeepL's button says `Test key`, Azure's says
> `Test key (uses a few characters)`. Verify the two endpoint facts before you commit to it (T1) — but do not
> "solve" it by testing Azure against `/languages` and calling that a key check. That would be the exact lie the
> AC forbids, told the other way round.

## Story

As a player who just pasted a key,
I want to know immediately whether it works,
So that I find out now rather than during a raid.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E6.S5. Do not weaken._

1. **Given** UX-DR13 and OQ-6
   **When** `Test key` is pressed
   **Then** the button is disabled and reads `Testing…` while in flight, the result lands **in the status line and
   never in a `MessageBox`**, and a failed test **does not clear the key**.
2. **Given** the nine result strings of `ux-mode-degrade.md` §3.7
   **When** each outcome occurs
   **Then** the exact sentence is used, including the distinct wrong-region case naming the region the user typed,
   and the `no internet` case.
3. **Given** OQ-6 is unanswered in the architecture (see the readiness report, gap R-1)
   **When** this story is implemented
   **Then** the validation uses a **non-billing** endpoint where one exists (DeepL `/usage`, Azure `/languages` or
   an equivalent) and, where none exists, the button label becomes `Test key (uses a few characters)` — the copy
   must not claim a free check that is not free.
4. **Given** I11
   **When** the test runs
   **Then** the key never reaches the log.

## The nine strings (`ux-mode-degrade.md` §3.7), verbatim

| Provider | Result | String on `DeepLStatus` / `AzureStatus` |
|---|---|---|
| DeepL | ok | `✓ Key works — DeepL is used for what you write.` |
| DeepL | invalid | `✕ DeepL refused this key. Check you pasted all of it (free keys end in :fx).` |
| DeepL | quota out | `⚠ The key works, but the DeepL quota is used up — the free engines are used until it resets.` |
| Azure | ok | `✓ Key works ({region}) — Azure is used for what you write.` |
| Azure | invalid key | `✕ Azure refused this key. Check the key, and that the region matches your resource.` |
| Azure | wrong region | `✕ Azure did not accept the region "{region}". Pick the one shown on your Azure resource.` |
| Azure | quota out | `⚠ Your 2 million free characters for this month are used up — resets on the 1st.` |
| either | no network | `Could not check the key — no internet connection.` |
| cleared | — | `○ No key — using the free engines (Google, Edge).` |

**UX-DR19 / hint 11: each of these exists exactly once in the codebase.** They go in
`Services/UserMessages.cs` (ruling GAP-4), parameterised on `{region}`, and a source scan asserts no ad-hoc
re-phrasing at a call site. That is what the ten strings E1–E10 cost this project.

**Two of the nine carry claims this story does not own.** The Azure quota row states *"2 million free
characters"* and *"resets on the 1st"* — both **subject to E6.S1 (U4)**, which has never been verified on a real
resource, and the reset day is not verified at all. **If U4 is still open when this ships, drop the reset
clause** and keep the sentence to what is known. E6.S1's copy table is the register.

      Completion Notes, with dated doc references:

        selection as translation — `DeepLTranslator.FreeKey(key)` (`:87`) picks `api-free.deepl.com` for a `:fx`
        key. Free, authenticated, returns `character_count` / `character_limit` — which is also how the
        **quota-out** row is decided without a translation.
  - [ ] **Azure:** confirm that `GET /languages?api-version=3.0` takes no subscription key (it is the public
        metadata endpoint) and therefore **cannot** validate one. If confirmed: the check is a **1-character
        translate** through the real provider, and the button is labelled `Test key (uses a few characters)`.
  - [ ] Record the finding in `architecture-cible.md` §15 / the readiness report's **R-1**, so the next reader
        does not re-derive it.
- [ ] **T2 — Two buttons (AC 1).** `MainWindow.xaml`, one `GhostButton` beside each Save button (`:622-623` and
      E6.S3's Azure row) — `ux` §4.2's mockup puts them there.
  - [ ] Content bound in **code**, not XAML, so the honest-label rule of AC 3 has exactly one home:
        `DeepLTestButton.Content = UserMessages.TestKeyLabel;` /
        `AzureTestButton.Content = UserMessages.TestKeyLabelCosts;`
  - [ ] `x:Name` on both — the handler must disable **the one that was pressed**, and both must be re-enabled in
        a `finally`.
- [ ] **T3 — The in-flight state (AC 1).**
  ```
  button.IsEnabled = false;
  var label = button.Content;                // restore EXACTLY what was there (the two labels differ)
  button.Content = UserMessages.TestingLabel;   // "Testing…"
  try { … } finally { button.Content = label; button.IsEnabled = true; }
  ```
  - [ ] **The `finally` is not optional.** A throw between the two leaves the button permanently
        `Testing…`/disabled, and the only way back is a restart — the same failure class E5.S4's review found
        with `_readingOnce` sitting seven statements above its `try`.
  - [ ] **Re-entrancy:** a second press while in flight must not start a second request. `if (!button.IsEnabled)
        return;` is enough here (the button *is* the flag) — this is not the shared-OCR-engine case that needed
        `_readingOnce`.
  - [ ] **Bound it.** A test that hangs leaves the button dead. Use a `CancellationTokenSource` with a short
        budget and cancel it on window close, the way `_readOnceCts` does (`MainWindow.xaml.cs:105-106`,
        `OnClosing` at `:291`). **I3 applies**: an `HttpClient` timeout is an `OperationCanceledException` whose
        token is **not** cancelled — every catch filters on `cts.IsCancellationRequested`, never on the
        exception type. `MainWindow.Ocr.cs`'s read-once catch is the shape to copy.
- [ ] **T4 — The result, in the status line, never in a `MessageBox` (AC 1, AC 2).**
  - [ ] Write into `DeepLStatus` (`MainWindow.xaml:625`) / `AzureStatus` (E6.S3's). `UpdateDeepLStatus`
        (`MainWindow.Translate.cs:253-259`) is the existing pattern.
  - [ ] **Never a `MessageBox`** — UX principle 3, NFR12, and `ux` §4.3's control table says it in the
        `TestKeyButton` row. (If one were ever justified it would be `MessageBox.Show(this, …)` with an owner,
        `project-context.md` — but it is not justified here.)
  - [ ] **A failed test does not clear the key** (AC 1). The handler reads the boxes; it must not write
        `_settings` at all. Easiest way to guarantee it: the method takes the key/region as **parameters** and
        touches no field.
  - [ ] **The wrong-region case is Azure's most likely mistake** (`ux` flow (c).4) and gets its own sentence
        naming the region **the user typed**. Distinguishing it from a bad key is the interesting part: both
        arrive as 401. Use the response's error envelope — Azure returns `{"error":{"code":…,"message":…}}` and
        the region failure carries its own code. **If the two are genuinely indistinguishable, say so in a
        Completion Note and ship the combined `invalid key` sentence**, which already names the region as a
        thing to check. Do **not** guess a distinction the response does not carry — inventing one is worse than
        the merged sentence.
  - [ ] `no internet` is `TranslationErrorKind.Network` from the classifier, not a string match.
- [ ] **T5 — Route through the typed pipeline, not around it.** The outcome-to-sentence mapping keys off
      **`TranslationErrorKind`**, which `ProviderErrorMapper` already produces (`AuthFailed`,
      `QuotaExhausted`, `RateLimited`, `Network`, …). Do not re-read status codes in the code-behind: E1.S3 exists
      so exactly one place in this app decides what a 403 means, and E1.S6's `UserMessages` exists so exactly one
      place decides what the player reads about it.
      **The mapping is a pure function** — `(providerId, kind, region) → string` — living in
      `Services/UserMessages.cs` so the nine strings are asserted headlessly (GAP-4). The code-behind calls it.
- [ ] **T6 — I11 (AC 4).** The key is in a header and in `ProviderOptions.Secret` (E6.S2), which the core scrubs
      from any body head before the §10.1 line (`DeepLTranslator.cs:49-54`). **If the DeepL `/usage` probe is
      sent outside `HttpProviderCore`** (see OQ-f below), it has no scrubber and no log line — write a test that
      no log line produced by a failed test contains the key. E1.S5's review found a credential leak in exactly
      this class (`auth_key=` inside an HTML error body) and E2.S5's review found two more on keyed providers.
- [ ] **T7 — Tests.** Unit through the fake handler: each of the nine outcomes maps to the right sentence; the
      `finally` restores label and enabled state on the failure path; a failed test leaves `_settings` untouched;
      no key in any log line.
- [ ] **T8 — `dotnet test tests/PWRUHelper.Tests`.** Green, headless, **no network** (IS-10/CI-2), no
      `%AppData%` write.

## Two questions for Winston (with recommended defaults, so nothing is blocked)

- **OQ-d / gap R-1 — "can a key be validated without spending quota?"** *Recommended answer:* **DeepL yes
  (`/v2/usage`), Azure no.** Ship the asymmetric labels of AC 3. The alternative — one honest label for both —
  is tidier and slightly dishonest about DeepL, which really is free to check.
- **OQ-f — does the `Test key` request go through `HttpProviderCore` (and therefore consult and report to the
  gate) or around it?** The test plan raises it and nobody has answered: *"Decides whether a user testing a wrong
  key three times pauses their own provider."*
  *Recommended answer:* **through the core for the Azure translate probe, around it for the DeepL `/usage`
  probe.**
  - Azure's probe **is** a real translate request: routing it around the core would send while the gate is open,
    which is the one thing E2 exists to prevent, and it would lose the redaction and the log line. That three
    wrong keys open the user's own Azure gate is **correct behaviour** — ruling **E2-a**: *"No state may lock the
    user out without a way back"*, and the way back is E6.S3's `ClearAuthBlock` on the next Save.
  - DeepL's `/usage` is not a translation, spends nothing and must answer **even while the gate is open** — a
    user diagnosing a paused provider is exactly who presses this button. Send it on the shared client with the
    same auth header, and give it its own redaction (T6).
  Whichever Winston rules, **record it in the code beside the send**, because the next reader will ask.

## Dev Notes

### Invariants this story must keep

- **I11 — keys never logged.** AC 4, and the `/usage` path is the one with no core behind it.
- **I3 — the OCE trap.** A `Test key` that times out must render `no internet`/`timeout`, not silence. Filter
  every OCE catch on `cts.IsCancellationRequested`.
- **I2 — `Services/` never formats for display.** The nine sentences are strings, not countdowns; nothing here
  formats a time, so the rule is easy to keep — but the pure mapping function still lives in `Services/` (GAP-4)
  and returns text, exactly as `UserMessages.Sentence(kind)` does.
- **NFR12 — no modal from a background path**, and this is not even a background path. No `MessageBox`.
- **I12** — this story adds **buttons**, not persisted controls, so `_restoringSettings` does not apply. Do not
  add a handler that writes settings, and the question does not arise.

### Rulings that apply

- **GAP-4 / UX-DR19** — every one of the nine lives in `Services/UserMessages.cs`, exactly once.
- **E2-i** — `ClearAuthBlock` clears `AuthFailed`/`QuotaExhausted` only. Relevant because OQ-f's answer decides
  whether a failed test can open a gate at all.
- **E2-a** — nothing may lock the user out without a way back; the Save button is it.
- **E1.S3** — the classifier is the single vocabulary for "what a status code means". Do not re-decide here.

### Repo traps

- **`AzureStatus` and `DeepLStatus` are also written by `UpdateEngineStatusUi`** (E6.S3) and by the Save
  handlers. A test result must not be erased half a second later by a refresh, and a refresh must not be
  suppressed for ever by a test result. Simplest rule that works: the **Save** handler and
  `UpdateEngineStatusUi` write the *configured* state; the **Test** handler overwrites it with the result;
  the next Save or restart resets it. Write that rule in a comment.
- **`ShowToast` routes to the overlay in compact mode** (`MainWindow.xaml.cs:473-476`). Not used here — the
  result goes in the status line — but do not "helpfully" add a toast: the About tab is open when this button is
  pressed, by definition.
- **`GhostButton` + `Padding="12,4"`** is the existing button shape in this block (`MainWindow.xaml:622-623`).
  UX-DR18: no new brush, font, image or colour.
- **The two labels differ**, so restoring `Content` must restore what was there, not a shared constant.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Testing

- **TP-IDs:** the test plan has no TP-KEY-* family; the closest existing rows are **TP-SET-09** (key save clears
  the auth block — E6.S3's) and the **TP-MAP-** family, which this story consumes rather than extends. Land the
  nine cases as **`AzureKeyTestTests`** / additions to `UserMessagesTests`, and record the new IDs in the test
  plan's §3.9 table so traceability stays real (`epics.md` DoD: *"every §3.7 string is reachable and exists
  exactly once in the codebase (UX-DR19)"*).
- **The nine, one case each**, through the fake handler (IS-8/IS-10/IS-11): DeepL ok / invalid / quota-out;
  Azure ok / invalid-key / wrong-region / quota-out; no-network (both); cleared.
- **The `{region}` substitution** is asserted on a region the user typed that is **not** in the seeded nine —
  the wrong-region sentence quoting a value the app never offered is the whole point of it.
- **UX-DR19 source scan:** each of the nine literals appears **exactly once** in production source. The
  `PublishFlagsTests`/`ProviderStateStoreTests` file-reading shape is the tool (`Code()` strips comments), and
  `UserMessagesTests` already has house-rule scans to extend.
- **AC 1 negatives:** on failure the key box still holds the key and `_settings.AzureApiKey` is unchanged; the
  button's label and `IsEnabled` are restored even when the send throws; **no `MessageBox` type is named in the
  handler** (source scan — it is the cheap way to pin "never in a `MessageBox`").
- **AC 4:** no `RequestLog` line from a failed test contains the key.
- **Isolation:** IS-8/IS-10/IS-11 (handler seam, no real network, recording handler), IS-9 (`azure-error-auth.json`,
  `azure-error-quota.json` — E6.S2's), IS-1/IS-3 (`TempSettings`) for the "does not clear the key" case,
  **CI-3** (the in-flight state is asserted on the *requested* budget, never by waiting).
- **Manual (the epic asks for it):** a real key, and a deliberately wrong region.
- **Must keep passing unchanged:** `UserMessagesTests`' house rules (no HTTP code in any deck sentence — note
  `✕`/`✓`/`⚠` are glyphs, not codes), `ProviderErrorMapperTests`, `StartupSettingsTests`.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. **The label.** The Azure button reads `Test key (uses a few characters)`; DeepL's reads `Test key`. If both
   read the same, T1's finding was skipped.
3. **Wrong region, the likely mistake.** Real Azure key + `eastus` when the resource is `westeurope`: the status
   names `"eastus"` — the value typed — and tells the user where to find the right one. No `MessageBox` appears.
4. **A failed test does not clear the key.** After step 3, the key box still holds the key; restart and it is
   still saved.
5. **The button comes back.** Disconnect the network mid-test: the status says `Could not check the key — no
   internet connection.` and the button is enabled again with its original label.
6. **I11.** Copy the error report after step 3: no key in it, and no key in
   `%AppData%\PWRUHelper\logs`.
