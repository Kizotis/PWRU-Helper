# Story E6.S4: "Use my key for screen reading" opt-in, off by default

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E6 (F) — Bring your own key: Azure · increment 5 · **Release B.1** · the owner's Phase-4 go was given
2026-09-06 (`README.md` § Phase 4)._

> **One checkbox, and the whole story is about the word "not".** The AC that carries the risk is AC 1:
> `UseKeyForReading` off ⇒ Azure is **not constructed into the read chain — asserted by a test on the built
> chain, not by a runtime guard.** That is the same shape as I8's DeepL rule and it is deliberate: a runtime
> guard is a line someone can move; a builder that never constructs the tier cannot be talked into it by a
> setting, a refactor or a future story.
>
> **Why it is off by default is arithmetic, not caution.** `benchmark…` §8.1 puts a heavy LIVE user at ~48 k
> characters per hour of busy chat; F0 is 2 M/month. The LIVE loop translates **every new chat line it sees**,
> unattended, for as long as the app is open. Risk **R-15** in the test plan states the failure exactly:
> *"a user's Azure F0 quota drained by LIVE because the opt-in arrived pre-ticked or defaulted on."* Ruling
> **OQ-12** puts it in one line: *an opt-in that arrives pre-ticked is not an opt-in.*

## Story

As a player with a free monthly quota,
I want to decide whether the screen reader may spend it,
So that a free allowance cannot disappear in three evenings without my having chosen it.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E6.S4. Do not weaken._

1. **Given** `UseKeyForReading` defaults to **false** (§12)
   **When** a key is saved but the box is unticked
   **Then** Azure is **not constructed into the read chain** — asserted by a test on the built chain, not by a
   runtime guard.
2. **Given** the box is ticked
   **When** the handler runs
   **Then** the read chain is rebuilt immediately, exactly as `DeepLSaveKey_Click` rebuilds the write chain
   (`MainWindow.Translate.cs:239`), and the checkbox obeys `_restoringSettings` (I12).
3. **Given** UX-DR15 and the arithmetic of `ux-mode-degrade.md` §4.3
   **When** the option is rendered
   **Then** it carries its cost sentence: *"Azure gives you 2 million characters a month for free — roughly 20 to
   40 hours of busy chat. Screen reading is off by default because live mode reads every new line and can use it
   up in a few evenings."* — subject to E6.S1's answer, and re-derived if the shared cache measurably changes the
   multiplier.
4. **Given** OQ-12 (resolved by John): an opt-in that arrives pre-ticked is not an opt-in
   **When** an existing user upgrades with a key already saved
   **Then** the box is off.
5. **Given** R9
   **When** Azure returns `QuotaExhausted`
   **Then** the gate opens for an hour rather than retrying, and the chain falls to the free tiers.

## Dev Notes

### Invariants this story must keep

- **I8 — DeepL is never in the read chain**, and this story is the first one that puts *anything* keyed there.
  Read `TranslationChains.cs:15-21` before touching `BuildRead`: the class comment is the invariant's home, and
  it already anticipates this story — *"E6 lands Azure-for-reading behind an opt-in, and the invariant that
  survives it is the one about DeepL"* (`MainWindow.Translate.cs:227-230`). **Update neither comment to say
  "no keys on the read path"; both are already worded correctly.**
- **I12** — the checkbox's handler bails on `_restoringSettings`; `ApplySettings` applies the side effect
  explicitly.
- **I13** — no default changes for an existing user, so no `Migrate` step and no bump. AC 4 is delivered *by*
  that fact.
- **I9** — one gate per provider, shared by both chains. The read chain's `AzureTranslator` and the write
  chain's are two objects over **one** `azure` gate. That is right, and it has a consequence worth knowing: a
  `QuotaExhausted` earned by the Translator tab also pauses the read path, which is exactly what a
  *quota* means.
- **I1** — `ITranslator` unchanged; priority is a ctor parameter.

### Rulings that apply

- **OQ-12** (John) — the opt-in stays off for a migrating user with a key already saved. AC 4.
- **R-7** — the setting is `UseKeyForReading`. `ux` §4.3's `AzureForReading` is the rejected spelling; the
  **control** may still be named `AzureForReadingCheck` (that is a control name, not a setting name) — keeping
  it makes `ux` §4.3's table row findable.
- **E3-a** — the chain skips a tier on `BlockedUntil > Now()`, never on `State == Open`. AC 5 rides on it.
- **E2-f / E2-h** — the quota window is 60 minutes with probes; a 30-day `Retry-After` is deliberately
  discarded. AC 5's "opens for an hour rather than retrying" is already true.
- **E4-a** — the shared cache is provider-agnostic: with the opt-in **off**, a line the Translator tab
  translated **through Azure** can still be served to the read path from the cache. That is accepted (§8.2
  trade-off) and it does **not** violate AC 1: *"I8 is about **requests**, not cached strings"*
  (`TranslationChains.cs:180-187`). Worth knowing before someone reports it as a bug.
- **GAP-4** — the cost sentence lives in `Services/UserMessages.cs`.

### Repo traps

- **`_readTranslator` / `_readOnceTranslator` are `readonly` today** (`MainWindow.xaml.cs:60-61`). E6.S3 drops
  it. If E6.S4 is implemented first for any reason, it drops it — but then E6.S3's AC 6 has nothing to reuse.
  **Keep the stated order.**
- **The read chain is built TWICE** (`:137-138`) with two different priorities. Both need the Azure tier and
  both get it automatically from `BuildRead` — but only if T1 passes `priority` through. A test that builds only
  the default (`Background`) chain will not catch the omission; sweep both, as `TP_CHN_14` does (`:162`).
- **`CheckBox` `Checked`/`Unchecked` are two events.** `SquadUppercaseCheck` is the shape already in the file.
- **`ApplySettings` is one `try`/`finally`** (`:212-257`); put the new line with the other Azure restores.
- **`ChainCompositionTests` scans files outside `Services/`** for `new CachingTranslator` and for
  `ProviderGates`. `RebuildReadChains` names `TranslationChains` only — keep it that way.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Testing

- **TP-IDs landed:** **TP-SET-08** — *"Azure key set, `UseKeyForReading` **off** ⇒ Azure is **not** a tier of the
  built read chain; **on** ⇒ it is the **first** tier"* (oracle: chain composition; maps R-15, story 29) — and
  **TP-SET-04** (fresh install ⇒ `UseKeyForReading == false`).
- **AC 1 is asserted on the BUILT CHAIN**, through `ChainCompositionTests`' existing `TiersOf`/`IdsOf` helpers —
  not through a behaviour test with a fake handler, and not through a source scan. Sweep **both** priorities.
- **`ChainCompositionTests.EveryPermutation()` (`:112-139`) must gain the Azure pair.** It varies **one**
  property per permutation by reflection, so `AzureApiKey = "set"` **and** `UseKeyForReading = true` — the only
  combination that puts Azure on the read path — is a shape it structurally cannot generate. Add the pair
  explicitly to the seed list at `:114-120`, beside the four `DeepLApiKey` shapes, **with a region**, and add its
  negatives: key+region without the tick, tick without a key, tick with a key but no region. That last one is
  the guaranteed-401-first-in-the-LIVE-chain case.
  TP-CHN-14 (I8) then sweeps the pair too, for free, which is the second reason to put it there.
- **AC 4** — a load-only case: a `TempSettings` file containing `AzureApiKey` and **no** `UseKeyForReading` key
  at all (an old file) loads with `UseKeyForReading == false`, `SettingsVersion` unchanged, and the built read
  chain has no Azure tier.
- **AC 2 / I12** — **TP-SET-05**'s shape extended to this control: a saved `"UseKeyForReading": true` survives a
  load → apply → save cycle with no user interaction (UX hint 8). And **TP-SET-06**: the handler entered during
  `ApplySettings` returns before writing.
- **AC 5** — L2 over the built read chain with the opt-in **on**: the fake handler returns Azure's
  `azure-error-quota.json` 403 envelope; the call is served by the next tier, the Azure gate's `BlockedUntil` is
  ~60 min out, and a second call issues **zero** Azure requests. Use a **local** `ProviderGate` with an injected
  clock (IS-6) so the file needs no `Gates` collection and **nothing sleeps** (CI-3) — `ReadOnceStatusTests` is
  the precedent.
- **Isolation:** IS-1/IS-3 (`TempSettings`) for the settings cases; IS-6 (injected clock) and IS-8/IS-10/IS-11
  (handler seam, recording handler) for AC 5; IS-9's `azure-error-quota.json` (E6.S2 creates it). CI-1, CI-3.
- **Must keep passing unchanged:** `TP_CHN_14_DeepL_is_structurally_absent_from_the_read_chain` — this is the
  story that puts a **keyed** provider on the read path, so that test stops being about "no keys there" and
  becomes about DeepL specifically. It already is, by construction and by name. Read it before you touch
  `BuildRead`. Also: `LivePauseTests`, `ReadOnceStatusTests`, `StartupSettingsTests`, `TemplateRenderTests`.

## Size, dependencies, risk

**Size:** S · **Depends on:** **E6.S3** (the settings fields, the `RebuildReadChains` seam, the About-tab block)
and **E3.S7** (`BuildRead`'s `priority` parameter and its two instances — done) · **Risk:** **low-medium.** The
code is a conditional `tiers.Add` and a handler. The three ways to get it wrong are all silent: forgetting
`priority:` (the LIVE loop quietly gains `Interactive` and eats the reserve §5.4 exists to protect), forgetting
the region in the condition (a guaranteed-401 tier first in the LIVE chain, opening its own gate on tick one),
and seeding the checkbox from "a key exists" (AC 4 gone, R-15 realised) ·
**DoD:** the read chain test passes both ways.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. **AC 4, the migration case.** Take a `settings.json` with an Azure key and no `UseKeyForReading` key. Start:
   the box is **off**.
3. **AC 1.** With the key saved and the box **off**, run LIVE over a chat region and watch the diagnostic log:
   **no `tr` line names `azure`.** Tick the box: the next tick's line does.
4. **AC 2.** Tick, close, reopen: still ticked, and the read chain still starts at Azure — the setting persisted
   *and* the restore did not clobber it (that is the v0.12.3 class).
5. **AC 5.** Force Azure's 403 quota envelope: the feed keeps filling from Google with no error text anywhere
   (UX hint 5 — a successful fallback is silent), and no Azure request is sent again for an hour.
6. **The reserve.** With the box on, start LIVE and then press Translate on the Translator tab: the interactive
   translation is not starved by the loop. (§5.4's reserve — this is what `priority:` buys.)
