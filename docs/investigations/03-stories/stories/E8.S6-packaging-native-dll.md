# Story E8.S6: How `bergamot.dll` ships — bundled, or downloaded with the models 🔬 spike (U7) + decision

Status: **blocked-dep · 🔬 spike (U7) · prototype branch only — needs E8.S2 to have something to publish, and
E9.S12's instrumented machines for the cold-start half**

_Epic E8 (H) — Offline fallback prototype · increment 7 · **Release C** · prototype branch, merges only on a go._

> **This story exists so that fixing P2 cannot quietly make P1 worse.** The whole investigation started with two
> problems; P1 is a 6–10 s cold start on some machines, and `IncludeNativeLibrariesForSelfExtract`'s first-run
> extraction to `%TEMP%\.net\…` is one of its named suspects. `bergamot.dll` is 21.4 MiB of native code. Putting
> it in the bundle re-arms that mechanism, on purpose, in the same release that was supposed to fix the other
> problem.
>
> **And it is the story that can break a promise nothing else may touch.** The portable exe's *"one file, put it
> anywhere"* is not negotiable, and `PublishFlagsTests.cs:62-70` enforces flag parity across the three build
> paths. **CI-7 names this story as the only thing in the whole plan that could legitimately weaken that test —
> and only with a measurement behind it.**
>
> **The recommendation is written below before the measurement, because it is falsifiable and cheap: download
> the DLL with the models. 0 MB of exe growth, no change to `%TEMP%`, no change to the build files, no change to
> `PublishFlagsTests`.** The measurement's job is to confirm it, or to find the reason it cannot work.

## Story

As the owner,
I want to know whether the offline option costs a startup regression,
So that fixing P2 cannot quietly make P1 worse.

## Acceptance Criteria

_All four Givens below are copied **verbatim** from `epics.md` § Story E8.S1 (the U7 spike, which under this cut
is the packaging decision). AC 5 and AC 6 are `[DERIVED]` and cover the third layout `epics.md` did not
consider — the DLL downloaded alongside the models — and the licence obligation that layout carries._

1. **Given** U7 and §7.6 constraint 4 — bundling the native DLL re-arms `IncludeNativeLibrariesForSelfExtract`
   extraction to `%TEMP%\.net\…`, the exact mechanism implicated in P1
   **When** the prototype is published **both ways** (bundled, and beside the exe)
   **Then** `tools/diagnostics/Measure-Startup.ps1` is run on both, on a personal Defender-only machine,
   reporting run #0 (fresh hash) and warm runs per `mesures-protocole.md`.

2. **Exit criterion (measurable).** `pre_process_ms` and `in_process_ms` for both layouts, and the file count and
   total size of `%TEMP%\.net\PWRUHelper\<id>` after each first launch (baseline: **5 WPF native DLLs, 8.2 MB**).

3. **Go / no-go.** **Go:** beside-the-exe shows no measurable cold-start regression against today's baseline ⇒
   that is the layout. **No-go:** either layout regresses cold start materially ⇒ the offline engine does not
   ship in the portable build, and the finding goes to the owner. **Hard constraint either way:** the portable
   exe's "one file, put it anywhere" promise is not negotiable, and `PublishFlagsTests.cs:62-70` (flag parity
   across the three build paths) is not weakened without a measurement that says otherwise.

4. **Test expectations.** `PublishFlagsTests.cs:44-70` must stay green on `main`; any change to it is part of the
   merge decision, not of the spike.

5. `[DERIVED — §7.6 constraint 4 vs the portable promise; benchmark §10 "download on first use into the editable-copy
   directory; do not embed"]` **Given** a third layout — the DLL **downloaded with the models** into the model
   store and loaded from there
   **When** it is evaluated
   **Then** it is measured on the same two axes as the other two (exe size · `%TEMP%` after first launch) and,
   if it works, it is **preferred**: it costs **0 MB** of exe growth, changes nothing in `%TEMP%`, changes no
   build file and therefore requires **no** change to `PublishFlagsTests`.

6. `[DERIVED — §7.6 constraint 8, NFR10, MPL-2.0]` **Given** MPL-2.0
   **When** the DLL is redistributed by whichever route wins
   **Then** what must ship alongside it is written down and shipped: the **MPL-2.0 licence text**, a
   **statement of which files are covered**, and a **pointer to their source form**. This is stated as a
   requirement of the packaging, not as a footnote in the About tab.

## Dev Notes

### The recommendation, stated before the measurement so it can be falsified

**Download the DLL with the models (layout C).** Four reasons, in the order they matter:

1. **It is the only layout that costs nothing to anybody who never enables the feature.** §7.6's models are
   already "downloaded on first use, never embedded"; the DLL is 21.4 MiB of the same kind of thing, needed by
   the same users, at the same moment. Sizing a full deployment, `benchmark…` §10 puts the DLL in the
   **download** column already: *"bundling would push the exe to ~325 MB and make every user pay for a feature
   most never enable — and v0.14.0 removed single-file compression precisely to avoid that class of cost."*
2. **It leaves `%TEMP%` alone.** The whole of U7 is the question "does the offline option cost a P1
   regression?", and a layout that adds nothing to the self-extraction set answers it with a **no** that needs
   no measurement to defend.
3. **It touches no build file, so `PublishFlagsTests` is untouched** — and CI-7's "only with a measurement
   behind it" carve-out is never spent.
4. **MPL-2.0 is easier to honour, not harder.** The licence text and the source pointer travel in the mirror
   release, physically beside the binary they cover.

**The two things that could kill it**, and T1 checks both in an hour: `ExcludeAssets="native"` must still
produce a usable managed binding, and the resolver must find a DLL outside the app directory. Neither is exotic
— `NativeLibrary.SetDllImportResolver` is the documented BCL mechanism for exactly this — but neither is assumed.

**Layout B is not a portable-build candidate at all.** AC 3 calls "one file, put it anywhere" non-negotiable,
and B is the layout that breaks it. It stays in the table as the control that `epics.md` asked for and as the
only sane option **if** the MSI ever ships the engine pre-installed — which `plan-migration.md`'s parallel track
already marks *"Not in this track… optional, low value, and it would require deliberately weakening
`PublishFlagsTests.cs:62-70`. Do not start it without a measurement on an affected machine."*

### Invariants and standing rules this story must keep

- **The portable exe is one file.** AC 3, and it is the app's distribution promise.
- **No `ReadyToRun`, no single-file compression.** Both are recorded deliberate non-features
  (`project-context.md`, `pwru-startup-perf`); compression cost ~118 MB of RAM and was removed on purpose in
  v0.14.0. A packaging story is exactly where somebody would re-propose them.
- **CI-7** — `PublishFlagsTests` is untouched unless packaging changes, and the SignPath wiring must edit
  `.github/workflows/release.yml` **and** `packaging/signpath-signing.md` in the same PR (`:72-79`).
- **CI-8** — no model download and no native DLL in CI.
- **R-14** (test-plan §risk table) — *"`PublishFlagsTests` weakened by accident while wiring SignPath or shipping
  the Bergamot DLL"*. This story is that risk's owner.
- **NFR10** — MPL-2.0 declared.

### Repo traps

- **`Build MSI Installer.bat` carries a hardcoded `VERSION=`** that must be kept in sync with
  `PWRUHelper.csproj`'s `<Version>` (`project-context.md`'s release checklist, step 2). A packaging story that
  edits that file must not disturb it.
- **`installer/Product.wxs`'s `UpgradeCode` is FIXED FOREVER** and the version needs a fourth part (`X.Y.Z.0`).
- **`.github/workflows/release.yml` attaches both artefacts**, and the checklist's step 5 is
  `gh release view vX.Y.Z --json name,assets`. A layout that adds a file to the release changes what that
  verification expects.
- **`packaging/signpath-signing.md` contains a replacement `release.yml`** and `PublishFlagsTests` pins the two
  to identical flags. It is the fourth file, and it is the one people forget.
- **The models mirror is a GitHub release under the owner's account.** Creating it is an **owner task**
  (E8.S3's T8); this story only decides whether the DLL goes in it too.

**Size:** **M** · **Depends on:** **E8.S2** (something to publish) and a machine with the diagnostics scripts —
**E9.S12**, which `epics.md` notes is a *parallel* epic and not a later one ·
**Blocks:** the merge decision, not the other stories ·

change to it belongs to the merge decision ·

## How to verify manually

1. Build layout C. `ls -l` the publish output: **no `bergamot.dll`**, exe size unchanged from a build with no
   package.
2. Launch it fresh (a copy Windows has never seen, on a Defender-only machine): `%TEMP%\.net\PWRUHelper\<id>`
   holds **5 files, 8.2 MB** — the baseline, unchanged.
3. Install the engine through About, translate offline: the resolver finds the DLL in the model store, and the
   translation comes back.
4. Build layout A. Exe is ~200 MB; after a first launch `%TEMP%` holds ~6 files, ~30 MB. Run
   `Measure-Startup.ps1` run #0 and warm.
5. Compare `pre_process_ms` and `in_process_ms` across the three, on the same machine, same session.
6. `dotnet test tests/PWRUHelper.Tests` — `PublishFlagsTests` green, **unchanged**.
7. Read the MPL-2.0 notice from the About tab, and confirm the licence text and source pointer are present
   wherever the DLL is distributed from.
