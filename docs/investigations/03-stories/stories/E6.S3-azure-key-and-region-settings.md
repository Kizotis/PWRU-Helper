# Story E6.S3: Azure key and region settings, re-entrancy-safe

Status: **done**

_Epic E6 (F) — Bring your own key: Azure · increment 5 · **Release B.1** · the owner's Phase-4 go was given
2026-09-06 (`README.md` § Phase 4)._

> **This is the riskiest story of release B, and the risk is not Azure.** `plan-migration.md` increment 5 names
> it: *"Not the provider — the endpoint is contracted and documented — but the **settings surface**, which is the
> code path with the most expensive prior bugs in this repo (two migrations exist solely to undo one)."*
> `SettingsService.Migrate` still carries both of them (`:140-149`): v1 set the filter default, **v2 set it again
> because v1 lost a race with a XAML-load handler that wrote the not-yet-restored UI back to disk.** Every
> control this story adds is one more entry in that race.
>
> **The counter-intuitive AC is #2: do NOT bump `SettingsVersion`.** I13 says changed defaults reach existing
> users only through a `Migrate` step — and there are **no changed defaults here**. Five *new* fields deserialise
> to their initializers from an old file, which is the intended behaviour. A bump would be a `Migrate` step that
> does nothing, run once against every user's file, for no reason. §12 rules it explicitly and **TP-SET-02**
> asserts it.

## Story

As a player,
I want my key and region to still be there tomorrow,
So that the settings bug class that already cost this project two migrations does not claim a third.

1. **Given** §12
   **When** the five fields are added to `AppSettings` (`Services/SettingsService.cs:7-81`)
   **Then** they are `AzureApiKey` (`""`), `AzureRegion` (`""`), `UseKeyForReading` (**`false`**),

   **When** these five fields land
   **Then** **`SettingsVersion` is NOT bumped and `Migrate` gains no step** — the fields are new, so an old
   `settings.json` deserialises them to their defaults, which is the intended behaviour.
3. **Given** I12 and the v0.12.3/v0.13.0 bug class
   **When** `AzureKeyBox`, `AzureRegionCombo` and the two check boxes are added
   **Then** every change handler starts with `if (_restoringSettings) return;` and `ApplySettings`
   (`MainWindow.xaml.cs:173-193`) applies their UI side effects **explicitly**, through a new
   `UpdateEngineStatusUi()` called where `UpdateOcrFilterUi` is called today (`:193`).
4. **Given** the region control (UX-DR16)
   **When** it is built
   **Then** it is a `ComboBox IsEditable="True"` seeded with `global, westeurope, francecentral, northeurope,
   eastus, eastus2, westus2, uksouth, swedencentral`, free text accepted, using the existing
   `SelectTag`/`SelectedTag` helpers (`MainWindow.xaml.cs:359-370`) — **not** a re-rolled loop.
5. **Given** a key without a region is a guaranteed 401
   **When** Save is pressed with one of the two empty
   **Then** the status line says so and no request is sent.
6. **Given** saving a key
   **When** the handler runs
   **Then** it calls `ProviderGates.ClearAuthBlock("azure")` and rebuilds **both** chains (the read chain too,
   since `UseKeyForReading` can put Azure in it), so a corrected key takes effect immediately instead of waiting
   out an `AuthFailed` window.
7. **Given** I11
   **When** the error report is copied
   **Then** no key appears in it (`MainWindow.xaml.cs:312-322`).

## Dev Notes

### Invariants this story must keep

- **I12 — settings-restore re-entrancy.** The whole story. Three rules, from `project-context.md` and
  `MainWindow.xaml.cs:28-35`: (1) every change handler bails on `_restoringSettings`; (2) `ApplySettings` applies
  UI side effects **explicitly**; (3) the flag starts **true at construction**, not at the top of
  `ApplySettings` — because `InitializeComponent()` fires handlers before `ApplySettings` exists.
- **I13 — changed defaults reach existing users only via `SettingsVersion` + `Migrate`.** Kept by **not** acting:
  nothing changes for an existing user, so nothing may run against their file. AC 2.
- **I11 — keys never logged, never in the error report.** AC 7 here; `Secret:` in E6.S2's `ProviderOptions`.
- **I8 — DeepL is never in the read chain.** Untouched: this story adds a tier to `BuildWrite` only.
  `ChainCompositionTests.TP_CHN_14` sweeps every settings shape and must stay green — and it will now sweep the
  new `AzureApiKey`/`UseKeyForReading` properties automatically (see Testing).
- **I10 — nothing reads `provider-state.json` before first paint.** `ClearAuthBlock` runs from a **click**, not
  from the ctor/`ApplySettings`/`OnWindowLoaded`. TP-START-02's three body scans stay green.

- **R-7** — architecture §12's names win: `AzureApiKey`, `AzureRegion`, `UseKeyForReading`,

  drift table.)
- **R-4** — `OfflineFallbackEnabled` is written by the About tab's **Download/Remove** actions (E8.S3). No

- **E2-i** — `ClearAuthBlock` clears account-scoped rows only.

  inside the loop or falls out). With `IsEditable="True"` that is the normal case for a free-text region. T5's
  `.Text` fallback is not belt-and-braces; it is the restore path for anyone outside the nine seeded values.
- **`SelectedTag` returns `null` for typed text**, because there is no `ComboBoxItem`. Every read of the region
  is `SelectedTag(AzureRegionCombo) ?? AzureRegionCombo.Text`.
- **`ApplySettings` is one `try` with one `finally`** (`:212-257`). A new line that throws inside it leaves
  `_restoringSettings` **false** (the `finally` runs) but the restore incomplete — order the additions after the
  window-placement block, with the other key box, where nothing throws.
- **`_readTranslator` and `_readOnceTranslator` are `readonly`** (`MainWindow.xaml.cs:60-61`) and the comment at
  `:56-58` explains why they are assigned in the ctor body. AC 6's read-chain rebuild needs them writable. Drop
  `readonly`, keep the ctor-body assignment, and keep the comment honest.
- **`_readChain`** (the `out ChainTranslator` of `TranslationChains.BuildRead`, `MainWindow.xaml.cs:137`) is what
  E5.S1's LIVE pause and E7.S3's chip read. A rebuild that reassigns `_readTranslator` and forgets `_readChain`
  leaves the pause check pointing at a dead chain over the same gates — it would still *work* (I9: same gates),
  which is exactly why it would go unnoticed. Reassign all three together.
- **`MainTabs_SelectionChanged` must keep its `e.Source is TabControl` filter** and the tab order is fixed
  (`project-context.md`). This story adds no tab.
- **`StartupSettingsTests` uses `TempSettings`** (`StaTestHost.cs:82-101`) and asserts **the file on disk**, not
