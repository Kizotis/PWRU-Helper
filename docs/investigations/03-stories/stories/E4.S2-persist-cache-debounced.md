# Story E4.S2: Persist the cache lazily and save it debounced

Status: **review**

_Epic E4 (D) — Shared persistent cache · increment 3 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **This is the story that gives the app a fourth file in `%AppData%`, and the third one this suite could poison.**
> `settings.json` was rewritten by the test run once (`SettingsService.PathOverride`); a real error report was
> seeded with fixture failures once (`Logging.DirectoryOverride`); `provider-state.json` was re-pointed at the
> developer's own file by `ResetForTests` once (E2.S2's review). **Land the redirect pair before the feature**:
> `TestCacheRedirect` (`[ModuleInitializer]`) plus a `TempCache` disposable, exactly as
> `TestGateStateRedirect.cs` + `TempGateState.cs` do — IS-2 and IS-3 are acceptance criteria, not suggestions.
>
> The second hazard is the opposite of a bug: **doing this eagerly**. I10 says nothing new happens before first
> paint, and a cache file is precisely the kind of thing that gets loaded "just at startup, it's only 300 KB".

## Story

As a player who restarts the app,
I want yesterday's translations still there,
So that a fresh session does not re-earn the same rate limit translating the same lines.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E4.S2. Do not weaken._

1. **Given** §8.2
   **When** the first cache **miss** of the process occurs
   **Then** `%AppData%\PWRUHelper\translation-cache.json` is loaded — off the UI thread, never at startup (I10).
2. **Given** a store operation
   **When** it completes
   **Then** a save is scheduled `CacheSaveDebounceMs` (5 s) later and coalesced with any other pending save; plus
   one save on the existing `OnClosing` path.
3. **Given** the file format
   **Then** it is `{"version":1,"entries":[{"k":…,"v":…,"p":…,"t":…}]}`, written **MRU-first** so the LRU order
   survives a restart, using the atomic pattern of `SettingsService.Save` (`SettingsService.cs:186-197`),
   best-effort, never throwing.
4. **Given** a corrupt or future-version file
   **When** it is loaded
   **Then** the cache is empty and no error surfaces.
5. **Given** I4
   **When** the file is inspected after a session that produced failures
   **Then** **no value in it starts with `(`**.
6. **Given** concern #2 of §8.2
   **When** the file is loaded and `OfflineFallbackEnabled` is now false
   **Then** entries whose `"p"` is `bergamot` are dropped.

## Scope note: `OfflineFallbackEnabled` does not exist yet, and `"p"` has nothing to write

AC 6 names a setting that **arrives in E6.S3 / E8.S3** (`R-7`: architecture §12's names win) and a provider that
arrives in **E8.S2**. Today's `AppSettings` (`Services/SettingsService.cs:15-80`) has no such field, and no tier
can ever produce `"p":"bergamot"` in A.2.

**What this story ships:**

- The `"p"` field is written for every entry from day one, because the schema wants it and because retrofitting a
  field into a file people already have is how a version bump gets earned for nothing.
- The drop rule ships **as a parameter**, not as a `#if`: `TranslationCacheStore(…, bool offlineEnabled = false)`.
  With the default, every `bergamot` entry is dropped on load — which is correct in A.2 (the setting is
  structurally false) and is exactly the behaviour E8 turns on by passing `settings.OfflineFallbackEnabled`.
- **TP-CACHE-05 is therefore writable today**: hand-write a file containing a `"p":"bergamot"` entry and assert it
  is not loaded. It is not a test of a future feature; it is a test of the drop rule, and the entry is a fixture.

**Where the `"p"` value comes from.** The store is handed a key and a value; it does not know which provider
answered. Two honest options, and the story takes the first:

1. `Store(key, value, providerId)` with `providerId` defaulted to `null` → written as `""`. `CachingTranslator`
   passes `null` in A.2 because a decorator does not know either — the chain does. **E7.S3 already has to read
   `ChainTranslator.LastOutcome.ProviderId` for the chip**, and that is the story that can pass it down. Record it
   as an open thread in the PR; do not invent a plumbing path here.
2. Reach into the chain from the decorator. **No** — that couples `CachingTranslator` to `ChainTranslator` and
   breaks the "it wraps ANY inner translator" property its class comment (`:9-10`) is built on.

So: the field exists, is round-tripped, is what the drop rule reads, and is `""` for entries A.2 writes. Say so in
the PR rather than leaving a reader to discover an always-empty field.

## Dev Notes

### Invariants this story must keep

- **I4 — only successes are cached, in memory AND on disk.** AC 5 is the on-disk half and it is the one a user
  could see: a cached `(rate-limited …)` would survive a restart and outlive the condition it describes, which is
  the exact shape of the complaint that started this whole investigation.
- **I10 — nothing before first paint.** The store is constructed in the ctor (E4.S4) and must read nothing there.
  TP-CACHE-10 and TP-CACHE-11 are the two halves; TP-START-01/02 must stay green.
- **I2** — `Services/` stays UI-free. `SaveNow()` is called *from* `OnClosing`; the store knows nothing about a
  window.

### Rulings that apply

- **E2-e (corrected)** — the lazy load runs **synchronously on the calling thread** inside the first trigger, not
  on a pool thread. Same trigger shape as the gate state, same reasoning, same few-KB-once size.
- **R-7** — the setting is `OfflineFallbackEnabled`, and it arrives in E6.S3. This story takes a bool, not a
  setting.
- **From E4.S1's code review (2026-09-07), four things this story inherits:**
  1. **The `(`-prefix guard on load and on save** (T5 above) — the architect's ruling, not a suggestion.
  2. **The entry widens here, not there.** E4.S1 deliberately left the in-memory entry a
     `KeyValuePair<string, string>` with no `p` and no timestamp: a field no code writes looks wired and is not.
     Widening it to a record carrying `p`/`t` is additive and nothing in E4.S1 makes it awkward.
  3. **`TryGet` promotes, so every READ mutates the order that IS the file format.** A calm LIVE session of pure
     hits reorders persisted state while storing nothing. AC 2 schedules a save on a **store** operation only —
     so the on-disk order lags the reads, deliberately. Say so in the code; do **not** "fix" it by saving on
     reads, which is a save every tick.
  4. **The capacity bounds entry COUNT, not bytes.** One Translator-tab paste is one multi-KB entry, and it goes
     to the file too. §8.2's "~150 B an entry ⇒ ≈300 KB" is the FILE's estimate at chat-line sizes; U8 (E4.S3)
     must measure with realistic entries. A per-entry size cap is the cheap answer if the file grows.
  5. **The store cannot yet be persisted:** `Count` is its only accessor. This story adds the MRU-ordered
     snapshot and the bulk load — E4.S1 left them out on purpose (nothing consumed them).
- **§8.2's trade-off, accepted, do not re-open:** the key is **provider-agnostic**. A value produced by a lower
  tier may later be served while a higher tier is healthy. `"p"` exists for the log and for the drop rule only —
  it is **not** part of the key, and adding it to the key would multiply the cache by the tier count and defeat
  its purpose.

### Repo traps

- **The three files this suite has already poisoned.** `settings.json`, the log directory, `provider-state.json`.
  T1 exists so `translation-cache.json` does not become the fourth. Do it first; the guard case is cheap and the
  reviewer will look for it.
- **`ProviderGates.ResetForTests()` deliberately nulls its override** and `GatesTestBase` re-applies the run-wide
  redirect (`TestGateStateRedirect.cs:14-21`). If this story adds a `ResetForTests` to the cache store, it owes
  the same re-application, or a case that forgets `TempCache` reaches the real file.
- **A debounced timer that outlives its test.** IS-4's second half: a reset must clear **the registry and any
  pending save**, or a queued write lands during the next case. `ProviderGates.CancelPendingSave` (`:415`) is the
  precedent.
- **Culture.** `ToString("O")` / `DateTimeOffset.TryParse` with `CultureInfo.InvariantCulture` and
  `DateTimeStyles.RoundtripKind`. E2.S6's review made this a rule after a `fr-FR` box formatted a timestamp with
  commas.
- **`File.Replace` throws when the target does not exist** — hence the `if (File.Exists)` fork at
  `SettingsService.cs:193-194`. Copy both branches.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Size, dependencies, risk

**Size:** M · **Depends on:** E4.S1 ·
**Risk:** **low-medium.** Three hazards, in order: (1) a partially written file — mitigated by the atomic pattern
and by treating any parse failure as an empty cache; (2) an **eager** load that quietly re-opens P1 — mitigated by
TP-CACHE-10 and by TP-START-01/02 staying green; (3) the suite writing the developer's real cache — mitigated by
T1, which is why T1 is first. ·
**DoD:** T17 passes; the real `%AppData%\PWRUHelper\translation-cache.json` is provably untouched by a test run.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. Delete `%AppData%\PWRUHelper\translation-cache.json`. Launch the app and **do nothing**: the file is still
   absent, and Process Monitor shows no read of it. That is I10 by hand.
3. Translate three sentences on the Translator tab, wait 6 s: the file appears, `version` is 1, the three entries
   are present, `t` is a UTC ISO timestamp, and the **most recent sentence is first**.
4. Pull the network cable, translate something so it fails, then close the app: no value in the file starts with
   `(`.
5. Truncate the file mid-entry, restart, translate the same three sentences: they translate normally (cache empty,
   no error surfaced) and the file is rewritten whole.
6. Hand-add an entry with `"p":"bergamot"`, restart, translate that exact text: it is **re-translated**, i.e. the
   entry was dropped on load.
