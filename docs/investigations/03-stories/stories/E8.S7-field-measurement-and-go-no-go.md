## Dev Notes

### The RAM ceiling is written twice, at two different numbers — flag **E8-a**, settled here

| Source | Number |
|---|---|
| `plan-migration.md` increment 7 "Go criteria" | RAM delta **≤ 150 MiB** while active |
| test-plan **TP-BRG-02** | **≤ 150 MiB**, released on unload |
| README amendment **A-1(c)** (owner, 2026-09-06) | **+127–310 MiB** while active, **accepted** |
| `architecture-cible.md` §7.6 (A-1(c) restated) | the RAM budget line is **relaxed** to that range |

They are not the same gate and the difference is a **configuration**, not a disagreement:

- **One model** (`tiny` ru→en) measured **+127 MiB USS** on the dev box — under 150 MiB, and it is the only
  configuration the prototype ships.
- **A RU↔FR pivot** needs **two** models resident and measures **250–310 MiB** — over 150 MiB, and it is what
  A-1(c)'s upper bound was accepting in advance.

**Proposed settlement, for the owner with the field number in hand:** **150 MiB is the go criterion** for the
shipping configuration and it is what T3 measures against. **310 MiB is A-1(c)'s hard ceiling**, which only a
second language pair could approach, and a second pair is **out of scope for the prototype** — §4.2's
`[ Add a language pair ]` button is not implemented (E8.S3 says so). If the field number lands between 150 and
310 for **one** model, that is a genuine conflict between a criterion and an acceptance, and it goes to the
owner as a question rather than being resolved by whichever document was read last.

### Repo traps

- **"Measured once, on the fast machine, declared fine"** is this project's named recurring failure mode
  (`verify-against-prior-releases`). E8.S1 is explicitly the *dev-box half*; this story is the other half, and
  skipping it is how the epic's whole measurement discipline becomes theatre.
- **Sample RAM after the first translate.** Repeated because it is the one that will be got wrong.
- **`Measure-Startup.ps1` run #0 is the number that matters** — a fresh hash, a file Windows has never seen. A
  warm run on a machine that has already launched the build measures nothing about P1.
- **One visit, two datasets** (test-plan §4.3). The E9.S12 P1 campaign and this one share a machine and a trip;
  scheduling them separately doubles a cost the owner pays in evenings.
- **Do not fold a fix into the campaign.** If TP-BRG-06 shows the RSS not returning, that is a **finding** that
  goes back to E8.S4 — not a patch applied on the owner's machine mid-measurement.

## How to verify manually

_This story **is** the manual verification. The checklist the owner works through:_

1. Two P1-affected machines, instrumented (E9.S12), machine sheet written for each.
2. `set PWRU_SPIKE=1 && dotnet test … --filter Category=Spike` on each: init, ms/line, lines/s.
3. Install through About, start LIVE, force every online tier paused, let the offline engine answer. Read the
   resident delta **after the first translate** — against **150 MiB**.
4. Leave LIVE running past the idle timeout: still loaded (TP-BRG-05). Stop LIVE, wait it out: RSS back to
   baseline (TP-BRG-06).
5. Read the three-column table of ≥ 30 of **your own** chat lines. Decide, out loud, whether the middle column
   is good enough when the alternative is no translation at all.
6. E8.S6's three layouts: exe size, `%TEMP%` contents, `Measure-Startup.ps1` run #0 and warm.
7. Delete the model mid-session (TP-BRG-09) and press `Remove` then restart (TP-BRG-10).
8. Write the verdict in one sentence at the top of `bergamot-go-no-go.md`, with the four numbers under it.
9. **If it is a no-go, close the branch and say so in the same file.** That is a success and the document says
   so.
