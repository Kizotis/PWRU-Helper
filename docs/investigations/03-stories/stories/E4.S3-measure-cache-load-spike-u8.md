# Story E4.S3: Measure the cache lazy-load cost 🔬 spike (U8)

Status: **done (2026-09-07) · 🔬 spike (U8) · exit criterion met · no network, no owner-designated connection**

_Epic E4 (D) — Shared persistent cache · increment 3 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **Not a feature. A number, and a decision that follows from it.** §8.2 says in one sentence what this spike is
> for: *"if it is not a few milliseconds off the UI thread, the capacity is the knob."* The knob is
> `TranslationPolicy.CacheCapacity`, and this story either leaves it at 2000 or halves it — nothing else.
>
> **This spike sends no request and needs no owner-designated connection** — unlike E3.S1/S2/S9 it is pure local
> I/O, so it does not carry their `blocked-owner` status. Its **second** measurement (a personal Defender-only
> machine) is the owner's, and it does not gate the go/no-go: the dev-box number decides the capacity, the
> personal-machine number confirms it against the P1 problem the app is already fighting.

## Story

As the owner,
I want to know what a 2000-entry cache costs to load,
So that a convenience feature cannot quietly become a startup regression on the problem we are already fighting.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E4.S3. Do not weaken._

1. **Given** U8 and G6 ("cost nothing at startup and nothing in RAM")
   **When** a synthetic `translation-cache.json` of 2000 realistic entries (~300 KB, §8.2) is placed and the lazy
   load is timed with a `Stopwatch` on the load path
   **Then** the elapsed time and the resident-memory delta are recorded in the PR and in this folder, measured on
   a personal Defender-only machine as well as the dev box.
2. **Given** I10
   **When** the measurement runs
   **Then** it confirms that no load happens before the window is visible.

**Exit criterion (measurable).** Milliseconds to load 2000 entries off the UI thread, and the working-set delta.

**Go / no-go.** **Go:** ≤ 50 ms off the UI thread and a working-set delta small against the ~150 MB budget ⇒
capacity 2000 stands. **No-go:** anything materially larger ⇒ **the capacity is the knob** (§8.2) — halve it and
re-measure; do not move the load onto the UI thread and do not load eagerly.

## Tasks / Subtasks

- [x] **T1 — The synthetic file (AC 1).** A small generator — a test-only helper or a script under
      `tools/diagnostics/` — writing 2000 entries in E4.S2's exact format.
  - [x] **Realistic, not `"aaa"`**: Russian chat lines of 20–90 characters with their English translations, mixed
        `ru|en` and `auto|en` keys, `"p"` populated, `"t"` spread over a week. A file of 2000 identical short
        entries measures `JsonDocument` on a best case that no user will ever have — and UTF-8 Cyrillic is two
        bytes a character, which is half of why ~150 B/entry is the estimate.
  - [x] Assert the produced file is **~300 KB** (§8.2's own figure). If it lands at 150 KB the entries are not
        realistic; if at 600 KB, say so — the estimate, not the measurement, is then what was wrong.
        **It landed at 981 KB, and the estimate is what was wrong** (§4 of the spike doc): the ~150 B counted
        Cyrillic at its two UTF-8 bytes and the serialiser escapes it to six. So no assert on 300 KB was
        written — it would have pinned a number the measurement disproved.
- [x] **T2 — The measurement (AC 1).** A `Stopwatch` around the load inside `EnsureLoaded`, reported through
      `Logging.Info` **behind a flag or in a branch build**, or — preferred — a `[Fact(Skip=…)]`-style opt-in case
      that runs on demand. Do **not** ship a timing log line on the hot path: the log is capped at 1 MB with one
      rollover (`Logging.cs:69,95-105`) and E1.S5 already fought for what earns a line in it.
  - [x] Record: **elapsed ms** (median of ≥ 5 runs, plus min and max — a single number from a machine with a warm
        file cache is the measurement that misleads), and the **working-set delta** around the load
        (`Process.GetCurrentProcess().WorkingSet64` before/after, plus `GC.GetTotalMemory(true)` for the managed
        half, which is the one the capacity actually controls).
  - [ ] Both runs: **cold** (first read after a reboot or after clearing the standby list) and **warm**. The cold
        number is the one that matters, because it is the one that shares a cause with P1.
        **Warm is done; cold is deliberately left open and carried into T6.** A reboot is not agent work and
        clearing the standby list needs elevation on a corporate box — and AC 1 already assigns the cold number
        to the personal Defender-only machine, where it means something. It does not gate the capacity decision
        (§6 of the spike doc says so in one sentence).
- [x] **T3 — Confirm I10 by observation, not by assertion (AC 2).** With the 2000-entry file in place, launch the
      app and **do not translate**: the window paints and the file has **not** been read. Evidence: Process
      Monitor filtered on `translation-cache.json`, or `Measure-Startup.ps1`'s pre-process/in-process split
      (`tools/diagnostics/`, the protocol in `mesures-protocole.md`) showing no change against a no-file run.
  - [x] This is the same claim TP-CACHE-10 makes in CI. The spike's value is that it makes it on a real launch,
        where a static initialiser or a helpfully-added warm-up would show up.
        **Done one step short of a real launch, and the step is named:** the harness builds all three chains —
        what `MainWindow`'s constructor does — over a full 2000-entry file and finds `TranslationChains.Cache`
        at 0 entries (6.5 ms, 97 KB). That is the whole startup composition path, in process; the Process
        Monitor confirmation on a launched exe rides along with the owner's T6 run, which launches the app
        anyway.
- [x] **T4 — Write the result down where it will be found.** A short section appended to

### Invariants this story must keep

- **I10** — AC 2 is this invariant, measured rather than asserted. If the spike finds a read before first paint,
  that is not a slow load — it is a **bug in E4.S2**, and it goes back to E4.S2.
- **G6** — "cost nothing at startup and nothing in RAM". The RAM half is why the working-set delta is in the exit
  criterion and not just the milliseconds. `pwru-startup-perf` (the project's own memory budget) is the ~150 MB
  the delta is judged against, and it is the budget that made single-file compression a removed feature.

### Repo traps

- **Do not add ReadyToRun and do not re-add single-file compression** to "help" a measurement. Both are recorded
  deliberate non-features (`project-context.md`, `pwru-startup-perf`); compression cost ~118 MB of RAM and was
  removed on purpose.
- **`PublishFlagsTests.cs:44-70`** guards the no-compression choice and flag parity across the three build paths.
  A spike that touches a build flag to get a cleaner number breaks it, and rightly.
- **A measurement on the dev box alone answers half the question.** The recurring failure mode this project has a
  memory note about (`verify-against-prior-releases`) is exactly "measured once, on the fast machine, declared
  fine". The dev-box number decides the capacity; the personal-machine number is what makes the claim survivable.
- **`Stopwatch` in a test is a measurement, not an assertion** (CI-3's single carve-out, TP-START-03). If any of
  this lands as a test, it must **report** and never **fail** on a duration.

### Line-number drift

None — this story reads `architecture-cible.md` §8.2/§15.1 and E4.S2's code; it introduces no new `file:line`
claim of its own.

## How to verify manually

1. Generate the file, confirm ~300 KB and 2000 entries.
2. Launch, do nothing, close: Process Monitor shows **zero** reads of `translation-cache.json` (AC 2).
3. Launch, translate one new sentence: exactly **one** read, and the `Stopwatch` reports the number.
4. Repeat cold (after a reboot) and warm; record median/min/max of ≥ 5 runs each.
5. Read the working-set delta against the ~150 MB budget and state the go/no-go in one sentence.

### Completion Notes List

**The numbers** (dev box `GSIN-WS-DT004`, i7-9700 / 16 GB / NVMe, Defender on, warm file cache, median of 7
after a discarded warm-up):

| entries | file | B/entry | ctor | load (med / min / max) | save | managed Δ | working set Δ |
|---|---|---|---|---|---|---|---|
| 500 | 231 KB | 474 | 0.001 ms | 3.6 / 3.5 / 3.8 ms | 11.9 ms | +229 KB | +644 KB |
| **2000** | **981 KB** | **502** | **0.003 ms** | **17.8 / 14.6 / 21.0 ms** | **15.3 ms** | **+960 KB** | +892 KB |
| 5000 | 2 612 KB | 535 | 0.006 ms | 32.0 / 25.4 / 34.0 ms | 28.9 ms | +2 514 KB | ~0 (noise) |

**Exit criterion: met, comfortably.** ≤ 50 ms off the UI thread and a working-set delta small against the
~150 MB budget ⇒ **17.8 ms** on the first miss's own thread for **≈1 MB**, 0.6% of the budget. **Capacity 2000
stands**; its grade in `TranslationPolicy.cs` is now `[MEASURED]` with the date and the numbers. E4.S4's
question is answered in the same table: the pre-sized 2000-slot map costs **3 µs**, and building all three
chains over a full file is 6.5 ms / 97 KB with **zero** entries read.

**The finding that was not on the list, and it was a live bug.** A realistic file is **502 B an entry**, not
§8.2's ~150 — `JsonSerializer`'s default encoder escapes Cyrillic to `\uXXXX`, six bytes a character instead of
two. So a FULL cache at capacity 2000 weighs **981 KB against a 1 MB `MaxBytes`**: 4% of headroom, crossing at
≈2088 entries. The heaviest users would have earned a full cache and had it refused **unread** on every launch —
silently, no error, no log line. This is exactly E4.S2's deferred review finding ("a byte bound over a
COUNT-bounded capacity"), and it was real. **`MaxBytes` 1 MB → 4 MB** (4× a measured full cache, ≈70 ms of
parsing at the measured ≈55 MB/s, still an unmistakable refusal for the corrupt 400 MB file the bound exists
for). The capacity was NOT the knob that needed turning; the guard was the thing mis-sized.

**Deliberately not done:** giving `Options` a non-escaping encoder would divide the Cyrillic by three, and it
changes the bytes of a file users already have — outside this spike's "may not" table (the file format). It is a
follow-up worth its own story; the 4 MB bound is sized so that story is an optimisation and not a rescue.

**5000 is on the record as a no.** 32 ms warm is already two thirds of the criterion before any cold multiplier,
for 2.5 MB. A future capacity increase is re-measured first.

**How the harness stays invisible.** `CacheLoadSpike.cs` compiles on every build — it cannot rot behind a flag —
but its `[Fact]` attributes only exist under the `PWRU_SPIKE` define, which the test csproj takes from the
environment variable of the same name. A normal `dotnet test` therefore discovers **zero** cases there: verified
**771 passed / 0 skipped / total 771 / 2 s**, unchanged from the baseline. A `[Fact(Skip=…)]` could not have done
this — `Skip` is a compile-time constant no environment variable can lift, and the cases would still be counted.

**Isolation.** Every case runs inside a `TempCache` (IS-3) with the debounce stretched so no timer writes under a
measurement, and each one snapshots and re-asserts the real `%AppData%\PWRUHelper\translation-cache.json`
(existence, length, last-write) — this is the class that writes megabytes, and it writes them to `%TEMP%`.

**Left open, on purpose:** the **cold** number, on the owner's Defender-only personal machine (T2's second
sub-bullet and T6). It does not gate A.2 — the story says so in its own header — and the one-line command is in
§7 of the spike doc.
