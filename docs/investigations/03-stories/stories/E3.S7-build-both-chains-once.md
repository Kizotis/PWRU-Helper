# Story E3.S7: Build both chains once, in the constructor, per the target composition

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E3 (C) — Provider chain and the new default endpoint · increment 2 · **Release A.1: E2 and E3 are separate
PRs but ONE release** · the owner's Phase-4 go was given 2026-09-06 (`README.md` § Phase 4)._

> **This is the story that makes the epic visible to a player.** Everything before it adds parts; this one wires
> them, and it is the only E3 story that touches `MainWindow`'s constructor — the part of this codebase with the
> worst bug history (`wpf-xaml-load-clobbers-settings`, v0.12.3; the `_readTranslator`-before-`_settings`
> declaration-order trap this story exists to fix).
>
> **It is also where `Background` finally reaches the read chain.** E2.S3 built the `Interactive` reserve and
> E2.S5 left it inert on purpose (*"`Background` did not reach the read chain: doing so would have meant a
> call-site change in `MainWindow.*`, and TP-START-02 allows exactly one `ProviderGates` reference outside
> `Services/`"*). This story is where that is resolved — **without** adding a second reference.

## Story

As a player,
I want the free tiers behind my key and my key never behind the screen reader,
So that a metered allowance cannot be drained by a loop I did not ask to spend it.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E3.S7. Do not weaken._

1. **Given** §8.1
   **When** the `MainWindow` constructor runs, before `InitializeComponent()`
   **Then** the read chain is
   `[Azure if AzureApiKey set AND UseKeyForReading] → GoogleDict → Edge → GoogleGtx → [Bergamot if enabled and
   present]` and the write chain is
   `[DeepL if key set] → [Azure if key set] → GoogleDict → Edge → GoogleGtx → [Bergamot if enabled and present]`.
2. **Given** `_readTranslator` is a field initializer at `MainWindow.xaml.cs:43` while `_settings` is initialised
   at `:50`
   **When** the chains move into the constructor body
   **Then** `_readTranslator` stays `readonly` and is simply assigned there, so it can see `_settings`.
3. **Given** I8
   **When** any configuration is applied
   **Then** **no setting can put DeepL in the read chain** — its absence is structural, asserted by a test on the
   built chain, not by a runtime check.
4. **Given** `BuildTranslator()` at `MainWindow.Translate.cs:226-233`
   **When** it becomes `BuildWriteChain()`
   **Then** it is still called from the key-save handler at `:239`.

## Scope note: three of the five optional tiers do not exist yet

AC 1 names Azure and Bergamot. **Neither exists in A.1**: `AzureTranslator` is E6.S2, `AzureApiKey` /
`UseKeyForReading` are E6.S3, `BergamotTranslator` is E8.S2 and `OfflineFallbackEnabled` is E8.S3. Today's
`AppSettings` (`Services/SettingsService.cs:15-80`) has `DeepLApiKey` and nothing else of the five.

**What this story ships, therefore:**

| Chain | A.1 shape (this story) | A.1 shape if E3.S5 was cancelled |
|---|---|---|
| **Read** | `GoogleDict → Edge → GoogleGtx` | `GoogleDict → GoogleGtx` |
| **Write** | `[DeepL if key set] → GoogleDict → Edge → GoogleGtx` | `[DeepL if key set] → GoogleDict → GoogleGtx` |

**What it must leave behind:** a builder shaped so that E6 and E8 each add **one conditional tier in one place**,
and an I8 test that already passes over "every settings permutation" as the settings arrive. Write the two
builders so the optional slots are visible as named, commented gaps — not so that E6 has to redesign the method.

## Dev Notes

### Invariants this story must keep

- **I1** — `ITranslator` unchanged. The per-instance priority (T2) exists *because* of it.
- **I2** — `TranslationChains` is in `Services/`: it reads `AppSettings` and constructs providers; it must not
  touch a WPF type, a dispatcher or a `MessageBox`.
- **I8 — DeepL is unreachable from the read path by construction.** The single most important line of this story,
  and the only one with a money consequence for the user.
- **I9** — one gate per provider, shared by both chains. Achieved by `ProviderGates.For(id)` returning the same
  instance, not by sharing provider objects.
- **I10** — nothing reads `provider-state.json` before first paint. `For` constructs; `TryEnter` loads; the first
  `TryEnter` happens inside `HttpProviderCore` on the first real request.
- **I16** — LIVE's behaviour is unchanged by this story. It gets a chain instead of a single provider and a
  `Background` priority; the loop itself is **E5**.

### Rulings that apply

- **R-3:** `ChainTranslator.LastOutcome` exists (E3.S3) and the **code-behind owns the chain instance**, which is
  what lets E7 read it. This story is what puts that instance in a field the code-behind can reach — but it wires
  **no UI**. Do not add a status chip here; that is E7.S3.
- **OQ-a:** read-once is `Interactive`. It is a user click. **It is wired at its call site in E5.S4**, not here —
  and note the tension this creates: read-once and LIVE share `_readTranslator`, whose providers this story
  builds with `Background`. E5.S4 is where that is resolved (most likely a second, `Interactive` read chain, or a
  priority the call can carry). **Record it; do not solve it here** — solving it needs E5's context.
- **E5-a:** LIVE honours short `Wait`s inside a tick; a `Background` caller needs its own fall-through when the
  delay exceeds the tick budget. That fall-through is **E5.S1's**, on the loop, not on the chain.
- **R-7 (setting names):** `AzureApiKey`, `AzureRegion`, `UseKeyForReading`, `OfflineFallbackEnabled`,
  `LastRunVersion` — architecture §12's names win. Use exactly these in the future-slot comments so E6 does not
  have to rename them.
- **Owner's decision:** `UseKeyForReading` defaults to **false** — a metered key must be opted into for an
  unmetered loop.

### Repo traps

- **Constructor ordering has produced bugs in this codebase, and this story is entirely about it.** Field
  initializers run in declaration order, before the ctor body: `_writeTranslator` (`:42`, uninitialised),
  `_readTranslator` (`:43`), `_updates` (`:49`), `_settings` (`:50`). Moving `_readTranslator` down the file
  instead of into the ctor would "work" and would be the wrong fix — AC 2 asks for the ctor, and the ctor is
  where a future reader will look.
- **`InitializeComponent()` fires change handlers** (`MainWindow.xaml.cs:30-35`'s comment: a `<Slider Value="70"
  ValueChanged=…/>` raises `ValueChanged` during `InitializeComponent`, long before `ApplySettings`). Both chain
  assignments must be **above** `:83`, and neither may depend on a control.
- **TP-START-02's `strays` assertion is an exact-equality assert on a one-element array.** Any new
  `ProviderGates` mention in `MainWindow.*` fails it with a message about startup paths. That is the guard doing
  its job; route through `TranslationChains`.
- **`HttpSeamGuardTests`' IS-10 guard** will hold every provider this story constructs. Constructing a provider
  with no handler is *production*, which is correct — the guard's rule is that a **test** may not do it.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green, TP-START-02 included.
2. Launch the app with **no** DeepL key: the Translator tab translates through `google-dict` (check the log's
   `provider=` on a forced failure, or the About tab's report).
3. Paste a DeepL key, save, translate: `provider=deepl`. Then use **read-once** on a screen region: the log must
   **never** show `provider=deepl`. That is I8, by hand.
4. Hand-edit `%AppData%\PWRUHelper\provider-state.json` to block `google-dict` into the future, restart,
   read-once: the translation still appears, and the log says `provider=edge` (or `google-gtx`), with **no**
   `tr` line for `google-dict`.
5. Block **every** free provider the same way and read-once: exactly **one** message, the `AllProvidersPaused`
   sentence, and **zero** `tr` lines.
6. Read the ctor: both chain assignments are above `InitializeComponent()`, and `_readTranslator` is still
   `readonly`.
