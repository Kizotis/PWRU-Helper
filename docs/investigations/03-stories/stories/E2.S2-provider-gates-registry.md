# Story E2.S2: `ProviderGates` registry, process-global and reset-able

Status: **review**

_Epic E2 (B) — Provider gate · increment 1 · **Release A.1: E2 and E3 are separate PRs but ONE release** · ⛔ no
production code until the owner's explicit go._

## Story

As the maintainer,
I want one gate per provider id shared by both chains,
So that the Translator tab cannot keep hammering a provider that LIVE has already been told to leave alone.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E2.S2. Do not weaken._

1. **Given** the read chain is a field initializer (`MainWindow.xaml.cs:43`) and the write chain is rebuilt on every
   key save (`MainWindow.Translate.cs:239`) — two independent instances today
   **When** `ProviderGates.For(id)` is introduced
   **Then** both chains obtain the **same** `ProviderGate` instance for the same id, and `ProviderIds` declares
   `google-dict`, `edge`, `google-gtx`, `deepl`, `azure`, `bergamot`.
2. **Given** the discipline already used twice in this repo (`SettingsService.cs:95`, `Logging.cs:31-39`)
   **When** the registry lands
   **Then** it exposes `internal static string? PathOverride`, `internal static Func<DateTimeOffset> Clock`,
   `internal static void ResetForTests()` and `internal static void ClearAuthBlock(string id)`.
3. **Given** R4 (static state leaks between parallel xUnit collections)
   **When** the gate tests are written
   **Then** they live in **one non-parallel xUnit collection** whose fixture calls `ResetForTests()`, and no gate
   test touches the real `%AppData%`.

        map `id → ProviderGate`, returning the **same instance** for the same id for the life of the process.
  - [x] Thread-safe: both chains, the LIVE loop and the Translator tab call `For` concurrently. A
        `ConcurrentDictionary` with `GetOrAdd`, or a `lock`ed dictionary — house style, no cleverness.
  - [x] `internal static class ProviderIds` **in the same file** (glossary §16) declaring the six ids as `const`
        strings: `google-dict`, `edge`, `google-gtx`, `deepl`, `azure`, `bergamot`. Nothing else may spell an id as
        a literal — that is how a typo becomes two gates.
  - [x] **Why static, restated so no story re-opens it** (§5.1): the state mirrors an *external,
        process-independent* condition (an IP-scoped counter on Google's side); the alternative would have to be
        threaded through a field initializer that runs **before** `_settings` is even loaded
        (`MainWindow.xaml.cs:43` vs `:50`) and through `BuildTranslator()`, which runs again on every key save.
- [x] **T2 — The three test seams and the auth clear** (AC: 2) — the discipline this repo already uses twice
  - [x] `internal static string? PathOverride` — mirrors `SettingsService.cs:95` and `Logging.cs:31-39`. The
        registry owns load/save of `provider-state.json`; the actual store is **E2.S4**. In this story the property
        exists and is honoured by whatever load/save stub lands, so no test can be written that touches the real
        `%AppData%` later.
  - [x] `internal static Func<DateTimeOffset> Clock` — **IS-6: the registry and every gate it hands out must share
        one clock**, or a persisted `blockedUntil` is compared against a different "now". `For` injects this clock
        into each `ProviderGate` it creates; changing `Clock` after gates exist must be honoured (hold the
        `Func<>` by reference, do not copy the value at construction).
  - [x] `internal static void ResetForTests()` — **IS-4: clears the registry AND any pending debounced save.** The

  - [x] `internal static void ClearAuthBlock(string id)` — closes an `AuthFailed` gate
        (`blockedUntil = DateTimeOffset.MaxValue`). Called from the key-save handlers (DeepL today,
        `MainWindow.Translate.cs:235-244`; Azure in **E6.S3**, §12). Wiring the call sites is **not** this story —

## Dev Notes

### Invariants this story must keep

- **I9 — gate state is process-global and persisted.** This story is the "process-global" half; **E2.S4** is the
  "persisted" half. Today the two chains are separate instances (`MainWindow.xaml.cs:43` vs
  `MainWindow.Translate.cs:229-232`, rebuilt at `:239`), which is exactly why the Translator tab can keep hammering
  a provider LIVE has been told to leave alone.
- **I10 — nothing new before the window is visible.** No I/O in the static initialiser, no reference from any
  startup path.
- **I2** — UI-free, headless-testable. **I3** — nothing here catches an OCE. **I11** — the registry logs nothing in
  this story (transition logging is **E2.S6**).
- **I16** — the LIVE loop is untouched.

### Rulings and decisions that apply

- **R-2 / OQ-c (binding): no event on the registry either.** `readiness-report.md` R-2 proposes
  `ProviderGates.StateChanged` and says to add it to E2.S1/E2.S2's scope. The architect's ruling overrides it:
  **poll `ProviderGate.Snapshot()` at 1 Hz from the countdown timer; no events out of `Services/`.** Do not add
  `StateChanged`, `INotifyPropertyChanged`, or a callback list. (Sprint-plan note 1.)
- **`ProviderIds` is the vocabulary of the whole rebuild.** `google-gtx` is the id for today's endpoint **before**
  the rename in E3.S6 — E1.S5's log line already uses it, so the field stays stable across the rename.
- `bergamot` is declared here even though **E8** may never merge. An id costs nothing; a second spelling of it
  would cost a silently duplicated gate.

### Repo traps

- **The static-facade pattern exists twice in this repo and both times for the same reason**:
  `SettingsService.PathOverride` (`SettingsService.cs:95`) after the suite rewrote a developer's own
  `settings.json`, and `Logging.DirectoryOverride` (`Logging.cs:31-39`) after the suite seeded a real error report
  with fixture failures ("deepl down"). Copy the shape, including the guard test.
- `tests/PWRUHelper.Tests/TestLogRedirect.cs:24-26` shows the other half of that lesson: a `[ModuleInitializer]`
  that catches everything, including the tests that never mention the facade. If a gate equivalent is ever needed,
  that is the pattern — but prefer the explicit `TempGateState` disposable, which is what IS-3 asks for.
- `InternalsVisibleTo PWRUHelper.Tests` (`PWRUHelper.csproj:28`) and the `tests\**` `DefaultItemExcludes` (`:18`)
  intact. **No `.sln`.** `dotnet test tests/PWRUHelper.Tests` green, headless, default parallelism unchanged.
- No settings control is touched in this story, so `_restoringSettings` (`MainWindow.xaml.cs:35`, cleared at
  `:201`) is not engaged. The first story of this rebuild that adds a persisted control is **E6.S3**, and it must
  follow that pattern with one clobber test **per control**.

**The two bundled rulings.**

- **E2-f — `Retry-After` is a floor, never a shortcut.** `ProviderGate.Honour`
  (`Services/ProviderGate.cs:425`) is now `max(computed, clamp(hint, 1 s, max(OpenCapMinutes, the row's own
  window)))`, and the `Escalate` arm (`:290`) lost its `if (retryAt is not null) _blockedUntil = window`
  exemption — every row goes through `BlockUntil`, so nothing can shorten a standing block any more. The three
  concrete failures it closes: a `Retry-After: 1` no longer buys a one-second pause while the strike ladder
  climbs; an HTTP date resolved against a client clock running five minutes fast is a no-op instead of
  collapsing to the floor; and the clamp ceiling is no longer `OpenCapMinutes` (30 min) for a `QuotaExhausted`
  row whose own window is 60 — a day-long hint clamps to **60 min**, where it used to *shorten* the quota block
  to 30. The floor half of the clamp is kept because the ruling states it, with a comment saying it can no
  longer be observed (the shortest computed window is `SoftCooldownSecs`, 5 s).
- **E2-g — 401 guarded on `keyWasSent`.** `Services/ProviderErrorMapper.cs:100-109` splits row 5 into 5 (a key
  was sent ⇒ `AuthFailed`) and 5b (keyless ⇒ `Blocked`), the same shape as rows 7/8. A keyless provider meeting
  a captive portal or a proxy 401 no longer reaches `blockedUntil = MaxValue` — a state with **no** reachable
  `ClearAuthBlock` caller, because a keyless provider has no key-save handler. `Blocked` is a state the
  breaker's own half-open probe can leave.

**Deviations and judgement calls — the reviewer's list.**

- **D1 — `ProviderGateTests` did not join the `Gates` collection.** T3 says to move it "**if** they now go
  through the registry"; they do not — every case still constructs a `ProviderGate` directly and the class holds
  no static state, so joining would serialise 58 fast cases for nothing. The file is still modified, for E2-f.
  If a reviewer prefers belt and braces, the change is one `[Collection("Gates")]` attribute.
- **D2 — T6's "`ClearAuthBlock` does nothing to a gate opened with `RateLimited`" is pinned at the registry
  level, not the gate level.** Per gate, E2.S1's **accepted deviation D7** is the opposite: `ClearAuthBlock()`
  clears the gate whatever opened it (re-saving a key is an explicit "try this provider now", and it is the only
  escape from a wrong `MaxValue`). Reversing that would undo a reviewed decision from outside this story's
  scope, so what is pinned here is the registry's own contract: clearing `deepl` closes deepl's auth block and
  leaves `azure`'s 429 window standing. **Flagged for the architect** — the E2.S1 review already recorded
  "`ClearAuthBlock()` clears more than its name says" as an open item.
- **D3 — `ResetForTests()` also clears `PathOverride` and `TransitionHook` and restores the wall clock.** IS-4
  names the registry and the pending save; a leaked fake clock is the same class of bug and costs one line to
  prevent. `TempGateState.Dispose` still nulls the path itself (`TempSettings`' shape), so the two are belt and
  braces rather than one relying on the other.
- **D4 — `Snapshot(id)` returns `null` for an id with no gate, and neither it nor `ClearAuthBlock` creates
  one.** A 1 Hz poll that created gates would populate the registry with six of them a second after the window
  opens, for providers the user never configured. "No gate" reads as "closed" at the call site (E7).
- **D5 — the transition seam is one internal delegate (`TransitionHook`), not an event and not a list.** Ruling
  R-2 keeps events out of `Services/`; E2.S4 (the debounced save) and E2.S6 (the transition line) each need one
  place to hang from, and `NoteTransition` swallows a throwing hook because observability may never fail a
  translation. Unwired today, exactly like `GateOutcome.Wait` and `RequestPriority` in E2.S1 — nothing calls it
  from production yet, and a gate does not know its own id (E2.S4 decides how the id reaches the hook).
- **D6 — `StatePath` is exposed (`PathOverride ?? DefaultPath`) so the `%AppData%` guard case has something
  concrete to assert**, and `DefaultPath` is a computed property rather than a static readonly field so the
  static initialiser stays free of even a shell-folder lookup (I10).
- **D7 — the `Gates` fixture is a base class (`GatesTestBase`), not an `ICollectionFixture`.** A collection
  fixture is constructed once per collection; IS-5 asks for a reset **before and after every case**, which in
  xUnit is the test class's constructor and `Dispose`. `DisableParallelization = true` is set on the collection
  as well.

**Two documents now trail the code, deliberately** (the rulings are recorded in `README.md`; the specs were not
rewritten): `architecture-cible.md` §5.5 still says a `Retry-After` "overrides the computed window", and §4.2
row 5 still maps 401 to `AuthFailed` unconditionally. E2-f and E2-g supersede both.

**Nothing user-visible changed.** No provider consults a gate until E2.S5, no XAML, template or `Run.Text`
binding was touched (I15/I16 not engaged), and the two ruling patches only change what happens *inside* a
breaker nothing calls yet — except E2-g, which changes a `Kind` the current chain never produced either (no
provider in the app today sends a 401 without a key).
