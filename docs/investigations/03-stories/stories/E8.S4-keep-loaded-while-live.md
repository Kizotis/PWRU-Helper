# Story E8.S4: Kept loaded while LIVE runs, unloaded after it stops ⛔ Phase 4 (prototype branch)

Status: **review · ⛔ Phase 4 · prototype branch only (`feature/p2-c-offline`) — merges only on E8.S1's go**

_Epic E8 (H) — Offline fallback prototype · increment 7 · **Release C** · prototype branch, merges only on a go._

> **This is the story amendment A-1(b) exists for, and it is a lifetime policy, not an engine.** §7.6 constraint
> 2 as originally written said "lazy load on first fallback use, unload after `IdleUnloadMinutes` (10,
> `[ASSUMED]`)". A-1(b) supersedes the unload half: once loaded, the model **stays** loaded for the whole LIVE
> session, and is released only after LIVE stops **and** an idle timeout elapses. The plain idle-unload still
> governs when LIVE is not running.
>
> **Why a separate story rather than a paragraph inside `BergamotTranslator`.** The policy is three inputs —
> is LIVE running, when was the last translation, what does the clock say — and one output. Written as a small
> pure type with an injected clock it is a dozen unit tests over literals (the shape `LiveTickPolicy`,
> `ResizeHitTest` and `EngineStatus.Of` already have in this repo). Written inside the provider it is a timer
> nobody can test without a 22 MB DLL and a stopwatch.
>
> **It is also the story that keeps the feature honest.** "0 MB at rest" is what makes a 127 MiB opt-in
> acceptable at all. If the model does not actually come back down, this story has nothing to implement and
> E8.S1's go-criterion 4 has already said so.

## Story

As a player who leaves LIVE running for an evening,
I want the offline engine to load once and then get out of my machine's way when I stop,
So that a feature that helps during an outage is not a permanent 127 MiB tax on the machine that is also
running the game.

## Acceptance Criteria

_AC 1 is copied **verbatim** from `epics.md` § Story E8.S2's third Given — the A-1(b) acceptance criterion,
which is this story's whole reason to exist. AC 2–5 are `[DERIVED]` from amendment A-1(b),
`architecture-cible.md` §7.6 constraint 2, and test-plan **TP-BRG-05 / TP-BRG-06**._

1. **Given** amendment A-1(b)
   **When** the model has been loaded and LIVE is running
   **Then** it **stays loaded** for the whole LIVE session; it is unloaded only after LIVE stops **and** an idle
   timeout elapses. The plain idle-unload of §7.6 constraint 2 applies when LIVE is not running.

2. `[DERIVED — §7.6 constraint 2, and it is a graded constant]` **Given** the idle timeout
   **When** it is written
   **Then** it is **one named constant in `Services/TranslationPolicy.cs`**, carrying **exactly one** evidence
   grade — `IdleUnloadMinutes = 10` `[ASSUMED]` is what §7.6 records, and `[ASSUMED]` is the honest grade until
   E8.S7 measures it. It is not a literal in `BergamotTranslator`, and it is not two literals.

3. `[DERIVED — TP-BRG-05]` **Given** LIVE is running and translating
   **When** ticks pass with gaps longer than the idle timeout between offline translations
   **Then** the model is **not** unloaded between ticks. A LIVE loop that pauses for a 30-minute gate window and
   then resumes must find the engine where it left it — reloading mid-session is the behaviour A-1(b) was
   written to forbid.

4. `[DERIVED — TP-BRG-06]` **Given** LIVE has stopped
   **When** the idle timeout elapses with no offline translation
   **Then** the engine is unloaded, `translator_free` is called exactly once, and the resident set returns to
   its pre-load baseline. **Measured, not assumed** — E8.S1's go-criterion 4 and E8.S7's TP-BRG-06.

5. `[DERIVED — I2, I10]` **Given** I2
   **When** the policy is written
   **Then** it lives in `Services/`, takes "is LIVE running" as a `Func<bool>` and its clock as an injected
   delegate, and holds **no** `DispatcherTimer`, no `Window`, no UI type. It never loads anything at startup
   (I10) — the policy can only *unload* something a translation already loaded.

- [x] **T2 — The LIVE signal, without a UI dependency (AC 1, AC 5).**

  - [x] Pass it as a **`Func<bool>`**, not as a reference to the window. The precedent is one line away:

  - [x] **Do not sample it once at construction.** A chain is built in the `MainWindow` constructor, before any

- [x] **T3 — When the check runs (AC 3, AC 4).** The policy needs a heartbeat, and the app already has three.
      **Do not add a fourth timer.** In order of preference:
  - [x] **(a) On each call into the provider** — cheapest and needs nothing new: before translating, ask
        `ShouldUnload()`; after translating, `RecordUse()`. This alone satisfies AC 3 fully (the model is never
        unloaded *between* ticks while LIVE runs) but never fires after the **last** call, so it cannot satisfy
        AC 4 on its own.
  - [x] **(b) The 1 Hz countdown timer E7.S2 landed** (`MainWindow.xaml.cs`, `CountdownTick`) is the natural
        home for AC 4 — but read E7.S2's and E7.S3's review notes first: the tick has **one** stop condition
        (`NeedsTick ∨ AllPaused`, widened in E7.S3), and a consumer that needs it to keep running for a reason
        the stop rule does not know about is exactly the bug E7.S2's review flagged. **Adding a third question
        to that stop rule is a decision, not a convenience** — if it is taken, it is written down in the same
        commit.
  - [x] **(c) `StopLive()` plus a one-shot** (`MainWindow.Live.cs:193-196`) — arm a single timer when LIVE
        stops, disarm it if LIVE restarts or a translation happens. Simplest correct answer to AC 4 and it adds
        no polling at all; the cost is one `DispatcherTimer` that is idle 99% of the time.
  - [x] **Recommendation: (a) + (c).** (a) is free and covers the LIVE session; (c) covers the tail with no
        1 Hz poll and no change to E7's stop rule. Whichever is chosen, **say why in the code**, because the
        next reader will wonder why it is not on the countdown tick.
  - [x] `OnClosing` unloads unconditionally — a native pool held across shutdown is not a leak the OS cannot
        clean, but `translator_free` is one line and the symmetry is worth it.

- [x] **T4 — `IdleUnloadMinutes` in `TranslationPolicy` (AC 2).**
  - [x] Add `internal const int IdleUnloadMinutes = 10;` with **exactly one** evidence grade in its comment.
        `TranslationPolicyTests.Every_member_carries_exactly_one_evidence_grade` enforces the "exactly one" —
        E4.S3's T5 hit it: **replace** the grade word when a measurement lands, never add a second.
  - [x] Grade it `[ASSUMED]`, and say what would change it: E8.S7's TP-BRG-06 measures the unload and the
        owner's own habit — a player who stops LIVE to read a quest text and restarts in 90 seconds pays a
        reload for a timeout that is too short.
  - [x] **Do not make it a setting.** §12's table is closed and R-4 already ruled that the offline engine gets
        **one** user-facing decision (Download / Remove). A second knob for a timeout nobody can feel is noise.

- [x] **T5 — Unload is idempotent and safe against a translation in flight (AC 4).**
  - [x] Take the same lock E8.S2's T3 uses for the lazy load. An unload racing a translate must either wait or
        no-op; it must never `translator_free` a handle a native call is inside.
  - [x] `translator_free` **exactly once** per load. Two frees on one handle is a native crash, and a crash in a
        prototype branch is what closes the branch for the wrong reason.
  - [x] After unload the next translation loads again, cleanly — a second load in one process must produce the
        same resident delta as the first. E8.S1's harness is where that is checked.

- [x] **T6 — Prove the memory comes back, in the spike and not in CI (AC 4).**
  - [x] The working-set check belongs in `BergamotSpike` (E8.S1's harness), **never** in the suite: CI-3 forbids
        timing assertions and a working-set assertion on a shared runner is worse than a timing one.
  - [x] In CI, the assertion is about **behaviour**: with a fake engine and an injected clock, `Free` was called
        once, at the right instant, and not before.

## Dev Notes

### The policy, as a table — because this is four cases and it is worth reading them all

| LIVE running? | Time since last offline translation | Loaded? | What happens |
|---|---|---|---|
| yes | anything | yes | **stays loaded** — AC 1, AC 3. This is the whole of A-1(b). |
| yes | anything | no | loads on the next offline translation, not before (I10) |
| no | `< IdleUnloadMinutes` | yes | stays loaded — the user may be between two Translator-tab lines |
| no | `≥ IdleUnloadMinutes` | yes | **unload**, `translator_free`, working set returns to baseline — AC 4 |

The row that matters, and the one a naive implementation gets wrong, is **row 1 with a long gap**: a LIVE session
whose engines are all gate-paused for a 30-minute window has no offline translation for 30 minutes. A plain
"unload after 10 idle minutes" would free the model in the middle of the session and pay the init again on
resume. A-1(b) exists precisely to forbid that, and **TP-BRG-05** is the test that catches it.

### What this story may and may not change

| May | May not |
|---|---|
| Add `Services/BergamotLifetime.cs` and one constant in `TranslationPolicy` | Add a setting, or a second knob (§12, R-4) |
| Read `MainWindow.IsLive` through a `Func<bool>` | Take a reference to `MainWindow` inside `Services/` (I2) |
| Arm a one-shot timer from `StopLive` | Add a second 1 Hz poll, or silently widen E7's countdown stop rule |
| Call `Unload()` on the provider | Own the unload **mechanism** — that is E8.S2's `translator_free` |
| Measure the working set in `BergamotSpike` | Assert on a working set or a duration in CI (CI-3) |

### Invariants this story must keep

- **I2** — the policy is a `Services/` type over two delegates. No `Window`, no `DispatcherTimer` inside it.
- **I10** — the policy can only unload. Nothing it does causes a load, and nothing it does runs before first
  paint.
- **I16** — the LIVE loop's shape is not this story's to change: *"the three dedup layers, the batch join, the
  `rateLimited` latch, the strictly sequential LIVE loop and the cancellation token reaching `HttpClient` are
  kept as they are"*. A lifetime hook that reorders a tick is out of scope.
- **CI-3 / IS-6** — injected clock, no `Task.Delay`, no sleeping test.

### Repo traps

- **`_liveCts` has exactly two writers** (`MainWindow.Live.cs:136`, `:196`) and E7.S2's review already found a
  guard that returned *before* a stop decision because of it. Read `MainWindow.xaml.cs:695-700`'s note before
  touching anything that reads `_liveCts`.
- **`StopLive` is reachable from four places** (`MainWindow.Live.cs:53, :84, :107`, and the hotkey) — arm the
  one-shot in `StopLive` itself, not at its call sites, or three of the four will be missed.
- **`TranslationPolicyTests` requires exactly one evidence grade per member.** Adding `[MEASURED]` beside an
  existing `[ASSUMED]` fails the test; E4.S3 documented this in its T5 and it is the same trap.
- **The compact overlay has its own 600 ms `_beat`** (E7.S4) and it now **stops** when paused. Do not hang a
  lifetime check on it: it is not running in the state where AC 4 fires.
- **A `DispatcherTimer` keeps a strong reference to its handler.** A one-shot armed in `StopLive` and never
  disarmed on window close is a small leak in a story whose entire subject is memory. Disarm in `OnClosing`.

## Testing

- **TP-IDs landed:** **TP-BRG-05** (kept loaded while LIVE runs — the model is not unloaded between ticks) and
  **TP-BRG-06** (unload timing — unloaded after `IdleUnloadMinutes` once LIVE has stopped; **the RSS half of
  TP-BRG-06 is E8.S7's**, on the P1-affected machines, per test-plan §4.3).
- **Everything in CI runs on the fake engine and an injected clock.** No model, no DLL, no sleeping.
- **Cases this story owes:**
  1. LIVE running, clock advanced by 10× the timeout, no translation ⇒ **not** unloaded (AC 1, AC 3,
     TP-BRG-05).
  2. LIVE stopped, clock advanced past the timeout ⇒ unloaded **once** (AC 4, TP-BRG-06).
  3. LIVE stopped, clock advanced **just under** the timeout ⇒ still loaded (the boundary, and it is where an
     off-by-one lives).
  4. LIVE stopped, timeout elapsed, then a translation arrives first ⇒ `RecordUse` defers the unload.
  5. LIVE restarts before the timeout ⇒ the one-shot is disarmed and nothing is freed.
  6. `Unload()` twice ⇒ `translator_free` once (idempotence, AC 4).
  7. Unload racing a translate ⇒ no free while a call is inside the engine (AC 4, T5).
  8. `TranslationPolicy.IdleUnloadMinutes` exists, is 10, and carries exactly one grade (AC 2) — the existing
     `TranslationPolicyTests` sweep covers the grade; add the value pin.
- **In the spike only** (`BergamotSpike`, `PWRU_SPIKE=1`): the working set returns to baseline after unload, and
  a second load costs the same as the first.

## Size, dependencies, risk

**Size:** **S** · **Depends on:** **E8.S2** (the engine seam and the `Unload()` capability) · **Blocks:**
nothing — E8.S5 wires the chain and does not read the lifetime ·
**Risk:** **low in code, high in consequence.** The policy is a dozen lines and a table of literals. What it
protects is the sentence the whole feature is sold on — *"uses memory only while translating"* (§4.2's mockup,
and the consent dialog says it too). If the unload does not work, the About tab is telling the user something
untrue about 127 MiB of their machine ·
**DoD:** TP-BRG-05 and TP-BRG-06's behavioural halves are green on the fake engine, and the spike shows the
working set returning to baseline on the real one.

## How to verify manually

1. Install the engine, start LIVE, force every online tier into a gate window, and let the offline engine answer
   one line. Note the working set.
2. Leave LIVE running for **longer than `IdleUnloadMinutes`** with no offline line — because everything paused,
   or because the chat is quiet. The working set does **not** drop: the model is still loaded (AC 1, AC 3).
3. Stop LIVE. Wait out the timeout. The working set drops back to its pre-load value (AC 4).
4. Translate one line in the Translator tab: it loads again, once, and the delta matches step 1.
5. Stop LIVE and restart it inside the timeout: nothing is freed and nothing is reloaded.
6. Close the app with the model loaded: no crash, no hang (T3's `OnClosing`).

### Completion Notes List

**The policy — `Services/BergamotLifetime.cs` (T1, AC 1, AC 5).** `Func<bool> liveIsRunning`, an
injected `Func<DateTimeOffset>` clock and a `TimeSpan` window (defaulted from the policy table).
`RecordUse()` stamps the last use; `ShouldUnload(bool isLoaded)` is the predicate; `RemainingIdle()`
is what lets the one-shot be armed for the remainder of a window rather than for a whole new one.
Written and tested over literals before it was wired to anything. No `Window`, no `DispatcherTimer`,
no settings read (I2), and it can only ever say *unload* (I10) — pinned by a source scan in the tests.

**The LIVE signal (T2).** `() => _liveCts != null`, handed in from `MainWindow`'s constructor — the
same spelling `PendingRetryQueue` gets at `MainWindow.Ocr.cs`. Sampled at every question, never at
construction, and a case exists whose only job is to catch a captured `false`
(`The_LIVE_question_is_asked_at_every_question_and_never_at_construction`).

**The heartbeat (T3) — recommendation (a) + (c), on the architect's ruling.**
- **(a)** `SweepLocked()` at the top of both translate paths and `RecordUse()` after the native call,
  both **inside the provider's existing lock** — so the question and the free are one instant.
- **(c)** ONE one-shot `DispatcherTimer` (`_offlineIdleTimer`), armed by `StopLive` and by nothing
  else a gesture can reach, disarmed on LIVE start and in `OnClosing`. It fires once, stops itself,
  and **re-arms only when it finds the window has moved under it** (a translation landed after the
  arming) — which closes the tail of the story's case 4: deferring must not mean forgetting.
- **E7's `CountdownTick` stop rule was NOT touched.** A test asserts the tick body still names
  nothing offline, and the reason is written in `_offlineIdleTimer`'s own remark: that tick has one
  stop rule, and a consumer needing it to run for a reason the rule does not know about is exactly
  the bug E7.S2's review flagged.
- `OnClosing` disarms and unloads. **Off the dispatcher and bounded**: `Task.Run(_offlineEngine.Unload)`
  with a **2-second** wait — an order of magnitude past a 40-line batched frame (3.75 ms/line,
  measured) and short enough that a wedged native call cannot hold a closing window open. Past the
  bound the process exits and the OS reclaims.

**The constant (T4).** `TranslationPolicy.IdleUnloadMinutes = 10`, `[ASSUMED]`, exactly one grade,
with what would change it (E8.S7's TP-BRG-06 plus the owner's own habit). Not a setting (R-4, §12).
Value pinned in `TranslationPolicyTests`.

**Idempotence and the race (T5).** `UnloadIfIdle()` takes the same lock the lazy load takes;
`translator_free` runs exactly once per load; an unload racing a translate waits for it and then
finds the window has moved (because the in-flight call recorded a use on its way out) — pinned with
the fake, whose `PeakConcurrentCalls` stays 1 and whose `WasDisposedWhileInFlight` stays false.

**T6.** The working-set-after-unload and second-load-costs-the-same cases are §9 of `BergamotSpike`,
under `PWRU_SPIKE=1` — measured through the app's own `BergamotTranslator` + `BergamotLifetime`
rather than through `BlockingService` (which §4 already covered), with the clock injected there too.
CI asserts behaviour only: no timing assertion, no sleep, no working set (CI-3).

**E8.S3's Remove-while-loaded, fixed.** `MainWindow.UnloadThenRemove(engine, store)` — the engine is
freed first, then the files are deleted. It waits on the provider's lock deliberately (a frame in
flight finishes or fails typed), which is the one place the dispatcher does; it is bounded by a
batched frame and it is a destructive gesture the user just confirmed. Static, so the ORDER is
provable with no window: `Remove_unloads_the_engine_before_it_deletes_the_files` records
`Directory.Exists` from **inside** `translator_free` (a new `OnDispose` hook on the fake) and asserts
the files were still there, then gone, and that the freed byte count is the true one — no more
"removed — 0 MB freed" over a full directory.

**Deviations (3), all deliberate:**

1. **`ShouldUnload` takes `isLoaded` as a parameter**, not as a fourth `Func<bool>`. The story writes
   the predicate as `… && loaded` without saying where `loaded` comes from; the caller that matters
   asks inside the provider's lock holding that truth in a local field, and a delegate sampled from
   outside the lock would answer about a different instant than the free.
2. **`OfflineModelStoreTests.No_startup_path_asks_the_model_store_anything` narrowed for the
   constructor only**, from the NAME `ModelDirectory` to the CALL `ModelDirectory()`. The provider is
   built in `MainWindow`'s constructor beside the chains and takes its two locators as method groups;
   a method group reads no disk. **Not a weakening** — `ApplySettings` keeps the full list, a call
   still fails, the narrowing is pinned non-vacuous (the argument list is asserted verbatim), and the
   behavioural half was **strengthened**: `Constructing_the_store_and_all_three_chains_opens_no_file…`
   now builds the provider too and still asserts the model root does not exist.
3. **`PausedStateTests.The_toast_route_and_its_lifetime_are_the_main_windows` now counts three
   `DispatcherTimer`s** in the main window, not two, and names the third. §2.4's "one `DispatcherTimer`
   for the whole app" means one COUNTDOWN — `_countdownTimer`'s own remark says so — and the count
   stays exact, so a fourth is still a decision.
