# Story E5.S2: Fix the auto-stop counter and add the time-window rule

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E5 (E) — Honest live translation · increment 4 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **One line is the whole bug.** `MainWindow.Live.cs:219` — `consecutiveErrors = 0;` — sits at the end of the
> `try`, so it runs on **every** non-throwing tick, including an empty one. In a calm chat the loop alternates
> "empty tick, failing tick, empty tick, failing tick" and the counter never reaches 2, let alone 5. That is
> scenario **S4c** (`analyse…` A2): the app trickles rejected requests all evening and **never** auto-stops.
>
> This is an **S**, and it is the story with the highest ratio of user-visible consequence to lines changed in the
> whole release. It is also the one that changes **when LIVE stops** — a behaviour users already know — so the
> 5-consecutive rule is kept exactly as it is and the new rule is added beside it.

## Story

As a player who walked away from a calm chat,
I want LIVE to stop when it is genuinely broken,
So that it does not trickle failing requests all evening while I am not looking.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E5.S2. Do not weaken._

1. **Given** `MainWindow.Live.cs:219` resets `consecutiveErrors = 0` at the end of every non-throwing tick —
   including an empty one — which is why the auto-stop never fires in a calm chat (`analyse…` A2, S4c)
   **When** the §9.2 table lands
   **Then**: a tick that translated ≥ 1 line successfully resets the counter and clears the window; an **empty**
   tick leaves both unchanged; a **gate-open** tick leaves both unchanged (it is neither a success nor a failure);
   a tick that threw increments the counter and stamps `DateTime.UtcNow` into a bounded queue trimmed to
   `AutoStopWindowMinutes` (2).
2. **Given** the two triggers
   **When** `consecutiveErrors >= 5` **or** the window holds ≥ 5 error stamps
   **Then** LIVE auto-stops, and the existing 5-consecutive rule is kept because it is what users already know.
3. **Given** §9.2's closing rule
   **When** every provider is paused
   **Then** LIVE **must not** auto-stop for that reason — pausing is the system working correctly.
4. **Given** the auto-stop message (`Live.cs:231-238`)
   **When** LIVE stops
   **Then** the sentence carries both the reason and the way back, per `ux-mode-degrade.md` §3.2
   (`Live stopped — {n} reads in a row failed. Press ▶ to try again.`).

## The four tick outcomes, as a table (§9.2)

| Tick outcome | `consecutiveErrors` | error-time window | `backoffSteps` (E5.S1) |
|---|---|---|---|
| translated ≥ 1 line successfully | **reset to 0** | **cleared** | reset to 0 |
| nothing new to translate (empty) | unchanged | unchanged | unchanged |
| gate open, tick skipped | unchanged — neither a success nor a failure | unchanged | `++` |
| threw | `++`, stamp `UtcNow` | trimmed to the last 2 minutes | unchanged |

**Express the outcome ONCE.** E5.S1 introduces `LiveTickPolicy`; this story puts
`internal enum LiveTickOutcome { Translated, Empty, Paused, Threw }` in it and drives **all three** counters —
`consecutiveErrors`, the window queue, and `backoffSteps` — from the same value. Two independent notions of "a
good tick" is precisely how `:219` became a bug, and re-creating it in a story whose entire purpose is to fix it
would be a poor joke.

## Tasks / Subtasks

- [ ] **T1 — The pure decision (AC 1, AC 2).** `Services/LiveTickPolicy.cs` (created by E5.S1):
  - [ ] `internal enum LiveTickOutcome { Translated, Empty, Paused, Threw }`.
  - [ ] `internal sealed class LiveErrorTracker` — **not** a static: two LIVE sessions in one test run must not
        share a counter, and `StopLive`/`StartLive` get a fresh one for free.
        - `int Consecutive`
        - a bounded `Queue<DateTimeOffset>` of error stamps
        - `internal bool Record(LiveTickOutcome outcome, DateTimeOffset now)` → **true when LIVE must stop**
        - `internal void Reset()`
  - [ ] **An injected clock, not `DateTime.UtcNow` inline** (IS-6, **CI-3**): the caller passes `now`, so
        TP-LIVE-07/08 assert the 2-minute window without a `Task.Delay`. `DateTimeOffset`, not `DateTime` —
        everything else on this path already speaks `DateTimeOffset` (`GateSnapshot`, `TranslationException.RetryAt`).
  - [ ] Trim on **every** `Record`, not only on an error: a session that fails 4 times, runs clean for an hour and
        fails once more must not stop. Trim by time (`now - stamp > AutoStopWindowMinutes`) **and** bound the
        queue's length (5 is enough to decide; keep ≤ 8 so a pathological burst cannot grow it).
  - [ ] The two triggers, OR'd: `Consecutive >= AutoStopConsecutiveErrors` **or** `stamps.Count >= 5`.
- [ ] **T2 — The constants, graded exactly once.** `Services/TranslationPolicy.cs`:
  - [ ] `AutoStopConsecutiveErrors = 5` — grade **`[CONFIRMED]`**: it is today's literal, at `Live.cs:231`, moved.
  - [ ] `AutoStopWindowMinutes = 2` — grade `[ASSUMED] architecture-cible.md §9.2`, and say what would settle it
        (field reports; the same U9/E2.S7 lane as the gate windows).
  - [ ] `AutoStopWindowErrors = 5` if the second trigger's count is not simply the first constant — §9.2 uses 5
        for both. Reusing one constant for two rules is a hidden coupling; two constants that happen to be 5 is
        one line more and is what a tuning commit will want.
  - [ ] `TranslationPolicyTests.Every_member_carries_exactly_one_evidence_grade` (`:53-80`) reads the file as
        **text**: one grade word per member, no more, no less.
  - [ ] Add the new numbers to `The_numbers_are_the_ones_the_code_uses_today` (`:85-109`). Unlike the rate-ceiling
        constants (deliberately unpinned, `:142-148`), these are behaviour a user watches, and a change to them
        should have to be deliberate.
- [ ] **T3 — Wire it into the loop (AC 1).** `MainWindow.Live.cs`:
  - [ ] **Delete `consecutiveErrors = 0;` at `:219`.** That is the bug. In its place, the tick's outcome is
        computed and handed to the tracker: `Translated` when `confirmed.Count > 0` and `AppendLinesToHistory`
        returned without throwing (`:203-210`), `Empty` otherwise (`:211-218`).
  - [ ] The `catch (Exception ex)` at `:228-239` records `Threw` and reads the tracker's verdict instead of doing
        its own `++consecutiveErrors >= 5` (`:231`).
  - [ ] E5.S1's skipped-tick branch records `Paused` — which changes **nothing** (AC 3), and the point is that it
        is written down and tested rather than being an accident of where the `continue` sits.
  - [ ] `StopLive()` (`:142-151`) and `StartLive` (`:71-111`) reset the tracker. A player pressing ▶ after an
        auto-stop must get a clean five, not one.
- [ ] **T4 — A pause never auto-stops (AC 3).** This is `Paused` leaving both counters unchanged — but assert it
      at the loop level too (**TP-LIVE-09**: 100 gate-open ticks, LIVE still running). It is the R-02/R6 failure
      mode: an app that stops itself because it was correctly waiting.
  - [ ] **Careful, this is the subtle one.** When every tier is paused, `ChainTranslator` throws
        `AllProvidersPaused` — an exception, which reaches the `catch` and looks like `Threw`. **E5.S1's pre-tick
        skip means that should not normally happen on the read path**, but it *can*: a gate can open between the
        `PauseNow()` check and the request. So the `catch` must classify:
        `ex is TranslationException { Kind: TranslationErrorKind.AllProvidersPaused }` ⇒ **`Paused`**, not
        `Threw`. One `when` clause, and without it AC 3 holds only by timing.
- [ ] **T5 — The sentence (AC 4).** `Live.cs:231-238`:
  - [ ] Replace `"Live stopped after repeated errors ({Friendly(ex)})."` with §3.2's form:
        `Live stopped — {n} reads in a row failed. Press ▶ to try again.` — the reason **and** the way back.
  - [ ] **The string belongs in `Services/UserMessages.cs`** (ruling GAP-4: every user-facing sentence lives in
        that table, keyed, testable, existing exactly once — UX hint 11). Add it there with a `{n}` parameter and
        read it from the loop. E7.S1 owns the final copy pass; putting the string in the right *place* now is what
        makes that pass a table edit instead of a hunt.
  - [ ] Keep `Services.Logging.Error(...)` at `:233` — the log line is what a bug report is made of — but let its
        text follow the new rule (a count, not "5 consecutive errors" hard-coded).
  - [ ] The window-rule stop needs its own wording (*n* errors in 2 minutes is not "in a row"). §3.2 has no row for
        it; write a provisional sentence in the same shape, in `UserMessages`, and flag it for **E7.S1** and for
        **Sally** in the PR — it is a genuine copy gap, not an oversight to paper over.
- [ ] **T6 — Tests (T15).**
  - [ ] **TP-LIVE-04** — a tick that translated ⇒ counter 0, window cleared.
  - [ ] **TP-LIVE-05** — an **empty** tick ⇒ counter **unchanged**. *Today it resets*; this case is the regression
        guard for the bug this story exists to fix, so name it after the behaviour, not after the story.
  - [ ] **TP-LIVE-06** — a gate-open tick ⇒ both unchanged.
  - [ ] **TP-LIVE-07** — a throwing tick ⇒ `++` and a stamp; stamps older than 2 minutes are trimmed.
  - [ ] **TP-LIVE-08** — **both** rules: 5 consecutive ⇒ stop; **and** 5 stamps inside 2 minutes **with successes
        interleaved** ⇒ stop. The second is the calm-chat case and is the reason the story exists.
  - [ ] **TP-LIVE-09** — 100 gate-open ticks ⇒ still running.
  - [ ] **AllProvidersPaused arriving as an exception is classified `Paused`** (T4's `when` clause).
  - [ ] All of these are **L1** over `LiveErrorTracker` with an injected clock. No window, no `Task.Delay`.

## Dev Notes

### Invariants this story must keep

- **I3 — the OCE trap, and it bites here specifically.** `Live.cs:227` filters
  `catch (OperationCanceledException) when (ct.IsCancellationRequested)`; a **timeout** is a
  `TaskCanceledException` with the token *not* cancelled and must fall through to the generic handler, be counted,
  and let the loop keep running. **TP-LIVE-16** pins it. Any new `catch` or `when` this story adds must not
  swallow a timeout as a cancel — nor count a genuine user Stop as an error. Read the comment at `:221-226` before
  editing anything in that block; it is the best description of the trap in the repo.
- **I16** — the loop stays strictly sequential and the eleven behaviours do not move. This story changes counters
  and one sentence.
- **I2** — `LiveTickPolicy` / `LiveErrorTracker` are UI-free and clock-injected.

### Rulings that apply

- **GAP-4** — user-facing sentences live in `Services/UserMessages.cs`, exactly once (UX hint 11).
- **§9.2's closing rule** — a gate-open pause is not an error and must never auto-stop LIVE.
- **E5-a** — a short rate-ceiling wait lengthens the tick; it is neither an error nor a pause. It ends as a
  `Translated` or `Empty` tick like any other.
- **E1.S6's deviations D1/D2/D4** are accepted until E7.S1. Match the existing `UserMessages` style (no `{P}`, no
  terminal stop on the six wrappers) rather than inventing a third voice.

### Repo traps

- **`:219` is the bug and it is one line.** Do not "keep it for safety". Deleting it is the story.
- **`consecutiveErrors` is a local in `LiveLoop`** (`:177`), not a field. Replacing it with a tracker object means
  deciding its lifetime: a local matches today's semantics (fresh per `StartLive`) and is the smaller change.
  Whatever is chosen, `StopLive` must not leave a stale counter behind for the next session.
- **`StopLive()` sets `"Live stopped."` and then the loop overwrites it** (`:234-235` — "this sets 'Live stopped.'
  first… then the real reason"). Keep that ordering; it is deliberate and commented.
- **`Friendly(ex)` is `UserMessages.For`** (`MainWindow.xaml.cs:458`). The new sentence carries a **count**, so it
  is not a `Friendly` wrapper — it is a new entry in the table.
- **`TranslationPolicyTests` reads the policy file as text**: one evidence grade per new constant.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Size, dependencies, risk

**Size:** S · **Depends on:** **E5.S1** (the `Paused` outcome must exist, and `LiveTickPolicy` is its file) ·
**Risk:** **medium — changing when LIVE stops is user-visible behaviour.** Two directions to get it wrong, and
they fail in opposite ways: too eager ⇒ LIVE stops during a normal blip and the player thinks the app broke; too
lax ⇒ S4c survives and the story shipped nothing. The 2-minute window with successes interleaved (TP-LIVE-08's
second half) is the case that distinguishes them ·
**DoD:** T15 passes; a calm chat under a persistent failure auto-stops.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. **The calm-chat case, which is the story.** Block one read provider and make the other fail (hand-edit
   `provider-state.json` for one; disconnect for the other, or point `hosts` at a black hole). Start LIVE on a
   chat that produces a line every ~20 s. Within ~2 minutes LIVE **stops**, with a sentence naming the reason and
   `Press ▶ to try again`. Before this story it ran all evening.
3. **The pause case.** Block **every** read provider 10 minutes out and start LIVE: it pauses (E5.S1) and, after
   100+ ticks, is **still running**. It must not stop.
4. **The known rule still works.** Five consecutive genuine failures ⇒ stop, exactly as before.
5. Press ▶ after an auto-stop: it starts clean and does not stop again on the first failure.
6. Press ■ mid-translation: the feed and status are untouched apart from `Live stopped.` (UX hint 1 — `Cancelled`
   never reaches a surface).
