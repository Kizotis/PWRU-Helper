# Story E5.S2: Fix the auto-stop counter and add the time-window rule

Status: **review**

_Epic E5 (E) — Honest live translation · increment 4 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **One line is the whole bug.** `MainWindow.Live.cs:219` — `consecutiveErrors = 0;` — sits at the end of the
> `try`, so it runs on **every** non-throwing tick, including an empty one. In a calm chat the loop alternates
> "empty tick, failing tick, empty tick, failing tick" and the counter never reaches 2, let alone 5. That is
> scenario **S4c** (`analyse…` A2): the app trickles rejected requests all evening and **never** auto-stops.
>
> This is an **S**, and it is the story with the highest ratio of user-visible consequence to lines changed in the
> whole release. It is also the one that changes **when LIVE stops** — a behaviour users already know — so the
> 5-consecutive rule is kept exactly as it is and the new rule is added beside it.

## Story

As a player who walked away from a calm chat,
I want LIVE to stop when it is genuinely broken,
So that it does not trickle failing requests all evening while I am not looking.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E5.S2. Do not weaken._

1. **Given** `MainWindow.Live.cs:219` resets `consecutiveErrors = 0` at the end of every non-throwing tick —
   including an empty one — which is why the auto-stop never fires in a calm chat (`analyse…` A2, S4c)
   **When** the §9.2 table lands
   **Then**: a tick that translated ≥ 1 line successfully resets the counter and clears the window; an **empty**
   tick leaves both unchanged; a **gate-open** tick leaves both unchanged (it is neither a success nor a failure);
   a tick that threw increments the counter and stamps `DateTime.UtcNow` into a bounded queue trimmed to
   `AutoStopWindowMinutes` (2).
2. **Given** the two triggers
   **When** `consecutiveErrors >= 5` **or** the window holds ≥ 5 error stamps
   **Then** LIVE auto-stops, and the existing 5-consecutive rule is kept because it is what users already know.
3. **Given** §9.2's closing rule
   **When** every provider is paused
   **Then** LIVE **must not** auto-stop for that reason — pausing is the system working correctly.
4. **Given** the auto-stop message (`Live.cs:231-238`)
   **When** LIVE stops
   **Then** the sentence carries both the reason and the way back, per `ux-mode-degrade.md` §3.2
   (`Live stopped — {n} reads in a row failed. Press ▶ to try again.`).

## The four tick outcomes, as a table (§9.2)

| Tick outcome | `consecutiveErrors` | error-time window | `backoffSteps` (E5.S1) |
|---|---|---|---|
| translated ≥ 1 line successfully | **reset to 0** | **cleared** | reset to 0 |
| nothing new to translate (empty) | unchanged | unchanged | unchanged |
| gate open, tick skipped | unchanged — neither a success nor a failure | unchanged | `++` |
| threw | `++`, stamp `UtcNow` | trimmed to the last 2 minutes | unchanged |

**Express the outcome ONCE.** E5.S1 introduces `LiveTickPolicy`; this story puts
`internal enum LiveTickOutcome { Translated, Empty, Paused, Threw }` in it and drives **all three** counters —
`consecutiveErrors`, the window queue, and `backoffSteps` — from the same value. Two independent notions of "a
good tick" is precisely how `:219` became a bug, and re-creating it in a story whose entire purpose is to fix it
would be a poor joke.

## Dev Notes

### Invariants this story must keep

- **I3 — the OCE trap, and it bites here specifically.** `Live.cs:227` filters
  `catch (OperationCanceledException) when (ct.IsCancellationRequested)`; a **timeout** is a
  `TaskCanceledException` with the token *not* cancelled and must fall through to the generic handler, be counted,
  and let the loop keep running. **TP-LIVE-16** pins it. Any new `catch` or `when` this story adds must not
  swallow a timeout as a cancel — nor count a genuine user Stop as an error. Read the comment at `:221-226` before
  editing anything in that block; it is the best description of the trap in the repo.
- **I16** — the loop stays strictly sequential and the eleven behaviours do not move. This story changes counters
  and one sentence.
- **I2** — `LiveTickPolicy` / `LiveErrorTracker` are UI-free and clock-injected.

### Rulings that apply

- **GAP-4** — user-facing sentences live in `Services/UserMessages.cs`, exactly once (UX hint 11).
- **§9.2's closing rule** — a gate-open pause is not an error and must never auto-stop LIVE.
- **E5-a** — a short rate-ceiling wait lengthens the tick; it is neither an error nor a pause. It ends as a
  `Translated` or `Empty` tick like any other.
- **E1.S6's deviations D1/D2/D4** are accepted until E7.S1. Match the existing `UserMessages` style (no `{P}`, no
  terminal stop on the six wrappers) rather than inventing a third voice.

### Repo traps

- **`:219` is the bug and it is one line.** Do not "keep it for safety". Deleting it is the story.
- **`consecutiveErrors` is a local in `LiveLoop`** (`:177`), not a field. Replacing it with a tracker object means
  deciding its lifetime: a local matches today's semantics (fresh per `StartLive`) and is the smaller change.
  Whatever is chosen, `StopLive` must not leave a stale counter behind for the next session.
- **`StopLive()` sets `"Live stopped."` and then the loop overwrites it** (`:234-235` — "this sets 'Live stopped.'

- **`Friendly(ex)` is `UserMessages.For`** (`MainWindow.xaml.cs:458`). The new sentence carries a **count**, so it
  is not a `Friendly` wrapper — it is a new entry in the table.
- **`TranslationPolicyTests` reads the policy file as text**: one evidence grade per new constant.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

### Completion Notes List

**The one line is deleted.** `consecutiveErrors` no longer exists in `MainWindow.Live.cs` — the scan
`The_reset_that_forgave_every_calm_tick_is_gone` asserts the name appears nowhere in the file's code. What
replaced it is `LiveErrorTracker`, a local of `LiveLoop`, fed the **same `LiveTickOutcome`** that drives
E5.S1's `backoffSteps`, on the two adjacent lines the scan also pins. Two independent notions of "a good
tick" is how `:219` became a bug; there is now one.

**The rule, exactly as it ships:** LIVE stops when **5 failures that cost a request**
(`LiveAutoStopThreshold`) fall inside **120 s** (`LiveAutoStopWindowSeconds`). `Translated` clears the queue,
`Empty` leaves it, `Paused` and `Refused` leave it (ruling **E5-c**), `SentFailure` stamps it. The trim runs
on every record, by time and by a hard `MaxErrorStamps = 8` bound.

**Ruling E5-c is the story's centre of gravity, and it is written down once** — in
`LiveTickPolicy.Classify(Exception)`: a `TranslationException` with `NotSent` **or**
`Kind: AllProvidersPaused` is `Refused`, everything else is `SentFailure`. The `NotSent` half is the one T4
does not name and E5-c requires: a tier refused from inside `HttpProviderCore` carries the gate's *last*
kind, so a 429 that was never re-sent still reads `RateLimited`, and only the flag can tell a refusal from a
failure. **I3 lives in the default arm** — a 12 s timeout is a `TaskCanceledException` with the token not
cancelled, it is a request that was sent and did not come back, and it counts. Nothing in `Classify` looks at
cancellation: the loop's filtered catch has already taken the genuine Stop, and re-testing it here is exactly
how a timeout becomes a phantom user-cancel.

**The dead-cable scenario, stated plainly because it is a deliberate outcome and not an oversight.** With
every read tier gated, E5.S1 skips the tick and E5-c refuses to count what still arrives as a throw: **LIVE
pauses for as long as the cable is out and never auto-stops.** That is the ruling — "a pause or a gate
refusal is never an error" — and it is R-02/R6 avoided. Pinned twice: 100 `Paused`/`Refused` records
(TP-LIVE-09) and 20 real `AllProvidersPaused` exceptions through `Classify`. The player is not left in the
dark; the skipped tick repaints "○ Live — paused, next try in {t}. It resumes on its own" every ≤ 5 s
(E5.S1). The stop §3.2 writes for that state — *"Live stopped — every engine is paused. Try again in {t}"* —
is not in A.2 and belongs to whoever owns "paused past the cap" (E7).

**Five deviations, all recorded; one that matters.**

1. **D1 — `LiveTickOutcome.Threw` ships as `SentFailure`, with a new sibling `Refused`.** Ruling E5-c landed
   after this story was written and splits "the tick threw" into the half that counts and the half that must
   not. `Refused` leaves `backoffSteps` alone — it is not a skipped tick, the tick really did capture and
   OCR — so E5.S1's curve is untouched.
2. **D2 — the two triggers ship as ONE predicate over one queue, and this is the deviation to review.**
   §9.2's table says a translated tick **clears the window**; §9.2's prose and TP-LIVE-08 want *"5 stamps
   inside 2 minutes with successes interleaved"* to stop LIVE. Both cannot hold: if a success clears the
   window, the window can only ever hold failures since the last success, which makes the second trigger a
   strict subset of the first. The spec contradicts itself; the architect's Phase-4 brief resolves it in
   favour of the table (`Translated` resets the queue; ≥ 5 sent failures inside 120 s stop LIVE) and names
   the discriminating pair of tests: *5 in 10 s ⇒ stop*, *5 spread over 3 min ⇒ no stop*.
   - What it **buys**: the stale streak E5.S1's review recorded is gone — four failures, a half-hour outage
     and one ordinary hiccup is now **one** failure and not five, so LIVE no longer stops on a single hiccup.
   - What it **costs, and a reviewer should look here**: five *consecutive* sent failures spread over more
     than two minutes no longer stop LIVE. That is reachable — a tick whose every request times out costs up
     to ~48 s (two tiers × `MaxAttempts` × 12 s), so five of them can exceed 120 s. In practice the gate
     opens a `SoftCooldownSecs` window on each such failure and the loop pauses instead, which by E5-c never
     stops LIVE either (see the dead-cable note). **If the owner wants a slow-timeout evening to stop LIVE,
     the honest fix is a rule about time spent failing, not a second counter** — a ruling, not a patch, so it
     is recorded rather than guessed at.
3. **D3 — `int Consecutive` ships as `RecentFailures`.** The same number: the queue is cleared by a
   translated tick, so what it holds *is* the streak, aged to the window. One notion, one name.
4. **D4 — the constants are `LiveAutoStopThreshold` (5, `[CONFIRMED]` — `Live.cs:301`'s literal, moved) and
