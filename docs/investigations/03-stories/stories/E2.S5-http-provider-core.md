# Story E2.S5: `HttpProviderCore` — 2 attempts, jitter, no retry on 429/403, `Retry-After` honoured

Status: **review**

_Epic E2 (B) — Provider gate · increment 1 · **Release A.1: E2 and E3 are separate PRs but ONE release** · the
owner's Phase-4 go was given 2026-09-06 (`README.md` § Phase 4)._

> **Release rule, non-negotiable, and this is the story it is about.** `epics.md` states it plainly: *"this is the
> story that, alone, makes the app 'correctly paused almost all the time' against `gtx`. It must not reach a
> release without Epic 3."* Once this lands, a 429 from an affected connection opens the gate on request #1 and
> the free tier is `client=gtx` and nothing else. E3 is what puts a working endpoint behind the gate. Ship them
> together (`architecture-cible.md` R7, owner's decision 2).

## Story

As a player whose connection has been throttled,
I want a refusal to cost one request,
So that the app stops paying three times for being told no.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E2.S5. Do not weaken._

1. **Given** today's loop retries three times with fixed 300/600 ms spacing and retries `HttpRequestException`
   (`TranslationService.cs:126-153,151`)
   **When** `HttpProviderCore` replaces it
   **Then** `MaxAttempts = 2`; the delay is **full jitter**, `Random(0, BackoffBaseMs << attempt)`, so two
   instances behind the same NAT stop retrying in lockstep; and **only `Unavailable` and `Timeout` are retried**.
2. **Given** a 429 or a 403
   **When** it arrives
   **Then** the provider raises immediately — exactly **one** HTTP request reaches the fake handler — and the gate
   owns the wait.
3. **Given** the shared shape of §7.0
   **When** any provider sends a request
   **Then** `HttpProviderCore` calls `gate.TryEnter(priority)` **before** the request and `gate.ReportSuccess()` /
   `gate.ReportFailure(kind, retryAfter)` **after** it; a provider never touches a gate directly; the per-request
   log line of E1.S5 is emitted here; the timeout stays 12 s (`TranslationService.cs:39`); the existing plausible
   Chrome User-Agent is kept and **not** rotated (`TranslationService.cs:41-42`).
4. **Given** a non-success response carrying `Retry-After`
   **When** it is parsed
   **Then** both forms (delta-seconds and HTTP-date) are accepted, the value is clamped to
   `[1 s, OpenCapMinutes]`, it **overrides** the computed window, and it is logged verbatim — even though Google
   measurably sends none today (`benchmark…` §3.1), because DeepL and Azure may.
5. **Given** I3
   **When** an `OperationCanceledException` surfaces
   **Then** it is filtered with `when (ct.IsCancellationRequested)` and a timeout is never mistaken for a user
   cancel.

## The seam, stated before the tasks: what moves, what stays

This is the story where two providers stop being two implementations of the same shape. Get the line right and E3
adds three providers by writing a URL and a parser; get it wrong and every provider re-implements the retry
policy.

## Dev Notes

### Invariants this story must keep

- **I1 — `ITranslator` does not change.** It is why the priority cannot ride on the call and why `LastOutcome`
  (R-3) is E3.S3's, on the chain, not on the interface. Assert `ITranslator`'s shape is byte-identical, as E1.S1
  did.
- **I2** — `HttpProviderCore` lives in `Services/`, UI-free, headless-testable. No WPF type, no dispatcher.
- **I3 — the OCE trap, and this story owns the one place it now lives.** Every OCE catch filtered with
  `when (ct.IsCancellationRequested)`. A `TaskCanceledException` from an `HttpClient` timeout carries a token
  that is **not** cancelled. E1.S3 closed the last unfiltered one; consolidating three catches into one is
  exactly the operation that reopens it.
- **I5 — never pad a batch count mismatch.** DeepL's `BadResponse` throw (`DeepLTranslator.cs:69-77`) stays
  untouched; padding once bypassed the fallback and poisoned the cache.
- **I9 / I10** — the core is the **first** caller of `gate.TryEnter`, which is what makes E2.S4's lazy load fire
  after first paint and (with `ConfigureAwait(false)`) off the dispatcher.
- **I11 — the log is pasted to Discord by design** (`MainWindow.xaml.cs:312-322`). No user text, no `q=`, no full

#### The behaviour changes, one line each (for the PR description)

1. **A 429 costs one request, not three** (TP-RET-01). The gate owns the wait.
2. **A 403 costs one request** (TP-RET-02) — it never retried, and now it is stated rather than implied.
3. **A 503 costs two requests, not three** (TP-RET-03); `MaxAttempts = 2`.
4. **A timeout is now retried once** (TP-RET-04): 1 request → 2. It was not retried before.
5. **A `Network` failure is no longer retried**: 3 requests → 1 (TP-RET-05). E3.S3's chain is the
   redundancy the retry used to fake.
6. **The back-off is full jitter, `Random(0, 500 << attempt)`**, replacing the fixed `300 × (attempt + 1)`.
7. **DeepL gains a retry it never had**: a 5xx or a timeout on a paid vendor path now costs two requests.
8. **DeepL gains §10.1 log lines** for the first time — and, with them, key redaction.
9. **Both providers now consult a gate**: a paused provider issues **zero** requests and raises with the
   gate's `RetryAt` (the epic's DoD sentence, tested end to end).
10. **The §5.4 rate ceiling now applies to real traffic**: a third request inside ~1 s waits ≤ 500 ms for a
    token instead of going straight out. A long per-line fan-out is therefore paced — E3.S8 caps it.
11. **`IOException` / `HttpIOException` are caught** where they used to escape raw, classified `Network`
    and given the `Network` sentence (not the timeout one today's ternary would have produced).
12. **The error body now reaches `Classify`** (one read, shared with the log and the §4.3 sniff). This can

    keyed on `Kind`; the provider literals moved into `ProviderOptions` verbatim.

#### Decisions and deviations worth a reviewer's eye

- **One admission per logical call, not per attempt** (T4 says "once per attempt"). Per-attempt
  admission is self-defeating with the numbers this story lands: the only two Kinds that are retried
  (`Unavailable`, `Timeout`) are exactly the two that arm §5.6's 5 s soft cooldown, so this call's own
  first failure would refuse its own second attempt and **TP-RET-03 (a DoD item) could never be true**.
  The core therefore admits once, counts every attempt into `burst60`, and reports **exactly once,
  after** — which is how TP-RET-07 reads. Flagged for Winston: if the ceiling must be charged per
  attempt, the soft cooldown has to stop applying to the call that caused it.
- **A `Wait` is honoured, not raised** — Winston's direction and `architecture-cible.md` §5, against
  T4's "this story does not wait". It waits through the injectable delay while
  `GateDecision.WorthWaiting`, at most twice, then raises. Raising instead would have made every
  third request in a burst fail: with `BucketCapacity = 2` the per-line fallback would refuse from
  line 3 onwards. E3.S3 still owns "move on to the next tier".
- **The parser runs inside the core**, handed in as a `Func<string, T>`. That is what lets a
  `BadResponse` reach the gate (§5.3 counts three in a row) and closes T3's `json!` item structurally:
  the loop returns a parsed value or throws, and no local can be null on the way out.
- **A retryable failure that the second attempt survives is not reported to the gate.** The logical
  call succeeded; a blip the retry absorbed is not evidence the provider is unwell. Say so if the
  gate should see it.
- **A genuine cancel mid-request reports nothing** (a cancel is not an outcome §5.3 has a row for). If
  it held the probe, the gate's own `ProbeTimeout` re-arms it — the zero-margin timeout E2.S1
  recorded is what covers this case, and it is the only path that relies on it.
- **The three per-line placeholder strings stayed put** (`TranslationService.cs:152`, `:160`, `:161`, `:174`), as the story
  instructs, and the disagreement is recorded: E1.S6's review named `HttpProviderCore` as their home,
  but they are produced by `TranslateLinesAsync`'s per-line fallback — batch policy (**E3.S8**) and
  copy (**E7.S1**), not one request. The `catch (TranslationException)` that renders a dead network as
  *"rate-limited"* is **not** fixed here either: the fix is a user-visible string, which this story is
  not allowed to change.
- **`RequestPriority` is `Interactive` everywhere**, passed as a per-call parameter of
  `HttpProviderCore.SendAsync`. `Background` did **not** reach the read chain: doing so would have
  meant a call-site change in `MainWindow.*`, and TP-START-02 allows exactly one `ProviderGates`
  reference outside `Services/`. E2.S3's reserve stays inert until **E3.S7 / E5.S4**.
- **The test suite now drives real gates.** Five classes that issue provider requests joined the
  non-parallel `Gates` collection (or, for `RequestLogTests`, the resetting base — it belongs to the
  `log-file` collection and cannot join a second one). `TestBackoffRedirect` turns IS-7's delay into a
  recorded request plus an advance of a run-wide virtual clock, so the token bucket is exercised for
  real and nothing sleeps (CI-3).
- **Three suites changed, not two.** The story allowed `HttpSeamGuardTests` and
  `TranslationPolicyTests`; `ProviderErrorMapperTests` and `RequestLogTests` also carry request-count
  assertions that the policy change makes false (network 3→1, timeout 1→2, 429 3→1). Each was
  re-pointed with the reason in the comment; no assertion was weakened.
