# Story E4.S5: Write the cache file as UTF-8 instead of `\uXXXX`

Status: **done (2026-09-07)**

_Epic E4 (D) — Shared persistent cache · follow-up to the E4.S3 spike · **Release A.2 (E4 + E5)** · the owner's
Phase-4 go was given 2026-09-06 (`README.md` § Phase 4)._

> **One line of options, and it is the whole story.** E4.S3 measured a full `translation-cache.json` at 502 B an
> entry — 3.3× §8.2's estimate — for one reason: `JsonSerializer`'s default encoder escapes every non-ASCII
> character as `\uXXXX`, so a Cyrillic letter that is two bytes in UTF-8 is written as six. The spike's own terms
> forbade changing the format, and it said so: *"switching to a non-escaping encoder … is the obvious follow-up …
> it is worth its own story."* This is that story.
>
> **The format is free to change right now and will not be again.** No shipped version of PWRU Helper writes this
> file — A.2 is unreleased — so nobody has one on disk to migrate (architect's ruling, 2026-09-07). The same
> change after A.2 ships would still be safe to READ (both forms parse identically) but would rewrite every
> user's file on their first save, which is a conversation this story does not have to have.

## Story

As a player with a full cache,
I want the file that holds my translations to be the size it should be,
So that the cache stays comfortably inside the guard that exists to refuse a corrupt one.

## Acceptance Criteria

1. **Given** a store that has cached a Russian line
   **When** the file is written
   **Then** the Cyrillic is in it as **UTF-8 text**, with no `\uXXXX` sequence anywhere in the file, and the file
   is still strictly valid JSON that this build reads back.
2. **Given** a `translation-cache.json` written in the **old** escaped form (a pre-E4.S5 branch build, or a hand
   edit)
   **When** it is loaded
   **Then** every entry is read exactly as before — a JSON parser cannot tell the two forms apart — and the next
   save simply rewrites it in the new form, with no migration and no `SchemaVersion` bump.
3. **Given** the spike's own 2000 realistic entries (`CacheLoadSpike.Entries`)
   **When** the full file is written through the store
   **Then** it costs **under 300 B an entry** and is **under 1 MB** — the bound it broke in E4.S3 — and CI
   defends both.

## What was changed

| | |
|---|---|
| `TranslationCacheStore.Options` | `+ Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping` (`System.Text.Encodings.Web`, in-box — **no new package**) |
| `MaxBytes` | **unchanged at 4 MB**, comment re-measured: the bound guards a corrupt file, not the cache, and ×7.6 of headroom is the lesson E4.S3 paid for |
| `ProviderStateStore` / `SettingsService` | **untouched.** Their options look similar and are not the same decision: both files hold ASCII, both are read by a human (`provider-state.json` is the one a user is asked to zip and send), and neither has a size problem |

**Why "unsafe" is safe here**, in the comment as well as in this file: the relaxed encoder stops escaping `<`,
`>`, `&` and `'`, which matters only where JSON is interpolated into HTML or a script. This file is written and
read by this app alone, parsed by `JsonDocument`, and never rendered anywhere (I11 goes further: it may not even
be named in the error report). Quotes, backslashes and control characters are still escaped — the output is
strictly valid JSON either way.

## The number

Re-measured with the E4.S3 harness (`PWRU_SPIKE=1`, same box, same seed, same generator) — full table in
`spikes/U8-cache-load.md` §8:

| entries | before | after |
|---|---|---|
| 500 | 231 KB · 474 B/entry · 3.6 ms | **128 KB · 263 B/entry · 2.4 ms** |
| **2000** | 981 KB · **502 B/entry** · 17.8 ms | **541 KB · 277 B/entry · 9.7 ms** |
| 5000 | 2 612 KB · 535 B/entry · 32.0 ms | **1 430 KB · 293 B/entry · 22.0 ms** |

**45% off the file and 45% off the load.** It is not §8.2's ~150 B an entry and it never could have been: only
the Russian **key** was escaped, while the English value (~70 B), the 33-byte round-trip timestamp and the field
names are ~130 B of every row. That is written down in the addendum so the estimate is not re-opened.

## Testing

Three cases in `TranslationCachePersistenceTests`, one per AC:

- `A_Cyrillic_entry_is_written_as_UTF8_and_never_as_escaped_code_points` — asserts on the **bytes** (`Contains
  "привет всем"`, `DoesNotContain "\u04"`), because a parser would pass either form, then reads the file back
  through a fresh store.
- `A_file_written_in_the_OLD_escaped_form_still_loads` — the escapes are spelled out in the fixture rather than
  produced by a serialiser, with a non-vacuity assertion on the fixture itself; also asserts the next save
  converts the file.
- `A_full_realistic_cache_costs_under_300_bytes_an_entry` — over `CacheLoadSpike.Entries(2000)`, which is why
  that generator became `internal`: the number CI defends and the number the spike publishes are produced by one
  method and cannot drift.

Regression: **774 passed / 0 failed / 0 skipped / 2 s** (baseline 771 — the three new cases). The spike stays
invisible to a normal run.

## Notes for what comes next

- **E5.S1 and the rest of E5 are unaffected.** Nothing about the chain, the gates or the LIVE loop changed; the
  cache file is smaller and reads the same.
- **The window to change this format closes at the A.2 release.** After that, a format change is a rewrite of
  every user's file on their first save.
- `MaxBytes` deliberately did **not** follow the file down. If a future story wants to tighten it, it re-measures
  first — that is the sentence E4.S3 wrote about the capacity and it applies to the bound too.
