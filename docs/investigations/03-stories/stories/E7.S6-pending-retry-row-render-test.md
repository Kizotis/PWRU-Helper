# Story E7.S6: Pending-retry row treatment, with a render test

Status: **review**

_Epic E7 (G) — Degraded-mode UX · increment 6 · **Release B.2** · the owner's Phase-4 go was given 2026-09-06
(`README.md` § Phase 4)._

> **Most of this already ships, and the story is therefore mostly a guard.** E5.S3 landed the pending-retry
> queue and both row forms in `Services/UserMessages.cs`: `PendingRetryRow()` → `"…"` (`:231`) and
> `RetryGaveUpRow()` → `"not translated — the engines did not come back"` (`:242`), the second wrapped in I4's
> `(` by the call site (`MainWindow.Live.cs:601`) and the first deliberately **not**. Both doc comments already
> carry this story's arguments — the pending form *"is deliberately **not** `"("`-prefixed, so it reads as
> pending rather than terminal"*, and *"a row never carries a countdown … there is exactly one explanation per
> window and it lives on the status line."*
>
> **What is genuinely left is the render test, and the reason it is a story of its own is that this is the exact
> trap that shipped a crash.** v0.11.2: a `Run.Text` binding — **TwoWay by default** — to a get-only property
> threw once per rendered item, invisible to an empty-list smoke launch. `TemplateRenderTests`' own doc comment
> is the lesson: *"verify list rendering with a genuinely injected item, not an empty collection."* Every
> `Run.Text` in both feed templates already carries `Mode=OneWay`; **this story's job is to make sure the next
> one does too, by scan and not by memory.**

## Story

As a player,
I want a row that is waiting to look different from a row that gave up,
So that I can tell "not yet" from "never".

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E7.S6. Do not weaken._

1. **Given** E5.S3's queue
   **When** a row is awaiting retry
   **Then** it renders as pending — the existing `…` placeholder treatment of `MainWindow.Live.cs:263`, **not** a
   `(`-prefixed terminal string — and **carries no countdown** (UX-DR5).
2. **Given** a row that exhausted `PendingRetryMaxAttempts`
   **When** it renders
   **Then** it shows the terminal form of §2.2 S5: `(not translated — all engines were paused)`.
3. **Given** I15
   **When** any new `Run.Text` binding is added to a feed template
   **Then** it is `Mode=OneWay` — a get-only property bound TwoWay throws once per rendered item — and it gains a
   case in the STA `TemplateRenderTests`, rendered through a `ContentControl` with a **real injected
   `OcrResultItem`**; an `ItemsControl` defers container generation headless and renders nothing.
4. **Given** `OcrResultItem` lives at the repository root with namespace `PWRUHelper` (not `.Models`)
   **When** this story lands
   **Then** it is **not moved** — the render test depends on it.

## Dev Notes

### Invariants this story must keep

- **I15 — every `Run.Text` binding is `Mode=OneWay` and gains an STA `TemplateRenderTests` case.** The whole
  story. `project-context.md`: *"`Run.Text` binds TwoWay BY DEFAULT — on a get-only property it throws once per
  rendered item."* `SpeakerPrefix` (`OcrResultItem.cs:19`) and `Translation`/`Original` (`:25`, `:42`) are
  **expression-bodied get-only properties** — precisely the shape that throws.
- **I4 — `(` is the failure marker.** The **given-up** and **cancelled** rows are parenthesised; the **pending**
  row is not. That is the whole distinction AC 1 and AC 2 draw, and it is also what keeps a placeholder out of
  the cache (`CachingTranslator.IsCacheable`). These strings are written by the UI onto a row and are never a
  translator's return value, so they cannot poison it — but the *visual* convention must stay consistent with
  the one that can.
- **Principle 5 / hint 2 — no row ever carries a countdown.** TP-RENDER-06.
- **NFR7 — repaint budget.** 50 rows × anything per second is the cost this epic exists to avoid.

### Rulings that apply

- **E5-g** — a row stamped `ReadCancelledRow()` is **finished, not failed**; the retry pass skips it, while the
  `({Friendly(ex)})` rows **are** retry candidates. Three row states, not two.
- **E3-h** — lines beyond `PerLineCap` are marked failed and re-translated after recovery by E5's retry pass.
  So a pending row can also come from a **cap** overflow, not only from a pause — another reason AC 2's *"all
  engines were paused"* over-claims (T1).
- **GAP-4 / UX-DR19** — the row strings live in `UserMessages`, once each. They already do.

### Repo traps

- **`TemplateRenderTests` uses a `ContentControl`, not an `ItemsControl`** (`:28-60+`), and `StaTestHost` is the
  shared STA + `Application` + Theme-resources host (`StaTestHost.cs:73-101`). It also uses `TempSettings`,
  because **constructing a `MainWindow` saves settings** and must never touch the developer's real `%AppData%`.
- **Both templates must be guarded, every time.** The test file's comment: *"Both the main Translator feed and
  the compact overlay feed render the same `OcrResultItem` … Guard BOTH templates."* The v0.11.2 crash was in
  one of them.
- **The `IsReadOnce` `DataTrigger` is a binding too** — the existing `framed` case exists because *"an
  `IsReadOnce` that got renamed or dropped would fail silently here rather than at the user."*
- **`Border` background/border live in the `Style`, not as attributes** (`MainWindow.xaml:320-325`'s comment):
  *"a local value beats a style trigger in WPF, so the read-once frame below would never win against them."* If
  T6 ever adds a trigger, that is the trap.
- **`OcrResultItem.TranslationBody` raises `PropertyChanged`; `Speaker`/`OriginalBody`/`IsReadOnce` do not**
  (`:10`, `:16`, `:22` are plain auto-properties). A row treatment that changes one of those after the item is
  in the list will not repaint. Set them before adding.
- **The `WPF` collection is serialised on one STA thread** (`StaTestHost.cs:73-74`) — **CI-4** budgets it at
  **< 15 s**; the epic's estimate is +3–6 s for ~8 render cases. If it grows past that, *"extract more logic to
  L1 rather than parallelising — a second `Application` throws."*
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Size, dependencies, risk

**Size:** S · **Depends on:** **E5.S3** (the queue and both row forms — in review at the time of writing) ·
**Risk:** **low-medium — this is the `Run.Text` TwoWay trap**, and the story's value is almost entirely in the
guard rather than in the behaviour. The way it fails is not a red test but a **green vacuous one**: a scan whose
regex matches nothing, or a render case that uses an `ItemsControl` and therefore renders nothing at all. Both
have precedents in this repo ·
**DoD:** every new binding has a render test.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green, and the `WPF` collection is still under ~15 s.
2. **Make the scan fail on purpose.** Delete `Mode=OneWay` from `MainWindow.xaml:340` and re-run: TP-RENDER-04
   goes red. Put it back. (If it stays green, the scan is vacuous — which is the only real risk here.)
3. **The three row states, on screen.** With LIVE running, block every provider: rows appear as `…`. Let two
   retries fail: they become `(not translated — …)`. Cancel a read-once mid-flight: those rows read
   `(not translated — read cancelled)`.
4. **No countdown in any row.** During the pause, the clock is in the chip/status line and **nowhere** in the
   feed — scroll the whole 50-row history.
5. **In place, not appended.** When the pause lifts, the `…` rows fill **in the same position** and the feed
   does not grow. (E5.S3's behaviour; this is the render half of it.)
6. **Both windows.** Repeat step 3 in the compact overlay: the same three treatments, same order.
