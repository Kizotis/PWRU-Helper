# Story E4.S4: Share one store between the read and the write decorators

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E4 (D) — Shared persistent cache · increment 3 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **This is the story that makes the epic visible to a player**, and it is the payoff sentence of the whole
> increment: *a line the LIVE feed translated is free when the player types it in the Translator tab.* Everything
> before it built a box; this one hands the same box to every decorator.
>
> It is also the second story in a row to touch the `MainWindow` constructor — the part of this codebase with the
> worst bug history — and it changes a line that a test pins **as source text**. Read the Repo traps before the
> first edit.

## Story

As a player,
I want a line I just watched being translated to be instant when I retype it,
So that the two halves of the app stop paying twice for the same sentence.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E4.S4. Do not weaken._

1. **Given** §8.1
   **When** the `MainWindow` constructor builds the pipeline
   **Then** one `TranslationCacheStore` instance is created and passed to **both** `CachingTranslator` decorators.
2. **Given** `MainWindow.Translate.cs:239` currently throws the write cache away on every key save (amplifier A5)
   **When** this story lands
   **Then** rebuilding the write chain **keeps** the store, and the session's accumulated translations survive a
   key save.
3. **Given** the trade-off recorded in §8.2
   **When** a value produced by any tier is stored
   **Then** the key stays provider-agnostic — a value produced by a lower tier may later be served while a higher
   tier is healthy, which is **accepted**; the producing provider is recorded in `"p"` for the log and for the
   Bergamot drop rule only.

## Scope correction: "both" is now **three**

AC 1 and §8.1's ctor sketch were written when there were two decorators. **E3.S7 landed a third**
(`_readOnceTranslator`, ruling OQ-a: read-once is a user click and needs `Interactive` providers, so it gets its
own chain instance over the same gates). Its own completion notes say so and name this story as the fix:

> *"Each chain keeps its own `CachingTranslator` … §8.2's single shared store behind thin decorators is **E4**, and
> it collapses all three caches at once."*

**The shared store wraps all three.** This is the architect's Phase-4 decision, recorded here so no reviewer has
to re-derive it, and it is what AC 1 means today:

```csharp
// MainWindow ctor, before InitializeComponent()
_cacheStore          = new TranslationCacheStore();                                       // lazy
_writeTranslator     = BuildWriteChain();                                                 // uses _cacheStore
_readTranslator      = new CachingTranslator(TranslationChains.BuildRead(_settings), _cacheStore);
_readOnceTranslator  = new CachingTranslator(
                           TranslationChains.BuildRead(_settings, RequestPriority.Interactive), _cacheStore);
```

Three decorators, one store, one file. It is **more** valuable than the two-decorator version, not a complication:
without it, a line LIVE just translated is not served to a read-once of the same screen a second later.

## Dev Notes

### Invariants this story must keep

- **I4** — the `(`-prefix rule stays in `CachingTranslator` (E4.S1 AC 2). Three decorators now share one store,
  which is exactly why the guard is upstream of all three and not inside it.
- **I10** — the ctor's new field constructs a store and reads nothing. The first **miss** loads the file, after
  first paint.
- **I2** — nothing about this reaches into `Services/` from the UI beyond constructing a store and passing it.
- **I9** (by analogy, and it is the same shape) — one gate per provider shared by both chains; now one cache store
  shared by all three decorators. Both are "shared state resolved once, at composition".

### Rulings that apply

- **OQ-a / E3.S7's deviation** — read-once has its own `Interactive` chain instance. That is why there are three
  decorators; it is not something to undo here.
- **§8.2's accepted trade-off (AC 3)** — the key is provider-agnostic on purpose. Do not add the provider to the
  key "now that we have `p`": it would multiply the cache by the tier count and defeat the one property the epic
  exists for. Write the `"p"` field, read it for the Bergamot drop rule and the log, and nothing else.
- **E3-c / TP-START-02** — the composition stays in `Services/TranslationChains`; the ctor names
  `TranslationChains` and `TranslationCacheStore`, never `ProviderGates`.

### Repo traps

- **`ChainCompositionTests.cs:320-322` pins the ctor line as text.** It will fail with a message about
  `CachingTranslator`, not about the cache. Update it deliberately (T4). This is the same class of guard as
  TP-START-02's `strays` array: the next change must be a decision, not a convenience.
- **`_readTranslator` and `_readOnceTranslator` are `readonly`** (`MainWindow.xaml.cs:33-34`) and must stay so.
  `_writeTranslator` (`:32`) is not, because the key save reassigns it — that asymmetry is deliberate and is
  pinned.
- **Field-initializer ordering.** `_cacheStore` may be an initializer **only** because it needs nothing else.
  If a later story gives the store a settings-dependent argument (E8 will: `OfflineFallbackEnabled`), it moves
  into the ctor body with the chains. Leave a comment saying so — that is E8's trap, planted here.
- **`_restoringSettings` is not engaged.** No control is added or persisted; every assignment happens before
  `InitializeComponent()` (`:86`) and therefore before any change handler can fire.
- **`ApplySettings()` must not rebuild a chain or a store.** It does not today; keep it that way. A setting that
  needs a rebuild goes through the explicit save-handler pattern (`Translate.cs:242`), never through a change
  handler during a restore (the v0.12.3 bug class).
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. Start LIVE on the game chat, let a few lines translate. Stop. Type one of those exact Russian lines into the
   Translator tab and press Translate: the answer is **instant** and the log shows **no** `tr` line for it. That
   is the epic, by hand.
3. Do the reverse: translate a sentence on the Translator tab, then read-once a screen region containing it — the
   row fills instantly, from the same store (the three-decorator half).
4. With a session's worth of translations accumulated, paste a DeepL key in About and Save. Re-translate one of
   those sentences: still instant. Before this story it cost a fresh request.
5. Close the app; `%AppData%\PWRUHelper\translation-cache.json` holds entries from **both** paths — the LIVE feed's
   and the Translator tab's — in one file.
