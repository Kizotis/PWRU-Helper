# Story E3.S8: Bound the batch-mismatch per-line fallback

Status: **review**

_Epic E3 (C) — Provider chain and the new default endpoint · increment 2 · **Release A.1: E2 and E3 are separate
PRs but ONE release** · the owner's Phase-4 go was given 2026-09-06 (`README.md` § Phase 4)._

> **This story closes a measured amplifier, not a theoretical one.** `analyse…` S6/A11: a batch mismatch on a
> 14-line LIVE tick turns one logical translation into **up to 30 requests inside one tick**. On a connection
> already being throttled that is the behaviour that keeps it throttled. `test-plan.md` grades it **R-09**
> (*"a request storm survives the rebuild"*).
>
> **Its urgency rose after E3.S1 was blocked.** With OQ-A shipped as the default (one request per line, because
> the `\n` batch is unproven), `PerLineCap` and the rate ceiling are the **only** things bounding LIVE fan-out.

## Story

As a player,
I want one bad response to cost one failure,
So that a 14-line tick cannot turn into thirty requests.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E3.S8. Do not weaken._

1. **Given** I5 and §6.3
   **When** a 1:1-contract provider (DeepL, Azure) returns the wrong number of results
   **Then** it is a `BadResponse` and the result is **never padded** — padding once bypassed the fallback and
   poisoned the cache (`DeepLTranslator.cs:49-53`).
2. **Given** a join/split provider (GoogleDict, Edge, GoogleGtx)
   **When** the split count does not match the input count
   **Then** it falls through to per-line **only while `lines.Count <= PerLineCap` (8)**, and is a `BadResponse`
   above that.
3. **Given** the measured amplifier (`analyse…` S6, A11) where a mismatch on a 14-line tick produces up to 30
   requests inside one tick
   **When** the cap lands
   **Then** that tick produces one `BadResponse` instead.

### Carried in from E3.S6 (landed 2026-09-07) — a second shape this cap has to cover

E3.S6 narrowed the `rateLimited` latch to `RateLimited`/`Blocked`, which closed the false
*"(skipped — rate-limited…)"* but left this story a second shape to bound. **A gate that closes the door for a
SOFT reason no longer stops the loop — the gate stops it instead, one line at a time.** A single Timeout,
Network, Unavailable or Unknown is a `SoftCooldown` (`ProviderGate.cs:612`): it blocks the provider for
`SoftCooldownSecs` (5 s) **immediately**, not after three strikes — only `BadResponse` needs three
(`BadResponseStrikesToOpen`). So a timeout on line 3 of 14 does not latch, and lines 4–14 are each offered to the
provider, refused at admission by `HttpProviderCore.Paused` (`HttpProviderCore.cs:390`) and rendered as
*"(translation failed: The translation service is paused after a recent refusal.)"* — the Kind is the gate's own
`LastKind`, so this arrives at the **non-latching** `catch`, not the latch. (Worth passing to **E7.S1**: nothing
*refused* anything when the cause was a timeout, so the row that replaced the false "rate-limited" one is not
true either. The `PausedMessage` constant is `GoogleGtxTranslator.cs:91` and predates E3.S6; the wording is
E7.S1's, the number of times it appears is this story's.)

Two things follow, and both are this story's:
1. It costs **no request** (`Paused` sets `NotSent`), so nothing hammers the endpoint — the volume story is fine.
   What is not fine is **eleven identical placeholder rows in a feed where one sentence would do**, which is
   exactly the shape `PerLineCap` exists to bound. (It read eleven rows before E3.S6 too — the latched sentence
   was simply the *false* one; the count never improved.)
2. Do **not** "fix" it by widening the latch back to "anything the gate refused" — that undoes E3.S6's AC 4 and
   brings the false sentence back. Bound the fan-out; leave the filter alone.

**And the one case the gate does NOT bound: `BadResponse`.** It is the only kind the narrowed catch lets through
that sets *no* window until three **consecutive** strikes, and `ReportSuccess` resets the count
(`ProviderGate.cs:517`). So a body shape that fails intermittently — one line unparseable, the next fine — never
opens the gate and every line of the batch issues a **real** request, where before E3.S6 the loop stopped at the
first one. That is not a new explosion (a per-line fallback whose lines all succeed already costs N requests, and
OQ-A accepts it), but it removes the accidental brake the old latch provided, which is one more reason
`PerLineCap` is this story and not a later one. The mirror case is worth a line too: three unparseable lines
**in a row** now open the 60 s breaker inside a *single* batch, where the old latch could only ever bank one
strike per batch — better detection of a genuinely changed endpoint, but a whole tier goes quiet for a minute on
the strength of one OCR frame.

Cases for both belong in T-testing here, alongside TP-CHN-12.

### One deviation worth a reviewer's eye

`epics.md`'s technical note puts the cap in *"`Services/ChainTranslator.cs` / the join-split providers"*. It
cannot be in the chain: `ChainTranslator` calls `ITranslator.TranslateLinesAsync` and receives a list — it has no
visibility of a *split count* at all, because the join and the split both happen inside the provider. The cap goes
in the join/split providers, once, shared. The chain's only related duty is the one it already has: never pad
what a tier returned.
