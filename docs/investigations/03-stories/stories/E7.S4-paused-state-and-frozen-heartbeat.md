# Story E7.S4: Paused state and a frozen heartbeat on both windows

Status: **review**

_Epic E7 (G) — Degraded-mode UX · increment 6 · **Release B.2** · the owner's Phase-4 go was given 2026-09-06
(`README.md` § Phase 4)._

> **This closes risk R-02, and R-02 is the owner's original complaint wearing its technical name.** *"Zombie
> LIVE indicator. The heartbeat blinks, the loop is paused or dead, the user waits forever. **Today's confirmed
> behaviour through a whole 429 storm.**"* (`analyse-implementation-actuelle.md` §1.5.) A blinking dot over a
> stopped pipe is a lie, and it is the lie the app has been telling for every release so far.
>
> **Half of it is already done, and half of it is not, and the split is exact.** E5.S1 froze the **main window's**
> heartbeat by not advancing `_liveTicks` on a skipped tick — the comment says so:
> *"the ● / ○ heartbeat freezes … the fuller `○  LIVE (paused)` form and **the overlay's own 600 ms blink timer
> are E7.S4's** — this loop does not reach into `CompactOverlay`."* So the main window stops **alternating** but
> still reads `●  LIVE` or `○  LIVE` depending on parity, and **the overlay's `_beat` timer keeps blinking
> regardless**, because it is driven by its own `DispatcherTimer` (`CompactOverlay.xaml.cs:20,47`) and knows
> nothing about the pause.
>
> **And the payoff is the one Sally wrote down:** *"the degraded state costs **less** CPU than the healthy one."*
> Stopping a 600 ms timer is the cheapest UX improvement in this epic.

## Story

As a player,
I want the blinking dot to stop when nothing is being sent,
So that the app stops telling me it is working while it is waiting.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E7.S4. Do not weaken._

1. **Given** UX-DR6 and the confirmed behaviour that the dot keeps blinking through a whole 429 storm
   (`analyse…` §1.5)
   **When** the path is paused (S3 with nothing below serving, S5, S6)
   **Then** `UpdateLiveIndicator` (`CompactOverlay.xaml.cs:77-83`) **freezes on `○`** instead of blinking, and the
   main window's `LiveIndicator` (`MainWindow.xaml:299`) switches from `●  LIVE` to `○  LIVE (paused)`.
2. **Given** the 600 ms heartbeat (`CompactOverlay.xaml.cs:20`)
   **When** the pause begins
   **Then** it **stops**, so the degraded state costs *less* CPU than the healthy one (UX-DR18).
3. **Given** the per-surface table of §2.2
   **When** each of S1–S8 is entered
   **Then** the Translator status line (`MainWindow.xaml:278`), the Screen-OCR status line
   (`MainWindow.xaml:394`), the read-feed header (`MainWindow.xaml:308`) and the overlay status
   (`CompactOverlay.xaml:44`) show exactly the strings of that table, through their existing setters
   (`MainWindow.Translate.cs:106-109`, `MainWindow.Live.cs:157-161`, `:163-175`, `CompactOverlay.xaml.cs:67-72`).
4. **Given** principle 1, "one state, one voice"
   **When** a state is entered
   **Then** the sentence is written **once** into the status line and left there until the next change — never
   repeated per message, never phrased two different ways on two surfaces.
5. **Given** UX-DR17 flow (f) step 4
   **When** the app starts with a persisted pause still active
   **Then** the chip shows it **before the user presses anything** — this is the fix for the owner's original
   "it appears at launch" complaint.

### Completion Notes List

**T1 / T2 / T3 — one decision, two surfaces.** `MainWindow.SetLivePaused(bool)` is the whole of AC 1: it writes
the main window's `○  LIVE (paused)` and **tells** the overlay (`_overlay?.SetPaused`), one way, the way
`SetStatus` already goes. Its input is `ChainPause.AllPaused` — the very answer the LIVE loop skips its tick on
— so the indicator cannot disagree with the loop that owns the tick, S3-with-a-backup keeps blinking (flow
(a).1), and a rate-ceiling wait is invisible to it (E5-a/E5-b). Guarded on the transition, so at 1 Hz it writes
nothing at all while the answer is unchanged (AC 4).

**All three "a second call site re-enabled it" traps are closed.** (1) `UpdateLiveIndicator` returns on
`_paused` before it can advance `_blink`, so all four entry points are covered and not just the timer.
(2) `_beat.Start()` has exactly ONE call site — `SyncBeat`, over the pure `BeatShouldRun(visible, paused)` — and
both `SetPaused` and `IsVisibleChanged` go through it, so toggling compact mode mid-pause cannot restart the
blink; the flag is remembered on the window, and `EnterCompactMode` tells a freshly opened overlay. (3)
`SetLiveUi`'s unconditional `"●  LIVE"` now reads `_livePaused ? LiveIndicatorPaused : LiveIndicatorRunning`,
which also means starting LIVE inside a standing window shows the paused form at once.

**AC 2 is about the timer and is asserted as one**: `BeatRunning` before and after, plus a visibility toggle
while paused that must not restart it. Nothing waits 600 ms (CI-3) — `SyncBeat(bool visible)` takes the
visibility, so the rule is exercised without `Show()`ing an always-on-top window on a build agent.

**T4 — §2.1's S5 and S6 on both surfaces, from one decision.** `ChainPause` now carries `NoNetwork`: every rung
inside a window the gate last recorded for `Network`, computed off the snapshot `BlockedUntil` already reads (no
second `Snapshot()`). The pause **predicate is untouched** — E5.S1's
`A_dead_network_pauses_the_whole_read_chain_with_no_special_case_for_S6` still passes verbatim — because the
flag says which sentence, never whether. Both renderers take it, so the skipped tick and the 1 Hz repaint
choose the same row, and the overlay's is 27 of its 40 characters.

**T4 / AC 4 — the toast arbitration, which E7.S2's review left open.** A toast routed to the overlay now OWNS
