# Story E1.S5: Emit the per-request diagnostic log line

Status: **review**

_Epic E1 (A) — Diagnosable translation pipeline · increment 0 · Release A.0 · ⛔ no production code until the
owner's explicit go._

## Story

As the owner reading a player's pasted error report,
I want one line per failed attempt with the status, the headers that matter and the request cadence,
So that the next P2 incident is a measurement instead of an argument.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E1.S5. Do not weaken._

1. **Given** `TranslationService` logs nothing today
   **When** an attempt ends non-success or exceptional
   **Then** exactly one `Logging.Warn` line is emitted in the shape of `architecture-cible.md` §10.1, carrying
   `provider`, `ep`, `dir`, `attempt=n/m`, `cid`, `status`, `elapsed`, `retry-after`, `ct`, `len`,
   `hdrs=[via/srv/xrl/set-cookie]`, `bytes`, `lines`, `burst60`, `ipv`, and `body` **only** for a non-JSON body
   (de-tagged, whitespace-collapsed, first 120 characters).
2. **Given** a successful attempt
   **When** it completes
   **Then** it is counted into `burst60` but **not** logged line by line (the log is capped at 1 MB with one
   rollover, `Logging.cs:69,95-105`).
3. **Given** I11
   **When** any line is written
   **Then** it contains no user text, no `q=`, no full URL and no API key — asserted by a test that translates a
   recognisable sentence with a recognisable key through the fake handler and greps the produced file.
4. **Given** `LogWriter.Write` (`Logging.cs:85`) writes second-resolution timestamps
   **When** this story lands
   **Then** the timestamp format gains milliseconds, so retry spacing is readable.

## Dev Notes

### Invariants this story must keep

- **I11 is the whole point.** No user text, no `q=`, no full URL, no API key — the log is pasted to Discord **by
  design** (`MainWindow.xaml.cs:312-322`). The negative assertions in T4 are the load-bearing tests of this story;
  if they are weak, the story is worse than not doing it.
- **I2** — the line builder is pure and headless. `Logging` is already UI-free.
- **I16** — the LIVE loop is not touched.

### Rulings and decisions that apply

- Emission moves to **`HttpProviderCore`** in E2.S5 (§7.0: the core calls `gate.TryEnter` before the request and
  `ReportSuccess`/`ReportFailure` after it, **and emits this line**). Write the builder as a function so that move
  is a call-site change, not a rewrite.
- **Gate-transition lines are E2.S6's**, not this story's — one line per *transition*, never per skipped request
  (§10.2). Do not pre-build them.
- What this story buys, stated as the DoD: **"Copy error report" stops being empty for a P2-shaped failure.** Today
  `TranslationService` logs nothing at all, so the About tab's report is empty for exactly the failure players
  report (`analyse…` §5.1 [CONFIRMED-ABSENT]).

### Repo traps

- `Logging` swallows its own errors by design — logging must never be the thing that breaks a feature
  (`Logging.cs:89`, `:104`, `:126`). Keep that property: a failure to build the line must not fail the request.
- The log is capped at **1 MB with one rollover** (`Logging.cs:69,95-105`). That cap is why successes are counted
  and not logged — a chatty success path would evict the evidence.
- Cost: the line is built only on the failure path, so it is off the hot path. Do not compute `burst60`,
  `ipv` or the header set on successes beyond the counter increment (footprint is a product requirement).
- `dotnet test tests/PWRUHelper.Tests` green and headless; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and the
  `tests\**` exclusion (`:18`) intact. **No `.sln`.**

- **T1 — one character in `Logging`** (`Services/Logging.cs:88`): `HH:mm:ss` ⇒ `HH:mm:ss.fff`. Nothing else in
  that file moved — not the facade, not `DirectoryOverride`, not the roll, not the 1 MB cap. TP-LOG-08 pins the
  format with a regex over a real written file.
- **T2 — `Services/RequestLog.cs`**, the story's first option. A static class of functions, **not** a method on a
  provider, because **E2.S5** moves the emission into `HttpProviderCore` and that must be a call-site change:
  `Line` (`:201`) is pure over strings and numbers, and the three `Emit` overloads (`:296`, `:301`, `:305`) are
  the only things that touch `Logging`.
- **The line, rendered** (the shape is in the test as a comment too):
  `tr provider=google-gtx ep=translate.googleapis.com/translate_a/single dir=ru->en attempt=2/3 cid=0054`
  `status=429 elapsed=142ms retry-after=30 ct=text/html len=40 hdrs=[via:"1.1 google" srv:"HTTP server (unknown)"`
  `xrl:- set-cookie:yes] bytes=7 lines=2 burst60=37 ipv=? body="We're sorry..."` — 258 characters, one line,
  printable ASCII only.
- **Field order: AC 1's, not the §10.1 example's.** The two disagree about one field — the example prints `ipv`
  between `len` and `hdrs`, while AC 1, T2's bullet and TP-LOG-04's field list all put it after `burst60`. The
  binding text wins; the field SET is identical either way.
- **I11 is structural before it is asserted**, which is the one thing this story had to get right. Three
  constructions, each of which makes a whole class of leak unrepresentable rather than merely untested:
  1. **`Call` (`:92`) holds no address and no text** — only host + path, a byte count and a line count. The
     endpoint is reduced by `Endpoint` (`:234`) at construction, so the query never enters the record the line is
     rendered from and no future change to the format can start printing it.
  2. **`BodyHead` (`:253`) is the only door a body can walk through, and it takes markup only** — §4.3 step 2
     alone (`LooksLikeHtml(resp: null, …)`, deliberately skipping step 1's content-type half). The wider §4.3
     rule would log a body a proxy had relabelled `text/plain`; that body is the provider's own JSON, and the
     provider's JSON **contains the user's sentence and its translation**. Markup is the server's page and
     nobody's sentence.
  3. **`FirstEcho` (`:277`)** cuts the head at the first `q=`, `://` or `%XX` — the other way user text reaches a
     server page: an interstitial that quotes the URL it refused. Google's own `/sorry/` page does not, but "the
     page we have seen does not" is not a rule, and I11 has to hold for the page nobody has captured yet. Four
     cases pin it, including the false-positive guard (`100% of requests` is prose, not an escape).
  Every value that reaches the line then passes `Ascii` (`:331`): bounded, printable ASCII, no quote, no
  backslash — so one server header cannot split one event into two lines or end the `body="…"` field early.
- **`cid` (`:70`)** is an interlocked 16-bit counter rendered as four hex characters, not a Guid: cheaper, and
  monotonic, which is what makes two interleaved calls readable in one file. Generated once per `RequestAsync`
  and shared by all three attempts — TP-RET-08's shape is already visible in
  `TP_LOG_04_a_429_logs_one_line_per_attempt_under_a_single_correlation_id` (one cid, `1/3` `2/3` `3/3`).
- **`burst60`** is `BurstCounter` (`:366`), a lock plus a queue of caller-supplied timestamps (IS-6-shaped, so a
  test needs no wall clock and E2's injected clock can drive it later), self-trimming, capped at 4096 entries so
  a pathological minute cannot grow memory. `RequestLog.Burst` is the shared instance; a test that wants exact
  numbers builds its own. **A successful request pays for this increment and for nothing else** — no header set,
  no body read, no line (`TranslationService.cs:187`).
- **`ipv=?` — a recorded gap, not an oversight.** `HttpClient` does not expose the socket on this path, and the
  only cheap way in is a `ConnectCallback` on the **production** handler: a hot-path change to
  `CreatePooledHandler` that this story is not scoped to make and that a footprint requirement should not absorb
  casually. §10.1's own instruction for that case is to log `?` rather than guess, and the constant
  (`UnknownAddressFamily`, `:54`) plus `Line`'s parameter are already in place. **E2.S5 owns the handler and is
  where the real value arrives.** TP-LOG-04 asserts `ipv=?` so the gap is visible rather than forgotten.
- **T3 — four emission points, all of §5.2's**: the HTML-200 sniff throw (`TranslationService.cs:213`), the
  non-success branch **before the throw decisions** (`:261`), the transport catch (`:289`) and the parse failure
  below the loop (`:347`). Success is the fifth insertion point and is the counter increment at `:187`.
- **The error body is now read — for the log, and not for the classification.** E1.S4 left the non-success branch
  body-less and named this story as the one that would read it. It does (`SafeBodyAsync`, `:320`, which swallows
  its own errors), but the body is **not** fed back into `Classify`: the `kind` on that branch is byte-for-byte
  what E1.S4 shipped. Two reasons, and the second is the decisive one. (i) Feeding it in would move a 400/404
  carrying an HTML body from `Unknown` to `Blocked` — defensible, but a Kind change this story was not asked to
  make. (ii) It would not even produce the field: on the measured 429 row 4 answers **before** row 11, so
  `Classify`'s `htmlHead` is `null` for exactly the shape §10.1's example shows a `body=` for. The log therefore
  computes its own head through E1.S4's two `internal` helpers. **E2.S5's `HttpProviderCore` is where the two
  become one read.**
- **The parse-failure line is honest about what it does not know** (`:347`). Its response object is gone by then,
  so it carries the status that was kept and the payload size, and `-` for every header-derived field — because
  §10.1 forbids paying for the header set on the success path, which is what that response still was. Four
  locals (`okStatus`, `okAttempt`, `okBurst`, `okStarted`) carry it out of the loop rather than re-deriving it.
- **`TranslationPolicy.MaxAttemptsToday` now IS the loop's bound** (`TranslationService.cs:179`), replacing the
  `attempt < 3` literal, and its comment was updated to say so. **Recorded as a deviation** — the story did not
  ask for it. The reason is narrow: `attempt=n/m` renders `m`, and an `m` that can drift from the loop's own
  bound is a log that lies. Same value, same behaviour; `TranslationPolicyTests` is green unchanged.
- **DeepL is left to E2.S5, as the task's second branch allows.** Routing it through the same helper is not one
  line: a different endpoint, a POST form instead of a query, one attempt instead of three, and a key on the
