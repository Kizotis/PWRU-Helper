# Story E1.S5: Emit the per-request diagnostic log line

Status: **ready-for-dev (Phase 4 — owner's go required)**

_Epic E1 (A) — Diagnosable translation pipeline · increment 0 · Release A.0 · ⛔ no production code until the
owner's explicit go._

## Story

As the owner reading a player's pasted error report,
I want one line per failed attempt with the status, the headers that matter and the request cadence,
So that the next P2 incident is a measurement instead of an argument.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E1.S5. Do not weaken._

1. **Given** `TranslationService` logs nothing today
   **When** an attempt ends non-success or exceptional
   **Then** exactly one `Logging.Warn` line is emitted in the shape of `architecture-cible.md` §10.1, carrying
   `provider`, `ep`, `dir`, `attempt=n/m`, `cid`, `status`, `elapsed`, `retry-after`, `ct`, `len`,
   `hdrs=[via/srv/xrl/set-cookie]`, `bytes`, `lines`, `burst60`, `ipv`, and `body` **only** for a non-JSON body
   (de-tagged, whitespace-collapsed, first 120 characters).
2. **Given** a successful attempt
   **When** it completes
   **Then** it is counted into `burst60` but **not** logged line by line (the log is capped at 1 MB with one
   rollover, `Logging.cs:69,95-105`).
3. **Given** I11
   **When** any line is written
   **Then** it contains no user text, no `q=`, no full URL and no API key — asserted by a test that translates a
   recognisable sentence with a recognisable key through the fake handler and greps the produced file.
4. **Given** `LogWriter.Write` (`Logging.cs:85`) writes second-resolution timestamps
   **When** this story lands
   **Then** the timestamp format gains milliseconds, so retry spacing is readable.

        change to `Logging`; the facade, the override, the roll and the 1 MB cap stay exactly as they are.
  - [ ] **TP-LOG-08** — a regex case asserting the format carries `.fff`.
- [ ] **T2 — The line builder** (AC: 1)
  - [ ] Build the §10.1 line as a pure `internal static` helper so it is testable without HTTP. Put it beside the
        emitter (a small `Services/RequestLog.cs`, or a region of `ProviderErrorMapper`'s file if the reviewer
        prefers fewer files — state the choice in the PR; **E2.S5 moves the emission into `HttpProviderCore`**, so
        keep it a function, not a method on the provider).
  - [ ] Fields, in the §10.1 order: `provider`, `ep` (**host + path only, never the query**), `dir` (e.g. `ru->en`),
        `attempt=n/m`, `cid`, `status`, `elapsed`, `retry-after`, `ct`, `len`,
        `hdrs=[via:… srv:… xrl:… set-cookie:yes|no]`, `bytes`, `lines`, `burst60`, `ipv`, and `body` **only** for a
        non-JSON body.
  - [ ] `cid` — a short correlation id shared by **both attempts of one logical call** (TP-RET-08 later asserts it).
        Generate it once per logical call and thread it through the retry loop.
  - [ ] `burst60` — a rolling count of requests issued in the trailing 60 s, **incremented by successes too**
        (AC 2). A small static ring/queue of timestamps; it must be cheap and lock-safe.
  - [ ] `ipv` — the address family actually used (`4` or `6`). From `mecanismes…` Q4: correctly-built rate limiters
        bucket IPv6 by prefix, so a dual-stack machine silently switching families looks like a block that "cleared
        itself". If the family cannot be obtained cheaply on this path, log `ipv=?` rather than guessing — and say
        so in the PR.
  - [ ] `body` — the de-tagged, whitespace-collapsed, **first 120 characters** produced by **E1.S4**. Never for a
        JSON body.
- [ ] **T3 — Emit it from the existing retry loop** (AC: 1, 2)
  - [ ] `Services/TranslationService.cs:132-153` (the non-success branches) and `:172-177` (the parse failure) —
        one `Logging.Warn` per **non-success or exceptional attempt**. Exactly one: a 429 retried three times
        today produces three lines, each with the same `cid` and `attempt=1/3`, `2/3`, `3/3`.
  - [ ] Successes: **no line**. Count into `burst60` only. A 1 MB cap with one rollover is the reason
        (`Logging.cs:69,95-105`).
  - [ ] Keep `provider` honest: this endpoint is `gtx` today. Use the id it will keep — `google-gtx`
        (`ProviderIds`, E2.S2) — so the field is stable across the rename in E3.S6.
  - [ ] DeepL: this story's scope is `TranslationService`, per `epics.md`'s technical note. If routing DeepL
        through the same helper is one line, do it and say so; if it is not, leave it to **E2.S5**, which moves both
        providers onto `HttpProviderCore`.
- [ ] **T4 — The I11 negative assertion — the load-bearing test** (AC: 3)
  - [ ] **TP-LOG-01** — translate a distinctive sentinel sentence that fails; the sentinel appears **nowhere** in
        the produced file.
  - [ ] **TP-LOG-02** — the line contains the host+path (`translate.googleapis.com/translate_a/single`) but **no

  - [ ] **TP-LOG-03** — with a recognisable DeepL key set and sent, the key value appears neither in the log nor

  - [ ] **TP-LOG-04** — the field set is complete for a 429. **TP-LOG-05** — `body=` present for the HTML fixture,
        de-tagged, ≤ 120 chars; absent for a JSON error. **TP-LOG-06** — 50 successful requests produce **zero**

  - [ ] All of it through `Logging.DirectoryOverride` (`Logging.cs:31-39`), the discipline

## Dev Notes

### Invariants this story must keep

- **I11 is the whole point.** No user text, no `q=`, no full URL, no API key — the log is pasted to Discord **by
  design** (`MainWindow.xaml.cs:312-322`). The negative assertions in T4 are the load-bearing tests of this story;
  if they are weak, the story is worse than not doing it.
- **I2** — the line builder is pure and headless. `Logging` is already UI-free.
- **I16** — the LIVE loop is not touched.

### Rulings and decisions that apply

- Emission moves to **`HttpProviderCore`** in E2.S5 (§7.0: the core calls `gate.TryEnter` before the request and
  `ReportSuccess`/`ReportFailure` after it, **and emits this line**). Write the builder as a function so that move
  is a call-site change, not a rewrite.
- **Gate-transition lines are E2.S6's**, not this story's — one line per *transition*, never per skipped request
  (§10.2). Do not pre-build them.
- What this story buys, stated as the DoD: **"Copy error report" stops being empty for a P2-shaped failure.** Today
  `TranslationService` logs nothing at all, so the About tab's report is empty for exactly the failure players
  report (`analyse…` §5.1 [CONFIRMED-ABSENT]).

### Repo traps

- `Logging` swallows its own errors by design — logging must never be the thing that breaks a feature
  (`Logging.cs:89`, `:104`, `:126`). Keep that property: a failure to build the line must not fail the request.
- The log is capped at **1 MB with one rollover** (`Logging.cs:69,95-105`). That cap is why successes are counted
  and not logged — a chatty success path would evict the evidence.
- Cost: the line is built only on the failure path, so it is off the hot path. Do not compute `burst60`,
  `ipv` or the header set on successes beyond the counter increment (footprint is a product requirement).
- `dotnet test tests/PWRUHelper.Tests` green and headless; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and the
  `tests\**` exclusion (`:18`) intact. **No `.sln`.**

## How to verify manually

Disconnect the network, translate from the Translator tab, then About → **Copy error report** and paste into a text
editor. You must see one `[WARN] tr provider=google-gtx …` line per attempt, with millisecond timestamps, a status
or transport reason, and `burst60`. **Read the paste and confirm your own typed sentence is not in it, and that no
`q=` and no key appear.** That reading is the manual half of I11.
