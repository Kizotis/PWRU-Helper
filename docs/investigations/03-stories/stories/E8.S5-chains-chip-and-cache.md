# Story E8.S5: Last tier of both chains, the `● Offline` chip, and the cache drop rule ⛔ Phase 4 (prototype branch)

Status: **done · ⛔ Phase 4 · prototype branch only — merges only on E8.S7's go**

_Epic E8 (H) — Offline fallback prototype · increment 7 · **Release C** · prototype branch, merges only on a go._

> **This is the wiring story, and almost all of it has already been written by other epics.** Two commented
> slots wait in the tier lists; the chip already knows the state; the cache already drops `"p":"bergamot"`
> entries; `ProviderNames` already answers **"Offline engine"** / **"Offline"**. What is missing is the four
> lines that connect them — and one real gap: `TranslationCacheStore.Store` is handed a provider id today and
> **every caller passes nothing**, so the `"p"` field is written empty and the drop rule has nothing to match on.
>
> **The scope discipline that makes this a small story.** It touches `TranslationChains`, `CachingTranslator`
> and the cache store's construction. It does **not** touch the provider (E8.S2), the store on disk (E8.S3) or
> the lifetime (E8.S4). Any change to `ChainTranslator` itself is out of scope — the chain algorithm does not
> know Bergamot exists, and that is the design working.

## Story

As a player whose engines are all paused,
I want the offline engine to be the last thing the app tries, and the chip to say so,
So that the feed keeps moving and I can see why.

### The `"p"` field is empty today, and that is the one real gap

The drop rule, the log's provider column and E7's chip all read a producing-provider id. Two of the three get it
from `ChainTranslator.LastOutcome`. The **cache** does not: `CachingTranslator.Store` (`:131`) calls
`_store.Store(key, value)` with no id, so every entry on every user's disk right now has `"p": ""`.

That is harmless while Bergamot does not exist — `""` never equals `"bergamot"`, so the drop rule is a no-op and
`TranslationCacheStore.cs:178` says so out loud (*"in A.2 it is structurally false and every `"p":"bergamot"`
entry is dropped on load"*). The moment the offline tier can answer, an empty `"p"` becomes a **silent
correctness bug**: offline output would be cached indistinguishably from Google's and served forever after the
user pressed `Remove`. That is precisely the complaint §8.2 concern #2 was written to bound —
*"I turned the offline engine off and it is still giving me its answers"*.

**So T3 is not a nice-to-have and it is not Bergamot-specific.** It is the field the schema has carried since
E4.S2 finally being written.

### Repo traps

- **`ChainTranslator.Of` throws on a duplicate id** (`:203-207`) — two tiers sharing one gate would be "a
  fallback that structurally cannot be one". If a test builds a chain with Bergamot twice, that throw is the
  design working.
- **The chip takes the *preferred* paused tier, not the first in chain order** — E7.S3's review fixed exactly
  that bug (`MainWindow.PreferredPause`). A new **last** tier changes what "below the serving tier" means;
  re-run `ProviderChipTests` and read its review note before assuming it still holds.
- **The cache is provider-agnostic on purpose** (ruling **E4-a**): a DeepL translation can be served to the read
  path, and that is accepted because I8 is about *requests*. Do not "fix" it while adding the `"p"` field.
- **`TranslationChains.Cache` is built on demand under a lock** (`:78-80`) and pins its path on first use. A
  test that lets the production instance resolve a `TempCache` path leaves every later case writing into a
  directory that no longer exists — `ResetCacheForTests`'s doc (`:94-106`) is explicit about it.
- **Two non-parallel collections** (`WPF`, `Gates` — CI-5). Cache tests that touch `ProviderGates` belong in
  `Gates`.

## Size, dependencies, risk

**Size:** **M** — small in the chains, real in the cache · **Depends on:** **E8.S2** (a provider to construct)
and **E8.S3** (`IsInstalled`, and the setting's writers) · **Blocks:** nothing; E8.S6 and E8.S7 are packaging
and measurement ·
**Risk:** **medium, and it is concentrated in one place.** The tier append is four lines and pinned by an
existing permutation sweep. The `"p"` field is the part that can go wrong quietly: read `LastOutcome` twice and
two concurrent calls stamp each other's provider onto each other's entries — a wrong `"p"` is invisible until
someone presses `Remove` and keeps getting offline answers ·
**DoD:** with the engine installed and the network disabled, both chains reach it, the chip says `● Offline`,
new entries carry `"p":"bergamot"`, and after `Remove` those entries are gone from the next session's cache.

## How to verify manually

1. Engine not installed: the About "Chain" line and the tooltip both show
   `… → Google (backup) → Offline engine (not installed)`; no bergamot tier exists (AC 6).
2. Install it, disable the network, translate: the chip reads `● Offline engine` (teal), the Translator status
   line reads `Translated on your PC (offline engine).`, and the compact overlay shows `● Offline` (AC 4).
3. Open `%AppData%\PWRUHelper\translation-cache.json`: the new entry carries `"p":"bergamot"` — and older
   entries from this session carry their real producer's id, not `""` (AC 5, and case 7).
4. Press **Remove**, restart, translate the same line: it is **re-translated** by an online tier; the offline
   entry did not survive the load (AC 5, TP-CACHE-05).
5. Re-enable the network with the engine installed: the chain goes back up, the chip returns to `● Google`, and
   §3.5's `Back on {P}.` shows once.

contradicts the setting, which is the "post-paint correction refreshes" half of the ruling. I10 holds: the
predicate reads a bool field, and a test asserts the builders ask it once per build and not at all when the
setting already answers.

**Single instance (E8.S4's review pin).** The builders receive `MainWindow._offlineEngine`; `TranslationChains`
