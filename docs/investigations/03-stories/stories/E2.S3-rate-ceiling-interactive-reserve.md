# Story E2.S3: Rate ceiling with an interactive-priority reserve

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E2 (B) — Provider gate · increment 1 · **Release A.1: E2 and E3 are separate PRs but ONE release** · the
owner's Phase-4 go was given 2026-09-06 ("go pour la Phase 4, ne t'arrête pas", `README.md` § Phase 4)._

> **Release rule, non-negotiable.** This epic must not reach users without Epic 3. A rate ceiling and a breaker in
> front of `client=gtx` — which 429s on request #1 from an affected connection — is an app that is correctly paused
> all the time (`architecture-cible.md` R7, owner's decision 2).

## Story

As a player typing a reply while LIVE is running,
I want my Enter key to be served,
So that a background loop cannot spend the whole budget on the feature I am not looking at.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E2.S3. Do not weaken._

1. **Given** the token bucket of §5.4 — capacity 2, one token per `MinSpacingMs` (500 ms)
   **When** `TryEnter` finds the bucket empty
   **Then** it returns `Wait(t)` where `t` is the time to the next token, and it is consulted **before** the
   request, never after.
2. **Given** a `Background` caller (LIVE, read-once)
   **When** exactly one token remains
   **Then** it is **refused that token** — one token of the capacity-2 bucket is reserved for `Interactive`.
3. **Given** a `Background` caller finds the gate probe-eligible
   **When** it would take the probe
   **Then** it defers once by `ProbeDeferMs` (1 s), so a user pressing Enter inside that second gets the probe
   instead.
4. **Given** a `Wait(t)` with `t > MaxSpacingWaitMs` (2 s)
   **When** the caller is a chain
   **Then** the tier is treated as unavailable and the chain moves on rather than waiting.

## Tasks / Subtasks

- [ ] **T1 — The four §5.4 constants into `Services/TranslationPolicy.cs`** (AC: 1–4)
  - [ ] `MinSpacingMs = 500`, `BucketCapacity = 2`, `MaxSpacingWaitMs = 2000`, `ProbeDeferMs = 1000`.
  - [ ] Each carries **exactly one** evidence grade or
        `TranslationPolicyTests.Every_member_carries_exactly_one_evidence_grade`
        (`tests/PWRUHelper.Tests/TranslationPolicyTests.cs:49`) fails. All four are
        **[ASSUMED, from the ecosystem's converged 500 ms]** (`mecanismes-de-blocage-google.md` Q2) — the same
        grade §5.6 gives them. That test scans the declaration line plus the comment block directly above it, so
        a grade on either reads.
  - [ ] `TranslationPolicyTests.The_numbers_are_the_ones_the_code_uses_today` (`:82-89`) asserts **only** today's
        five values and its comment says the §5.6 targets are "deliberately absent until the code that reads them
        exists". Adding four members does not break it — do not weaken it, and do not add the new four to it
        (E2.S7 is what tunes them; a literal pin there would make a tuning commit rewrite the suite).
- [ ] **T2 — The token bucket, inside `ProviderGate`** (AC: 1) — `Services/ProviderGate.cs`, created by E2.S1
  - [ ] Continuous refill computed from the injected clock, not a timer: keep `tokens` (a `double`) and
        `tokensAt`, and on each `TryEnter` add `(now − tokensAt) / MinSpacingMs`, clamped at `BucketCapacity`.
        **No `Timer`, no `Task.Delay`, no background thread** — a bucket that refills lazily on read is exact and
        costs nothing while nobody is asking.
  - [ ] `Wait(t)` where `t` is the time to the **next token the caller is allowed to take** (see T3): for
        `Interactive` that is the time to `tokens >= 1`, for `Background` the time to `tokens >= 2`. A `Wait`
        computed against the wrong threshold would tell a `Background` caller to come back 500 ms too early and
        it would be refused again — the same request, twice, which is the behaviour this epic exists to remove.
  - [ ] **Consulted before the request, never after** (AC 1). `TryEnter` is the only consumer; a token is spent
        **only** when the decision returned is `Allow` or `Probe`. `Wait` and `Open` spend nothing — no request
        is made on those paths, so no budget may be charged for one.
  - [ ] The bucket lives beside the breaker state under the **same single `lock`** E2.S1 introduced. §5.2: "the
        ceiling is independent of the breaker: a closed gate can still answer `Wait`" — independent in *rule*,
        not in *lock*. Two locks would let a caller be admitted by the breaker and refused by the bucket with the
        probe latch already taken.
  - [ ] Footprint: `TryEnter` is on the hot path of every request. Arithmetic and one lock; no allocation beyond
        the decision value, no logging (E2.S6 logs **transitions**, and a `Wait` is not one).
- [ ] **T3 — The `Interactive` reserve** (AC: 2) — "one enum and two `if`s, not a scheduler" (§5.4)
  - [ ] `Background` requires `tokens >= 2`; `Interactive` requires `tokens >= 1`. With `BucketCapacity = 2`
        that is exactly §5.4's rule: `Background` "may draw the bucket down but may not take the last token".
        Write it as `tokens >= (priority == RequestPriority.Background ? 2 : 1)` and not as a hard-coded 2, so
        E2.S7 can move `BucketCapacity` without silently deleting the reserve.
  - [ ] `RequestPriority` was defined by **E2.S1** in this same file. This story only reads it.
  - [ ] **Ruling OQ-a (binding): read-once is `Interactive`** — "it is a user click". LIVE is `Background`. The
        enum has no third value and this story must not add one. The **call sites** are not wired here: a
        provider never touches a gate directly, `HttpProviderCore` (**E2.S5**) passes the priority, and who
        passes what is settled in E3.S7 (chain composition) and E5.S4 (read-once).
- [ ] **T4 — The probe defer** (AC: 3) — the second half of the architect's concern #1
  - [ ] A `Background` caller that finds the gate probe-eligible is answered
        `Open(probeEligibleAt + ProbeDeferMs)` until that instant; at or after it, `Background` may take the
        probe like anyone else. `Interactive` is never deferred.
  - [ ] **Latch the instant, not the caller.** Record `probeEligibleAt` (= the `blockedUntil` that expired) and
        derive the defer window from it. A per-caller "has deferred once" flag is untestable on a fake clock and
        would let two `Background` callers each defer once and then both race for the probe. The window is
        deterministic: before `probeEligibleAt + 1 s` no `Background` caller gets the probe; after it, the first
        caller of any priority does.
  - [ ] **Ruling OQ-b (binding): the probe consumes a rate-ceiling token** — "it is a real request; one rule, no
        special case." E2.S1 left the seam; wire it here.
  - [ ] **Edge case the AC does not state and the dev must get right: a probe that cannot afford a token must not
        burn the probe latch.** If the caller is probe-eligible but the bucket refuses it, return `Wait(t)` and
        leave the gate half-open-eligible — do **not** hand out `Probe` and do **not** mark the probe as taken.
        Otherwise the one probe of a 30-minute window is spent by a caller that never sent a request, and the
        gate stays open for another full window with nothing outstanding. That is R-01 (permanently paused app),
        arrived at by the back door. Order inside `TryEnter`: breaker verdict → priority/defer verdict → bucket
        verdict → **then** take the token and the latch together, or take neither.
- [ ] **T5 — `MaxSpacingWaitMs` is the CALLER's rule, and it stops at the constant here** (AC: 4)
  - [ ] AC 4 is about what `ChainTranslator` does with a `Wait` — "the tier is treated as unavailable and the
        chain moves on rather than waiting". `ChainTranslator` does not exist yet (**E3.S3**); the LIVE loop's
        own back-off is **E5.S1**.
  - [ ] This story therefore lands **the constant and the shape of the decision** (`Wait` carries a `TimeSpan` a
        caller can compare) and nothing else. **`TryEnter` must never block, never sleep, never take a
        `CancellationToken` and never return a `Task`.** A gate that waits for you is the scheduler §5.4
        explicitly refuses to build.
  - [ ] If a one-line pure helper reads better than repeating the comparison in E3.S3 and E5.S1, add
        `internal static bool WorthWaiting(TimeSpan t) => t <= TimeSpan.FromMilliseconds(TranslationPolicy.MaxSpacingWaitMs);`
        and give it a case. Rule of Three says do not build more than that.
- [ ] **T6 — `Snapshot()` is unchanged** (R-2 / OQ-c)
  - [ ] The bucket does **not** appear in `GateSnapshot`. R-2 fixes it as `{State, BlockedUntil, Strikes,
        LastKind}` and E7.S2/E7.S3 render exactly those. A `Wait` is a sub-second delay nobody can read at 1 Hz.
  - [ ] `Snapshot()` must stay side-effect free: it may **not** refill the bucket by advancing `tokensAt`, take
        a token, or resolve the probe defer. A 1 Hz poll that quietly refills the bucket would make the ceiling
        depend on whether the About tab is open.
  - [ ] **Still no event, delegate or `INotifyPropertyChanged` out of `Services/`** (sprint-plan note 1).
- [ ] **T7 — Tests, all on the fake clock** (AC: 1–4)
  - [ ] **TP-GATE-16** — capacity 2, refill 1 per 500 ms: two immediate `TryEnter(Interactive)` are `Allow`, the
        third is `Wait(t)` with `t <= 500 ms`; advance the clock 500 ms and the next is `Allow`.
  - [ ] **TP-GATE-17** (the AC-2 pin) — bucket at 1 token: `TryEnter(Background)` ⇒ `Wait`;
        `TryEnter(Interactive)` ⇒ `Allow`. Assert the pair in that order in one case, so a regression that drops
        the reserve cannot pass by making both `Allow`.
  - [ ] **TP-GATE-18** — probe preference: an open gate whose `blockedUntil` has just passed answers a
        `Background` caller `Open(probeEligibleAt + 1 s)`; an `Interactive` caller inside that second gets
        `Probe`; with no `Interactive` caller, a `Background` caller at `probeEligibleAt + 1 s` gets `Probe`.
  - [ ] **The T4 edge case gets its own case:** probe-eligible + empty bucket ⇒ `Wait`, and the probe is still
        available to the next caller once a token refills. This is the one assertion that stops R-01 by the back
        door and it exists in no TP row — name it in the PR.
  - [ ] A `Wait` and an `Open` **spend no token**: drive 50 `TryEnter` against an open gate, then close it and
        assert the bucket is still full.
  - [ ] **No `Task.Delay` in a gate test, ever** (CI-3). Every refill, every defer window, every `Wait` bound
        drives E2.S1's injected `Func<DateTimeOffset>`.
  - [ ] Cases join the non-parallel `Gates` collection **E2.S2** defines (IS-5) if they go through
        `ProviderGates`; a directly-constructed `ProviderGate` holds no static state and may stay outside.

## Dev Notes

### What this story changes in a file that already exists

`Services/ProviderGate.cs` is created by **E2.S1** and is the only production file this story modifies besides
`TranslationPolicy.cs`. Read it before touching it and record, in the PR:

- **Current state** — the breaker: `strikes`, `blockedUntil`, `lastKind`, `lastAt`, `cleanSince`, the consecutive
  `BadResponse` count, the half-open latch, one `lock`, one injected `Func<DateTimeOffset>`, and
  `TryEnter(RequestPriority)` / `ReportSuccess()` / `ReportFailure(kind, retryAfter)` / `Snapshot()`.
- **What this story changes** — `TryEnter` only: it gains a bucket verdict after the breaker verdict, and the
  probe grant gains a priority-dependent defer and a token charge.
- **What must be preserved** — every §5.3 row E2.S1 landed (TP-GATE-01…15), `Cancelled` never touching the gate,
  the whole-state snapshot equality of TP-GATE-12 (**if the bucket becomes part of that snapshot's identity,
  TP-GATE-12 has to keep passing — `Cancelled` must not refill or charge the bucket either**), and `Snapshot()`
  staying side-effect free.

### Invariants this story must keep

- **I2** — `ProviderGate` stays in `Services/`, UI-free and headless-testable. No WPF type, no `DispatcherTimer`,
  no event.
- **I3** — nothing here catches an `OperationCanceledException`. `TryEnter` is synchronous and takes no token;
  there is no OCE to filter. The **OCE trap** (an `HttpClient` timeout is a `TaskCanceledException` whose token is
  *not* cancelled) applies to **E2.S5**, which owns the one transport catch — this story must not pre-empt it.
- **I9** — the gate holds no static state; instances come from `ProviderGates` (E2.S2). **The bucket is part of
  the persisted-state question and the answer is no:** §5.7's schema has no token field, and it must not gain one.
  A bucket restored from a file written 40 minutes ago is either full (so restoring it was pointless) or a
  fabricated debt. E2.S4 persists the breaker; the bucket starts full in every process.
- **I10** — no disk, no network, no startup path. Pure arithmetic over the injected clock.
- **I11** — this story produces no log line at all.
- **I16** — the LIVE loop is not touched. LIVE becoming a `Background` caller happens at its call site in E3.S7 /
  E5.S1, not here.

### Rulings and decisions that apply — the rulings win over the older documents

- **OQ-b (binding, `README.md` § Architect's rulings):** a half-open probe **does** consume a rate-ceiling token.
  §5.4 does not say so; the ruling does, and it wins. One rule, no special case.
- **OQ-a (binding):** read-once is `Interactive` — it is a user click, not a background loop. It matters to
  **E5.S4**, and to nothing in this file except that the enum keeps exactly two values.
- **R-2 / OQ-c (binding):** poll `Snapshot()` at 1 Hz, no events out of `Services/`. `readiness-report.md` R-2
  proposes `ProviderGates.StateChanged` and asks for it to be added to E2.S1/S2's scope; the architect's ruling
  overrides it (sprint-plan note 1). Nothing in this story reopens that.
- **U9 / E2.S7:** all four constants are [ASSUMED]. Assert **relationships** (the third immediate call waits; the
  reserve refuses `Background` at one token; the defer is one `ProbeDeferMs`), not literals, so a tuned constant
  does not rewrite the suite. Where a literal is unavoidable, say so in a comment so E2.S7 changes it
  deliberately.
- **The architect's concern #1 is the whole story.** A shared gate (I9) is correct, and it is exactly what lets a
  LIVE loop spend the budget and the probe on the feature the user is not looking at, pausing the Translator tab
  — the one-request-per-Enter interaction the user values most. The resolution is deliberately minimal: one enum
  and two `if`s.

### Repo traps

- **No `Task.Delay`, no wall clock, no `Timer`.** CI-3. A bucket implemented with a refill timer is untestable on
  a fake clock, allocates a thread-pool item per gate, and is the opposite of "tiny footprint is a product
  requirement".
- **Do not make `TryEnter` async.** Every caller is inside a provider that is already async; a synchronous
  decision is what lets `HttpProviderCore` (E2.S5) charge the gate before the first `await` without an extra
  state machine.
- **`double` refill and equality.** Compare with `>=` against 1 and 2, never `==`. Clamp at `BucketCapacity`
  before the comparison so a gate idle for an hour cannot bank 7 200 tokens.
- No settings control is touched, so `_restoringSettings` (`MainWindow.xaml.cs:35`, cleared at `:201`) is not
  engaged. Nothing in E2 adds a persisted control; the first story that does is **E6.S3**.
- `InternalsVisibleTo PWRUHelper.Tests` (`PWRUHelper.csproj:28`) and the `tests\**` `DefaultItemExcludes` (`:18`)
  intact. **No `.sln`.** `dotnet test tests/PWRUHelper.Tests` green, headless, default parallelism unchanged.

## How to verify manually

Nothing user-visible changes: no provider consults a gate until **E2.S5**, and no chain reads `MaxSpacingWaitMs`
until **E3.S3**. Verify by running `dotnet test tests/PWRUHelper.Tests` and reading `ProviderGateTests` against
§5.4 line by line: capacity 2, one token per 500 ms, `Background` refused at the last token, the probe deferred
by one second for `Background` only, and a `Wait` never charging the bucket. The first manual verification of the
epic's *behaviour* is E2.S5's DoD (a 429 costs one request in the log); the first verification of *this* story is
at the A.1 release gate — with LIVE running, press Enter in the Translator tab and get an answer.
