# Story E7.S2: The one-per-window 1 Hz countdown

Status: **review**

_Epic E7 (G) — Degraded-mode UX · increment 6 · **Release B.2** · the owner's Phase-4 go was given 2026-09-06
(`README.md` § Phase 4)._

> **Small story, and it goes first.** Every `{t}` in the copy deck, the chip's countdown and the About tab's
> `retries in 0:58` all render through the formatter this story writes — **E7.S1, E7.S3, E7.S4, E7.S5 and E7.S7
> are all downstream of it.** The epic lists E7.S1 as depending on it explicitly.
>
> **A.2 already ships a coarse version of this, deliberately.** `MainWindow.Live.cs`'s paused branch recomputes
> the countdown *inside the skipped tick*, so it steps at most every 5 s (the back-off cap) and **there is no
> timer anywhere** — the code comment says so and names this story: *"E7.S2 replaces exactly this line with the
> 1 Hz poll, §2.4's granularity bands and the repaint guard."* `CountdownText` (`Live.cs:451-455`) is today's
> two-band formatter (`{s} s` under a minute, `{n} min` above); this story replaces it with §2.4's four bands
> **and keeps its two current callers working** (`LivePausedStatus` at `:435`, read-once's paused status).
>
> **And it is a performance story wearing a copy hat.** Principle 5, NFR7: at most one countdown per window,
> ticking at 1 Hz, running **only while something is paused**. The 600 ms heartbeat stays the fastest thing on
> screen — and E7.S4 makes it stop while paused, so *the degraded state costs less CPU than the healthy one.*

## Story

As a player mid-raid,
I want the countdown to be quiet,
So that a status line cannot cost me frames.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E7.S2. Do not weaken._

1. **Given** UX-DR5 / §2.4
   **When** a pause begins
   **Then** **one** `DispatcherTimer` for the whole app starts at **1 Hz**, and it is **stopped** the moment
   nothing is paused — it never runs idle.
2. **Given** the granularity rule
   **When** the remaining time is ≤ 90 s
   **Then** it renders `m:ss` updated every second; above 90 s it renders `about N min` updated only when N
   changes; at the 30-minute cap it renders `about 30 min`; under 5 s it renders `about to retry` rather than
   counting to zero.
3. **Given** the repaint guard
   **When** the timer ticks
   **Then** `.Text` is assigned **only when the rendered string differs from the last one** — so above 90 s that
   is once a minute (UX acceptance hint 7).
4. **Given** the placement rule
   **When** a window is in a paused state
   **Then** **at most one countdown is visible per window** — chip **or** status line, never both showing the
   same clock (UX acceptance hint 2), and **no row ever carries a countdown**.

## §2.4, verbatim — the rules

| Rule | Value |
|---|---|
| Tick rate | **1 Hz**, one `DispatcherTimer` for the whole app |
| Timer lifetime | started when a pause begins, **stopped** when nothing is paused; never runs idle |
| Granularity | `≤ 90 s` → `m:ss`, updated every second · `> 90 s` → `about N min`, updated when N changes · at the 30 min cap → `about 30 min` |
| Repaint guard | assign `.Text` **only when the rendered string differs** from the last one — above 90 s that is once a minute |
| Placement | at most **one** countdown per window (chip **or** status line, never both showing the same clock) |
| Under 5 s | do not show `0:03` counting to zero; show `about to retry` and let the state change do the talking |

## Dev Notes

### Invariants this story must keep

- **I2 — `Services/` never formats a countdown.** The formatter is in `MainWindow.Live.cs`; `Services/` supplies
  **seconds** (`LiveTickPolicy.CountdownSeconds`) and **receives rendered text**
  (`UserMessages.ReadOncePaused(lines, tryAgainIn)`, `:265-268`). Two files already document the split; keep it.
- **NFR7 — repaint budget.** One 1 Hz timer, stopped when idle, one assignment per second at most and only when
  the string changed. §6: *"One text re-measure per second is invisible next to the existing 600 ms heartbeat;
  two of them, or a per-row countdown over 50 feed rows, is not."*
- **I10 — nothing new touches the disk before first paint.** T2's caveat. A `Snapshot()` is *"side-effect free by
  contract: taking a snapshot must never advance a clock, take the probe or spend a rate-ceiling token"*
  (`ProviderGate.cs:75-79`) — but it also does not load the file, and that is the honest limit on TP-START-04.
- **I15** — if the countdown ever becomes a `Run.Text` binding, it is `Mode=OneWay` **and** gains an STA case.
  Prefer a plain `TextBlock.Text` assignment: it is what every surface already uses and it needs no binding at
  all.

### Rulings that apply

- **OQ-c / R-2 — poll at 1 Hz, no events out of `Services/`.** *"Poll at 1 Hz from the countdown timer Sally
  already requires (≤ 1 Hz repaint). No event, `Services/` stays passive."* **This story's timer is that poll**,
  and E7.S3's chip is its consumer. `ProviderGate.Snapshot()` returns the immutable
  `{State, BlockedUntil, Strikes, LastKind}` (`ProviderGate.cs:80-84`); `ProviderGates.All()` returns them all
  (`:311`).
- **E3-a** — a tier is paused when `BlockedUntil > Now()`, **never** when `State == Open` (that state
  deliberately outlives the window). The timer's "is anything still paused?" question uses the **same** rule, or
  it will never stop.
- **E5-a / E5-b** — a rate-ceiling `Wait` is **not** a pause: it sets no `BlockedUntil`, `PauseNow()` cannot see
  it, and the timer must not start for it. `MainWindow.Live.cs`'s comment says it in as many words.

### Repo traps

- **`DispatcherTimer` roots its handler.** `_toastTimer` (`MainWindow.xaml.cs:140`) is the existing one; copy its
  lifecycle, and stop the new one in `OnClosing`.
- **A `DispatcherTimer` does not tick on a background thread and does not tick while a modal is open.** Neither
  matters here (no modals from a background path, NFR12) — noted so nobody adds a `Timer`.
- **`SetScreenStatus` writes BOTH windows** (`Live.cs:195-198`) — main window and the overlay. A countdown
  written through it appears twice by design, on two windows, which is AC 4-compliant (one *per window*).
- **The overlay's own 600 ms heartbeat is a second timer** (`CompactOverlay.xaml.cs:20,47`). It is not this
  story's; **E7.S4 stops it while paused**, which is what makes the degraded state cheaper than the healthy one.
  Do not fold the two timers together — different owners, different rates, different windows.
- **`LivePausedStatus` and `ReadOncePaused` are the two existing consumers of `CountdownText`.** Changing the
  bands changes their expected strings; `LivePauseTests` and `ReadOnceStatusTests` assert them. **Update those
  expectations deliberately, with the reason in a comment** — the precedent is E5.S4 updating
  `ChainCompositionTests.cs:315`.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Size, dependencies, risk

**Size:** S · **Depends on:** **E5.S1** (done — `ChainTranslator.PauseNow()` and `_readChain`, the pause seam the
timer polls) · **Risk:** **low.** The formatter is pure and the timer is fifteen lines. The two real hazards are
(a) a timer that never stops — it must stop *itself*, on a tick, using **E3-a**'s `BlockedUntil > Now()` rule,
because a `State == Open` test would keep it running for ever after the window expires; and (b) `DateTimeOffset.UtcNow`
sneaking in instead of the gates' clock, which E5.S1's review already caught once ·
**DoD:** the formatter has a test per band; the timer is provably stopped when nothing is paused.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. **It is not running when nothing is wrong.** Healthy app, LIVE running: attach a profiler or add a temporary
   tick counter — the countdown timer is **stopped**.
3. **The bands.** Force a 2-minute pause: `about 2 min` … `about 1 min` — **two** repaints in two minutes, not
   120. Then a 60-second pause: `0:58`, `0:57`, … stepping every second, and at `0:04` it becomes
   `about to retry` rather than counting to zero.
4. **It stops.** Let the window expire: the first successful call clears everything and the timer stops on the
   next tick.
5. **One per window.** In the paused state, the main window shows the clock in one place, not two. The compact
   overlay shows it once, in its single status line.
6. **No row has a clock.** Scroll the feed during a pause: pending rows are `…`, nothing counts down in them.

### Completion Notes List

**The bands, as implemented** (`MainWindow.Live.cs:520` — `CountdownText`, unchanged name, file and
null-in/null-out contract, so all four existing `{t}` callers picked them up):

| Seconds in | Renders | Band |
|---|---|---|
| `null` | `null` | nothing honest to count down to |
| `≤ 4` (0 and negatives included) | `about to retry` | §2.4's floor |
| `5 … 90` | `0:05` … `1:30` | `m:ss`, culture-invariant |
| `91 … 1800` | `about 2 min` … `about 30 min` | ceiling, so the number never promises the gate will reopen sooner than it will |
| `> 1800` (`int.MaxValue` included) | `about 30 min` | the display cap, clamped **before** the ceiling arithmetic so `MaxValue + 59` cannot overflow to a negative |

`m:ss` is built from two `ToString(CultureInfo.InvariantCulture)` calls, not a date format — the `:`
of a custom time format is the culture's `TimeSeparator`. Pinned by a hostile-culture test in
`CountdownTests`, the shape E2.S6's review gave `GateLog`.

**The timer** (`MainWindow.xaml.cs:129`, `:577-643`): one `DispatcherTimer` at `1 s`.
`EnsureCountdownRunning(ChainPause)` starts it if it is not running and repaints at once, so the
first paused second is not a second of stale text; it is idempotent, so every pause site may just
call it. The **tick stops the timer** — `PauseNow().AllPaused` is `BlockedUntil > Now()` and never
`State == Open` (ruling E3-a), which is the difference between a timer that stops and one that runs
for ever. `StopLive()` stops it too (NFR7's "never runs idle" at the moment the surface it paints
goes away) and `OnClosing` stops it because a `DispatcherTimer` roots its handler.

**The repaint guard** (AC 3): `MainWindow.SetIfChanged(TextBlock, string)` and
`CompactOverlay.SetStatusIfChanged(string)`, both comparing the control's **own** text rather than a
cached field. Above 90 s that is one assignment a minute on each surface. The guard is asserted
through `ReadLocalValue` rather than by counting change notifications, and the test says why: WPF
drops a dependency-property change whose value is equal, so a bare `Text = same` raises nothing
either and the two implementations would be indistinguishable from the outside — but a local value
is set by an assignment and by nothing else.

**Three deviations / decisions, all deliberate:**

1. **§3.2's under-5 s row is implemented, and it had to be.** `about to retry` is a *clause*, so
   `LivePausedStatus` renders `○ Live — paused, about to retry.` rather than substituting it into
   `next try in {t}`. That string is the deck's own §3.2 row, verbatim — no new wording was invented
   (E7.S1 still owns the wording). The same reasoning produced **`CountdownJoinText`**
   (`Live.cs:543`), which is `CountdownText` plus one question: under the floor it answers `null`, so
   read-once's `Try again in {t}.` and the key test's §3.7 row fall back to their existing
   no-number forms (amendment **A12**: `in {t}` → `shortly`) instead of reading "Try again in about
   to retry." **Neither `Services/` sentence was changed.**
2. **The overlay gets §3.2's short form** (`LivePausedOverlayStatus`, `Live.cs:479`), inside the
   deck's 40-character budget, asserted for every band. `MainWindow` formats and `CompactOverlay`
   renders (I2); the overlay never learns what a countdown is. `SetScreenStatus` still writes the
   long form to both surfaces on the first paused tick — the E5.S1 scan requires that exact call —
   and the tick that `EnsureCountdownRunning` fires in the same dispatch replaces the overlay's copy
   with the short form, so there is no flicker.
3. **The countdown does not start from read-once's paused status**, although T2 lists it as a start
   site. A read-once summary is a *past-tense report of a finished read* on the very same
   `ScreenReadStatus`; stepping a clock over it would be a second clock on one window (AC 4) and
   would overwrite a sentence about something else. `CountdownTick` therefore repaints only while
   `_liveCts != null`. The seconds read-once shows are still this story's bands — it just does not
   tick. **For Winston**, with the flag below.

**Flagged for Winston (carried from the story, now measured):** **TP-START-04's "at first paint" is
still not reachable without breaking I10.** `ProviderGates` constructs its gates at startup and loads
`provider-state.json` on the first `TryEnter`, so a saved pause becomes visible on the first tick
*after* the first request. Nothing in this story reads the file earlier; the reason is written at
`EnsureCountdownRunning`'s doc comment so E7.S3 does not "fix" it.
