# Story E7.S2: The one-per-window 1 Hz countdown

Status: **ready-for-dev (Phase 4 — owner's go given)**

_Epic E7 (G) — Degraded-mode UX · increment 6 · **Release B.2** · the owner's Phase-4 go was given 2026-09-06
(`README.md` § Phase 4)._

> **Small story, and it goes first.** Every `{t}` in the copy deck, the chip's countdown and the About tab's
> `retries in 0:58` all render through the formatter this story writes — **E7.S1, E7.S3, E7.S4, E7.S5 and E7.S7
> are all downstream of it.** The epic lists E7.S1 as depending on it explicitly.
>
> **A.2 already ships a coarse version of this, deliberately.** `MainWindow.Live.cs`'s paused branch recomputes
> the countdown *inside the skipped tick*, so it steps at most every 5 s (the back-off cap) and **there is no
> timer anywhere** — the code comment says so and names this story: *"E7.S2 replaces exactly this line with the
> 1 Hz poll, §2.4's granularity bands and the repaint guard."* `CountdownText` (`Live.cs:451-455`) is today's
> two-band formatter (`{s} s` under a minute, `{n} min` above); this story replaces it with §2.4's four bands
> **and keeps its two current callers working** (`LivePausedStatus` at `:435`, read-once's paused status).
>
> **And it is a performance story wearing a copy hat.** Principle 5, NFR7: at most one countdown per window,
> ticking at 1 Hz, running **only while something is paused**. The 600 ms heartbeat stays the fastest thing on
> screen — and E7.S4 makes it stop while paused, so *the degraded state costs less CPU than the healthy one.*

## Story

As a player mid-raid,
I want the countdown to be quiet,
So that a status line cannot cost me frames.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E7.S2. Do not weaken._

1. **Given** UX-DR5 / §2.4
   **When** a pause begins
   **Then** **one** `DispatcherTimer` for the whole app starts at **1 Hz**, and it is **stopped** the moment
   nothing is paused — it never runs idle.
2. **Given** the granularity rule
   **When** the remaining time is ≤ 90 s
   **Then** it renders `m:ss` updated every second; above 90 s it renders `about N min` updated only when N
   changes; at the 30-minute cap it renders `about 30 min`; under 5 s it renders `about to retry` rather than
   counting to zero.
3. **Given** the repaint guard
   **When** the timer ticks
   **Then** `.Text` is assigned **only when the rendered string differs from the last one** — so above 90 s that
   is once a minute (UX acceptance hint 7).
4. **Given** the placement rule
   **When** a window is in a paused state
   **Then** **at most one countdown is visible per window** — chip **or** status line, never both showing the
   same clock (UX acceptance hint 2), and **no row ever carries a countdown**.

## §2.4, verbatim — the rules

| Rule | Value |
|---|---|
| Tick rate | **1 Hz**, one `DispatcherTimer` for the whole app |
| Timer lifetime | started when a pause begins, **stopped** when nothing is paused; never runs idle |
| Granularity | `≤ 90 s` → `m:ss`, updated every second · `> 90 s` → `about N min`, updated when N changes · at the 30 min cap → `about 30 min` |
| Repaint guard | assign `.Text` **only when the rendered string differs** from the last one — above 90 s that is once a minute |
| Placement | at most **one** countdown per window (chip **or** status line, never both showing the same clock) |
| Under 5 s | do not show `0:03` counting to zero; show `about to retry` and let the state change do the talking |

## Tasks / Subtasks

- [ ] **T1 — The pure formatter (AC 2).** Replace `MainWindow.CountdownText(int? seconds)`
      (`MainWindow.Live.cs:451-455`) with §2.4's four bands. **Keep the name, the file and the null-in/null-out
      contract** — it already has two callers (`LivePausedStatus` `:435-441` and read-once, E5.S4) and its doc
      comment already says *"Shared by the LIVE status above and by read-once's (E5.S4) so the two cannot come to
      disagree about what a countdown looks like."*
  ```
  null            -> null            // nothing honest to count down to
  s <  5          -> "about to retry"
  s <= 90         -> "m:ss"          // 0:58, 1:30
  s <= 30*60      -> "about N min"   // N = ceiling
  otherwise       -> "about 30 min"  // the cap
  ```
  - [ ] **`m:ss` is culture-invariant.** `$"{s / 60}:{s % 60:00}"` or an explicit
        `CultureInfo.InvariantCulture` — E2.S6's review made the gate log culture-invariant for the same reason,
        and a `:` separator from a locale-aware format is a real defect on a Russian-language Windows.
  - [ ] **Static and pure.** It already is; keep it that way — `LivePausedStatus`' doc comment says why
        (*"so the copy can be asserted headlessly"*).
  - [ ] **It stays in the code-behind, not `Services/`** (I2). `UserMessages.cs:169-170` and
        `Live.cs:449-450` both write the reason down: *"a countdown is formatting, which stays out of
        `Services/`."*
  - [ ] **The cap is 30 min but `MaxCountdownSeconds` is 3600** (`LiveTickPolicy.cs:62-66`) — that constant is
        the guard for the `AuthFailed` `MaxValue` sentinel ("beyond an hour a countdown stops being one") and it
        answers **null**, which is a *different* rule from §2.4's 30-minute display cap. Both stay. Do not
        collapse them.
- [ ] **T2 — One `DispatcherTimer`, app-wide (AC 1).** `MainWindow.xaml.cs` owns it, beside `_toastTimer`
      (`:140`).
  - [ ] `Interval = TimeSpan.FromSeconds(1)`.
  - [ ] **Started when a pause begins; stopped the moment nothing is paused.** The truth source is
        `ChainTranslator.PauseNow()` on `_readChain` (`ChainTranslator.cs:305`, returning
        `ChainPause(AllPaused, RetryAt, Now)`) and `ProviderGates.All()` (`ProviderGates.cs:311`) for the
        per-provider windows the chip shows. **The tick itself decides to stop**: if nothing is paused, do a
        final repaint of the healthy text and `Stop()`.
  - [ ] **Who starts it.** Anything that learns of a pause: the LIVE loop's paused branch
        (`MainWindow.Live.cs`), a caught `TranslationException` with a `RetryAt`, read-once's paused status, and
        **first paint** — flow (f).4 / **TP-START-04**: *"a saved open gate ⇒ the chip shows the paused state at
        first paint, with **zero** requests issued."* A `Start()` on an already-running `DispatcherTimer` is a
        no-op, so every site may just call `EnsureCountdownRunning()`.
  - [ ] **I10 — do NOT read `provider-state.json` to make first paint work.** `ProviderGates.Snapshot(id)` and
        `All()` **construct only**; the file loads on the first `TryEnter` (`ProviderGates.cs:166`,
        `ProviderStateStoreTests:815-834`). So at first paint the chip is honest-but-empty until the first
        request. **TP-START-04 is therefore satisfied by the first tick after the first request, not before it**
        — flag it: making it literally true at first paint would mean loading the file before the window is
        visible, which is exactly what I10 forbids and what P1 is about. **For Winston.**
  - [ ] **It must not survive the window.** `Stop()` it in `OnClosing` (`MainWindow.xaml.cs:288+`) beside
        `CancelReadOnce()`. A `DispatcherTimer` roots its handler.
- [ ] **T3 — The repaint guard (AC 3).** A tiny helper, used by **every** countdown surface:
  ```
  private static void SetIfChanged(TextBlock target, string text)
  { if (!string.Equals(target.Text, text, StringComparison.Ordinal)) target.Text = text; }
  ```
  - [ ] **Compare against the control's own `Text`**, not a cached field: one source of truth, and it survives a
        surface being written by something else (which `SetScreenStatus` does — it writes both windows,
        `Live.cs:195-198`).
  - [ ] Above 90 s that is **one assignment a minute**, which is the whole of hint 7 and **TP-RENDER-07**'s
        second half.
- [ ] **T4 — At most one countdown per window (AC 4).** The rule is placement, and it is decided **here** so
      E7.S3 and E7.S4 can obey it rather than negotiate it:
  - [ ] **Main window:** the countdown lives on **the chip** (E7.S3) whenever the chip is visible, and on the
        **status line** otherwise. Never both. §2.2's table shows exactly this: S3 puts `0:58` in the chip and
        the Screen-OCR line, which are **two different windows' worth of surface** — re-read it as *one per
        window*, per hint 2.
  - [ ] **Compact overlay:** the chip is a **prefix of `OverlayStatus`** (`CompactOverlay.xaml:45`), so there is
        structurally one line and therefore one clock. `SetStatus` (`CompactOverlay.xaml.cs:67-72`) receives the
        **formatted string** — `MainWindow` formats, the overlay renders (I2 again, and the epic's technical
        note says it).
  - [ ] **No row ever carries a countdown.** Principle 5, hint 2, **TP-RENDER-06**. Pending rows keep `…`
        (`UserMessages.PendingRetryRow()`, `:231`, whose doc comment already argues it). E7.S6 owns the rows;
        this story owns the prohibition and its test.
- [ ] **T5 — Retire the coarse A.2 countdown.** `MainWindow.Live.cs`'s paused branch currently calls
      `SetScreenStatus(LivePausedStatus(LiveTickPolicy.CountdownSeconds(pause.RetryAt, pause.Now)))` from inside
      the skipped tick. **Keep that call** — it is what makes the *first* paused tick immediate — and let the 1 Hz
      timer take over the stepping. Update the code comment that names this story; leaving it claiming "there is
      no new timer anywhere" would be false the moment this lands.
  - [ ] **`pause.Now`, never `DateTimeOffset.UtcNow`.** `RetryAt` was produced against the **gates'** clock;
        subtracting a different one is the two-clocks bug **IS-6** and `ProviderGate.Now()` exist to prevent
        (E5.S1's review found it). The 1 Hz tick must ask `PauseNow()` (which returns its own `Now`) or read
        `ProviderGates.Clock` — **not** `DateTimeOffset.UtcNow`.
  - [ ] `LiveTickPolicy.CountdownSeconds(retryAt, now)` (`LiveTickPolicy.cs`) stays the seconds source; this
        story only changes the *rendering* and the *cadence*.
- [ ] **T6 — Tests (TP-RENDER-07 + the timer-lifetime assertions).**
- [ ] **T7 — `dotnet test tests/PWRUHelper.Tests`.** Green, headless, **nothing sleeps** (CI-3).

## Dev Notes

### Invariants this story must keep

- **I2 — `Services/` never formats a countdown.** The formatter is in `MainWindow.Live.cs`; `Services/` supplies
  **seconds** (`LiveTickPolicy.CountdownSeconds`) and **receives rendered text**
  (`UserMessages.ReadOncePaused(lines, tryAgainIn)`, `:265-268`). Two files already document the split; keep it.
- **NFR7 — repaint budget.** One 1 Hz timer, stopped when idle, one assignment per second at most and only when
  the string changed. §6: *"One text re-measure per second is invisible next to the existing 600 ms heartbeat;
  two of them, or a per-row countdown over 50 feed rows, is not."*
- **I10 — nothing new touches the disk before first paint.** T2's caveat. A `Snapshot()` is *"side-effect free by
  contract: taking a snapshot must never advance a clock, take the probe or spend a rate-ceiling token"*
  (`ProviderGate.cs:75-79`) — but it also does not load the file, and that is the honest limit on TP-START-04.
- **I15** — if the countdown ever becomes a `Run.Text` binding, it is `Mode=OneWay` **and** gains an STA case.
  Prefer a plain `TextBlock.Text` assignment: it is what every surface already uses and it needs no binding at
  all.

### Rulings that apply

- **OQ-c / R-2 — poll at 1 Hz, no events out of `Services/`.** *"Poll at 1 Hz from the countdown timer Sally
  already requires (≤ 1 Hz repaint). No event, `Services/` stays passive."* **This story's timer is that poll**,
  and E7.S3's chip is its consumer. `ProviderGate.Snapshot()` returns the immutable
  `{State, BlockedUntil, Strikes, LastKind}` (`ProviderGate.cs:80-84`); `ProviderGates.All()` returns them all
  (`:311`).
- **E3-a** — a tier is paused when `BlockedUntil > Now()`, **never** when `State == Open` (that state
  deliberately outlives the window). The timer's "is anything still paused?" question uses the **same** rule, or
  it will never stop.
- **E5-a / E5-b** — a rate-ceiling `Wait` is **not** a pause: it sets no `BlockedUntil`, `PauseNow()` cannot see
  it, and the timer must not start for it. `MainWindow.Live.cs`'s comment says it in as many words.

### Repo traps

- **`DispatcherTimer` roots its handler.** `_toastTimer` (`MainWindow.xaml.cs:140`) is the existing one; copy its
  lifecycle, and stop the new one in `OnClosing`.
- **A `DispatcherTimer` does not tick on a background thread and does not tick while a modal is open.** Neither
  matters here (no modals from a background path, NFR12) — noted so nobody adds a `Timer`.
- **`SetScreenStatus` writes BOTH windows** (`Live.cs:195-198`) — main window and the overlay. A countdown
  written through it appears twice by design, on two windows, which is AC 4-compliant (one *per window*).
- **The overlay's own 600 ms heartbeat is a second timer** (`CompactOverlay.xaml.cs:20,47`). It is not this
  story's; **E7.S4 stops it while paused**, which is what makes the degraded state cheaper than the healthy one.
  Do not fold the two timers together — different owners, different rates, different windows.
- **`LivePausedStatus` and `ReadOncePaused` are the two existing consumers of `CountdownText`.** Changing the
  bands changes their expected strings; `LivePauseTests` and `ReadOnceStatusTests` assert them. **Update those
  expectations deliberately, with the reason in a comment** — the precedent is E5.S4 updating
  `ChainCompositionTests.cs:315`.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## Testing

- **TP-IDs landed:** **TP-RENDER-07** — *"the pure formatter: ≤ 90 s → `m:ss` per second; > 90 s → `about N min`,
  a new string only when N changes; < 5 s → `about to retry`; at the cap → `about 30 min`"* (oracle: string
  sequence; maps `ux` §2.4, **H7**). Also **TP-RENDER-06** (no countdown in a row) — E7.S6 lands the render half;
  land the **source/behaviour** half here, because this is the story that owns the prohibition.
- **The formatter is a pure function of `int?` → `string?`** — one case per band, plus the boundaries: `null`,
  `0`, `4`, `5`, `90`, `91`, `1800`, `1801`, `3599`, `3600`, `3601`. The boundaries are where a band rule is
  actually written down.
- **The repaint guard (AC 3, hint 7):** drive the formatter over a **descending sequence** of seconds and assert
  the number of **distinct** strings — 300 → 240 yields **one** change, not sixty. This is testable without a
  timer and without a window: it is a property of the formatter plus `SetIfChanged`. Assert `SetIfChanged`
  separately with a real `TextBlock` on the STA host, counting assignments.
- **AC 1, the timer lifetime, L3 on the STA host:** it is **not running** on a healthy app; it starts when a
  pause is signalled; it **stops itself** on the first tick where nothing is paused. **Assert the
  `DispatcherTimer.IsEnabled` flag, never by waiting** (CI-3) — drive the tick handler directly.
- **AC 4:** a source/render assert that no feed-template path can receive a countdown string (TP-RENDER-06), and
  that a paused main window shows the clock on **one** of chip / status line.
- **Isolation:** IS-6 (an injected clock — `ProviderGates.Clock`, `ProviderGates.cs:102`) for anything reading
  `BlockedUntil`; **CI-3, absolutely: nothing in this story may sleep.** A countdown test that waits is a
  countdown test that is flaky and slow, and it would be the first one in the suite.
- **Must keep passing unchanged (with deliberate expected-string updates):** `LivePauseTests`
  (`LivePausedStatus`' composed text), `ReadOnceStatusTests` (`ReadOncePaused`'s), `LiveTickPolicyTests`
  (`CountdownSeconds` is untouched — if one of its cases moves, you changed the wrong layer),
  `TemplateRenderTests`.

## Size, dependencies, risk

**Size:** S · **Depends on:** **E5.S1** (done — `ChainTranslator.PauseNow()` and `_readChain`, the pause seam the
timer polls) · **Risk:** **low.** The formatter is pure and the timer is fifteen lines. The two real hazards are
(a) a timer that never stops — it must stop *itself*, on a tick, using **E3-a**'s `BlockedUntil > Now()` rule,
because a `State == Open` test would keep it running for ever after the window expires; and (b) `DateTimeOffset.UtcNow`
sneaking in instead of the gates' clock, which E5.S1's review already caught once ·
**DoD:** the formatter has a test per band; the timer is provably stopped when nothing is paused.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green.
2. **It is not running when nothing is wrong.** Healthy app, LIVE running: attach a profiler or add a temporary
   tick counter — the countdown timer is **stopped**.
3. **The bands.** Force a 2-minute pause: `about 2 min` … `about 1 min` — **two** repaints in two minutes, not
   120. Then a 60-second pause: `0:58`, `0:57`, … stepping every second, and at `0:04` it becomes
   `about to retry` rather than counting to zero.
4. **It stops.** Let the window expire: the first successful call clears everything and the timer stops on the
   next tick.
5. **One per window.** In the paused state, the main window shows the clock in one place, not two. The compact
   overlay shows it once, in its single status line.
6. **No row has a clock.** Scroll the feed during a pause: pending rows are `…`, nothing counts down in them.
