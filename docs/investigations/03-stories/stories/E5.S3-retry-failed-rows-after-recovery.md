# Story E5.S3: Retry failed rows once the providers recover

Status: **done**

_Baseline commit: `8e08b7d`._

_Epic E5 (E) — Honest live translation · increment 4 · **Release A.2 (E4 + E5)** · the owner's Phase-4 go was
given 2026-09-06 (`README.md` § Phase 4)._

> **The riskiest story of Release A.2**, and the reason is not the failure it fixes but the failure it could
> cause: *"a duplicated feed row would be worse than the failure"* (`epics.md`, and flow (a).5 says it twice). A
> row that fails today stays `(Google is limiting…)` for the session — annoying and honest. A row appended twice
> is the app lying about what was said in the game chat.
>
> **It is also where two earlier rulings come home.** **E3-h**: lines beyond `PerLineCap` are marked failed and
> *"re-translated after recovery by E5"* — this story is that promise. **V1.3**: *zero permanently-parenthesised
> rows in a session that recovered* — this story is that validation.
>
> `LiveDedup` is **not touched at all**. §9.3 calls that "the strongest possible guarantee that it cannot swallow
> anything", and it is a task with a `git diff --stat` check attached.

## Story

As a player,
I want a row that failed during a 30-second blip to fill in afterwards,
So that a temporary outage does not permanently burn the messages that arrived during it.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E5.S3. Do not weaken._

1. **Given** `LiveDedup` marks a failed line emitted, so the row is burned for the session (`analyse…` §3.1,
   `LiveDedup.cs:91-97`)
   **When** the §9.3 queue lands
   **Then** it lives in `MainWindow.Live.cs` as
   `List<(OcrResultItem Row, string Body, string Target)> _pendingRetry` and **`LiveDedup` is not touched at
   all** — which is the strongest possible guarantee that it cannot swallow anything.
2. **Given** a failure at `MainWindow.Live.cs:277-283`
   **When** the row is enqueued
   **Then** its `TranslationBody` is set to a value that is deliberately **not** `(`-prefixed, so it reads as
   pending rather than terminal, and so I4 keeps it out of the cache.
3. **Given** the queue's bounds
   **Then** it is bounded at `MaxHistory` (50), oldest dropped; an entry is discarded when its row is no longer in
   `_ocrItems` (the `MaxHistory` trim at `Live.cs:268`); and `StopLive()` clears it.
4. **Given** the first tick after a successful translation
   **When** it runs
   **Then** the queue is drained **before** new lines are processed, in one batch through the same
   `_readTranslator`, so cache hits make most of it free.
5. **Given** a drain that fails
   **When** it is retried
   **Then** the rows go back on the queue, and after `PendingRetryMaxAttempts` (2) they become a terminal `(…)`
   row.
6. **Given** UX-DR17 / flow (a) step 5
   **When** rows are re-translated
   **Then** they are updated **in place**, keeping their position and their 🔑 glossary line — never appended a
   second time.

## Reading AC 4 precisely, because its wording pre-dates E5.S1

*"the first tick after a successful translation"* is written as if a tick could run while everything was paused.
After **E5.S1** it cannot: a tick either is skipped whole (`Paused`) or runs. So the operative reading is:

> **On the first tick that is not skipped, drain the queue before processing new lines.**

That is the same behaviour §8.3's diagram draws (`tick N+k` … "drain the pending-retry queue, reset back-off") and
it is stronger than a "wait for a success first" rule, which would need a successful *new* translation before old
rows could be retried — in a chat that has gone quiet, that success never comes and the rows stay burned. **Drain
first; the drain itself is the success.**

## The two ways this story goes wrong, and the property that stops each

| Failure | What stops it |
|---|---|
| **A duplicated row.** The queue holds the `OcrResultItem` **reference**, not the text, and the drain writes `row.TranslationBody = …`. It never calls `_ocrItems.Add`. `OcrResultItem` raises `PropertyChanged` for `TranslationBody` **and** `Translation` (`OcrResultItem.cs:30-39`), so both feeds repaint in place, for free. **A test asserts `_ocrItems.Count` is unchanged across a drain and that the item is the same object.** |
| **A cached apology.** AC 2's pending text is not `(`-prefixed *so that it does not read as terminal* — but that also makes it **cacheable** by `CachingTranslator.IsCacheable` (`:82-85`). It is only safe because the row's text never goes near the cache: the cache stores *translator output*, and this string is written by the UI. **TP-LIVE-14 asserts both halves**: not `(`-prefixed **and** no cache store on the failure path. |

## Dev Notes

### Invariants this story must keep

- **I4 — only successes are cached.** The pending wording is not `(`-prefixed by design, so `IsCacheable` would
  accept it — it is safe only because it never reaches the cache. TP-LIVE-14 asserts the second half; do not drop
  it as redundant.
- **I6 — the glossary runs upstream of every engine.** The drain goes through `TranslateBodiesAsync`, which
  expands (`:311`). Store the **raw** body in the queue or a retried line is expanded twice.
- **I7 — the source language is chosen per message.** Same reason, same method.
- **I15 — every `Run.Text` is `Mode=OneWay` and gains a `TemplateRenderTests` case.** This story adds none; E7.S6
  does.
- **I16 — the eleven LIVE behaviours.** The three dedup layers stay exactly as they are, because `LiveDedup` is
  not touched.
- **I3 — the OCE trap.** The drain is a new `await` inside the loop's `try`. A timeout there is a
  `TaskCanceledException` with the token **not** cancelled and must count as an error and let the loop continue —
  never break out. `Live.cs:227`'s filtered catch is what makes that work; do not add an unfiltered
  `catch (OperationCanceledException)` around the drain.

### Rulings that apply

- **E3-h** — capped/failed rows are re-translated after recovery **by E5**. This is that story; the rows arrive
  here as ordinary failures, which is why no special case is needed for them.
- **GAP-4** — the pending and terminal sentences live in `Services/UserMessages.cs`.
- **OQ-B / E5.S1** — nothing is captured while paused, so the queue can only be fed by ticks that actually ran.
  There is no queue of un-OCR'd frames to bound (AC 2 of E5.S1), which is why this queue is small.
- **UX principle 5 / hint 2** — a row never carries a countdown; exactly one countdown per window. The explanation
  lives in the status line and (E7.S3) the chip.

### Repo traps

- **`_ocrItems` is an `ObservableCollection` shared with the compact overlay** (`CompactOverlay.xaml.cs:40-42`,
  `Feed_Changed` → `ScrollToEnd`). An `Add` during a drain would scroll both feeds to the bottom and reorder what
  the player is reading. In-place `TranslationBody` writes raise `PropertyChanged`, not `CollectionChanged`, and
  do not scroll — which is exactly right.
- **`while (_ocrItems.Count > MaxHistory) _ocrItems.RemoveAt(0);`** runs at `:268` (LIVE) and
  `MainWindow.Ocr.cs:290` (read-once). A queued row can be evicted by **either**. Check membership at drain time,
  not at enqueue time.
- **The loop is single-threaded on the dispatcher** and strictly sequential (I16). The queue needs no lock, and
  adding one would be a claim that it might be touched from elsewhere. Do not.
- **`AppendLinesToHistory` rethrows** (`:283`) and that is load-bearing for E5.S2's counter. Enqueueing must not
  swallow the exception.
- No `.sln`; `InternalsVisibleTo` (`PWRUHelper.csproj:28`) and `DefaultItemExcludes` (`:18`) intact.

## How to verify manually

1. `dotnet test tests/PWRUHelper.Tests` — green, and `git diff --stat Services/LiveDedup.cs` is empty.
2. Start LIVE on a busy chat. Mid-session, hand-edit `provider-state.json` to block every read provider for ~30 s
   (or pull the cable for 30 s).
3. During the blip: rows appear with the **pending** text — **not** `(Google is limiting…)`, and **no countdown in
   the row**.
4. When the block expires: those exact rows fill in **where they are**. Their position does not move, their 🔑
   line is still there, the feed does not jump, and **no row appears twice**. Count the rows before and after.
5. Check the compact overlay at the same time: the same rows updated in place, no scroll jump.
6. Make the drain fail twice in a row (re-block during the recovery): those rows become `(…)` and stop being
   retried.
7. Let a session accumulate more than 50 messages after a blip: the oldest queued rows are dropped and never cost
   a request.
8. Press ■: the queue is cleared; pressing ▶ does not resurrect old rows.

### Completion Notes List

**The two decisions the story left to the PR, decided.**

1. **The pending row text is `…`** (T2). §9.3 sketched «Sally: retrying…» and `ux-mode-degrade.md`
   §2.2's S5 row says pending rows keep the existing `…`. §2.2 wins, and the reason is UX principle 5
   rather than economy: a row never carries a countdown and, by the same argument, never carries a
   status — there is exactly one explanation per window and it lives on the status line. A row saying
   "retrying…" would be a second one, on every row, saying less than the line above it. It lives in
   the copy deck all the same (GAP-4): `UserMessages.PendingRetryRow()`, a method rather than a const
   so it is not read as a row of the `Sentence(kind)` table by the house-rule scan. AC 2's requirement
   — deliberately not `(`-prefixed — holds, and `UserMessagesTests` asserts the negative directly.
2. **The given-up sentence is the deck's**: `UserMessages.RetryGaveUpRow()` →
   `"not translated — the engines did not come back"`, wrapped in `(` by the call site like every
   other non-translation. It names no engine and no reason on purpose — the reason was on the status
   line while the row was pending; what the row owes the player afterwards is the one fact the status
   line cannot carry once it has moved on.

**Which failures are queued, and it is a decision this story had to make.** `PendingRetryQueue.IsRetryable`
keeps a row only when a later attempt could plausibly answer differently: any `NotSent` refusal
whatever kind it carries, plus `RateLimited`, `Blocked`, `Timeout`, `Network`, `Unavailable`,
`AllProvidersPaused`. Excluded, with the reasons in the source and a `[Theory]` row each:

- **`BadResponse` — not queued.** The provider answered something we could not read; a retry re-sends
  the identical body for the identical answer. It is not lost: three in a row open the gate
  (`BadResponseStrikesToOpen`), and the rows that fail *after* that are `NotSent`/`AllProvidersPaused`
  and **are** queued, so V1.3 still holds for the session that recovers.
- **`QuotaExhausted` / `AuthFailed`** — a billing period and a key box; neither recovers inside a
  session, and neither can reach the keyless read chain at all (I8).
- **`Unknown` and anything untyped** — §4.4's honest last resort, and the shape a dead OCR engine or a
  failed capture arrives in. Nothing says a retry would help.

**Read-once rows: the test plan's open question, answered.** They join the queue **only while the LIVE
loop is running**, because the loop is the only thing that drains. A read taken with LIVE stopped has
nothing coming for it, and a row left pending for ever with nothing behind it is amplifier A7 — the
very thing E5.S4 exists to remove. A drain is coming ⇒ the row waits on `…`; no drain is coming ⇒ it
says what went wrong, exactly as it always did. **Cancelled-read rows never enter**, and structurally:
the enqueue lives in the *generic* catch, while a cancel is taken by the filtered
`OperationCanceledException` catch above it (I3).

**Deviation from AC 1's literal shape, and why it is not a weakening.** AC 1 writes the queue as
`List<(OcrResultItem Row, string Body, string Target)> _pendingRetry` in `MainWindow.Live.cs`. The
FIELD is exactly there (declared at the top of the partial, with the reason in its doc comment); the
TYPE is `Services/PendingRetryQueue<TRow>`, generic over the row so it carries no UI dependency. T1
already asked for the tuple to become a record ("a four-element tuple at three call sites is where an
argument-order bug lives"), and moving that record into `Services/` buys the three properties that
can silently make this story a no-op — the bound, the FIFO order, and "an evicted row costs no
request" — as L1 unit tests instead of facts about a window. What AC 1 is actually protecting is
untouched: **`git diff --stat Services/LiveDedup.cs` is empty** (T5, verified before the commit).

**How the in-place update works, since it is the risk.** The queue holds the `OcrResultItem`
*reference*; the drain assigns `entry.Row.TranslationBody` and stops. `OcrResultItem` raises
`PropertyChanged` for `TranslationBody` **and** `Translation`, so the main feed's two-tone line and
the overlay's single string both repaint where the row already is, through bindings that already
exist and are already `Mode=OneWay`. Nothing touches `_ocrItems`, so no `CollectionChanged` fires and
neither feed scrolls. **No `Run.Text` was added and no template changed, so `TemplateRenderTests` is
untouched and still green** (I15; the retry badge stays E7.S6's, with its own render case). The
no-duplicate pin is `TP_LIVE_10_a_drain_updates_the_same_rows_in_place_and_appends_nothing`:
`Assert.Same` on every row, `Count` unchanged, **and a `CollectionChanged` counter that must stay at
zero** — "no duplicate row" and "no scroll jump" are the same assertion seen from either end.

**The bundled rulings.**

- **E5-e** (`PerLineFallback`) — when nothing was translated, the **last SENT failure** is rethrown if
  there is one, else the last refusal. Two capture slots instead of one, keyed on `NotSent` (the flag,
  never the kind: a 429 that was never re-sent still reads as `RateLimited`). The locals are named
  `lastSentFailure` / `lastRefusal` on purpose — `ChainTranslatorTests.NotSent_is_written_in_exactly_one_place`
  scans production source for `NotSent\s*=`, and a local called `lastNotSent` reads to it as a second
  writer of a flag only `HttpProviderCore.Paused` may set.
- **E5-f** (`LiveTickPolicy.NextBackoffSteps` + the loop's catch) — a `Refused` tick advances the same
  back-off step a `Paused` one does, and the catch now *waits* it (`pausedWait`), computed from the
  current step count before the counter advances, exactly as the skipped branch does. It still reaches
  no error counter at all (E5-c). `LivePauseTests`' two verbatim pins — `errors.Record(outcome);` and
  `if (errors.Record(LiveTickPolicy.Classify(ex)))` — are **untouched**: the back-off is applied after
  the auto-stop verdict, from a local `Classify` call of its own.
- **E5-g** (`MainWindow.Ocr.cs`, `ReadOnceSummary`, `UserMessages`) — the pre-capture pause check is
  **removed**. Read-once captures and OCRs (both local, both free), the cache serves what it can, and
  the pause is *reported* by the chain as `AllProvidersPaused` — still **zero requests**, which is the
  only half of E5.S4's AC 3 that was ever about the provider. `ReadOnceSummary.Status` gains a fourth
  branch and a `pausedTryAgainIn` argument; `UserMessages.ReadOncePaused` gains `{n}`, which the old
  check could not know. The countdown is rendered by the code-behind from `_readChain.PauseNow()` —
  the gates' own clock, never `UtcNow` (IS-6).

### Review Findings

_Code review (Amelia CR, 2026-09-07) over `8e08b7d..cb21575`: three adversarial layers (Blind Hunter,
Edge Case Hunter, Acceptance Auditor) plus the reviewer's own pass. **Verdict: approved, fixes
applied.** No duplicate-row path was found; every finding below is about a row left saying the wrong
thing, or saying nothing at all for ever._

**The duplicate-row hunt, which is what this story is judged on.** `_ocrItems` is mutated in exactly
three places, all pre-existing: the `Add` + `MaxHistory` trim in `AppendLinesToHistory`
(`Live.cs:474`), the same pair in read-once's `TranslateSentencesInto` (`Ocr.cs:419`), and `Clear()`
in `StartLive`. **The drain adds nothing** — it writes `Row.TranslationBody` and stops — so no new
path can append a row, and the queue holds references, so a retried row is the same object
(`Assert.Same`, `Count` unchanged, `CollectionChanged` at zero). Two consequences were checked and
pinned rather than changed:

- **A pending line that scrolls off and comes back.** `LiveDedup` re-emits a message that has been
  gone for more than `ReappearAfterFrames`, so it appends a NEW row while the old one is still
  pending. That is **correct and unchanged**: it is the same rule that already gives a second row to
  a re-posted LFM whose first row was translated, and it is a decision about the game chat, not
  about the queue. E5.S3 touches neither side of it (`LiveDedup` diff-stat empty).
- **The queue can never re-add.** Nothing in `Services/PendingRetryQueue<TRow>` knows what a feed is.

**Fixed in this review.**

1. **A drain that threw discarded every target group after the failing one** (AC 5 / T4's named
   risk). `TakeAll` empties the queue first, so the entries of the not-yet-tried groups were gone —
   off the queue, off the retry path, stuck on `…` for the session. Reachable exactly when the
   player changed the target combo during the outage, which is the case the grouping exists for. The
   groups are now materialised and the untried ones go back at the **same** attempt count; the
   cancel exit handles its own leftovers. New pin: `The_drain_leaves_no_entry_behind_on_any_exit`.
2. **A cancel mid-drain threw away a translation that had already come back.** The rows a completed
   batch answered are now written before the cancel is observed — the answer was paid for, and an
   in-place write cannot duplicate anything.
3. **■ Stop left every pending row on `…` for ever.** Stop clears the queue but not the feed, so the
   rows stayed on both surfaces with the only thing that could drain them stopped — a pending row
   that never resolves, amplifier A7, the exact failure the epic is about. §2.2 draws the line (a row
   keeps `…` **while** something is coming; otherwise it is a given-up row), so `StopLive` now writes
   `GiveUpRow` over what it clears. This also covers the **auto-stop**, which ends a long outage by
   calling `StopLive()` for the player.
4. **A row the bound dropped while it was still on screen kept `…` for ever.** The queue and the feed
   are both bounded at 50 and normally forget the same row on the same tick, but they are two lists
   trimmed by three call sites and their ORDER can diverge. `Enqueue` now returns what it dropped and
   `MainWindow.EnqueueForRetry` — the only enqueue path, pinned by a scan — gives a dropped row that
   is still in `_ocrItems` the given-up sentence.
5. **A refusal spent one of the row's two attempts.** The drain runs on every non-skipped tick, so a
   probe deferral or a rate-ceiling refusal twice over handed a row the given-up sentence inside
   ~1.4 s — during the very outage the queue exists to survive, and without a single request having
   been sent about it. An attempt is now spent only by a drain that **reached a provider**
   (`LiveTickPolicy.Classify(ex) != Refused` — E5-c's principle, and the app's one definition of
   "this cost a request"). It cannot spin: an all-paused state skips the tick entirely, and ■ Stop
   ends every wait. It is also what makes `PendingRetryMaxAttempts = 2` mean "two real tries after
   recovery" rather than "two ticks".
6. **Four comments that were not true.** (a) `AppendLinesToHistory`'s catch claimed a genuine Stop
   never reaches it — it does; what keeps a cancel out of the queue is `IsRetryable`, not the shape
   of the catch (same correction in `PendingRetryQueue`'s doc). (b) `IsRetryable`'s bullet list read
   as if `QuotaExhausted`/`AuthFailed` were excluded unconditionally; the `NotSent` test comes first
   **on purpose** (a refusal carries the gate's last kind, not this call's) and that is now written
   down. (c) `LiveTickOutcome.Refused`'s own doc still said it does not advance the back-off, the
   opposite of E5-f — and E5.S2's deviation **D1 is thereby superseded**, which the enum now records.
   (d) the drain's doc named the overlay as binding `Translation`; both feeds bind `TranslationBody`.
7. **The read-once enqueue is unreachable today, and now says so.** `_liveCts != null` can never hold
   inside a read: the button path calls `StopLive()` first and Ctrl+Alt+R refuses while LIVE runs
   (the OCR engine is shared and non-reentrant). The decision — a row waits only while a drain is
   coming — is right and the guard stays, as a guard, for the day E7 lets a read run alongside the
   loop; but nothing depends on it, and `UserMessages.ReadOncePaused`'s doc no longer claims
   otherwise.
8. **Four test pins that could not fail.** `MaxHistory = 50` was asserted with `Contains`, so
   `MaxHistory = 500` passed it (now a regex on the value); "no new binding" grepped for this story's
   own words, so the retry badge it exists to stop would have passed (now: **every** bound `Run` in
   both feeds must say `Mode=OneWay`, which is I15's actual trap);
   `A_row_whose_failure_stops_being_retryable_gives_up_at_once` asserted two predicates side by side
   and never touched a row; and the three cases that mirror `RequeueOrGiveUp` now share one mirror,
   held against the source by `The_requeue_decision_in_the_window_is_the_one_mirrored_here`.

**Recorded, not fixed — for Winston.**

- **A partially-failed batch is never retried.** `PerLineFallback` does not throw when at least one
  line came back, so the rows that got `(skipped — …)` / `(rate-limited …)` placeholders are written
  terminal and never queued — on the append path (pre-existing) and, identically, on the drain path.
  Ruling **E3-h** ("capped/failed rows are re-translated after recovery by E5") is the one this
  leaves half-kept, and closing it means enqueueing on `!ReadOnceSummary.IsTranslation(result)` —
  a behaviour change on the SUCCESS path of both callers, not taken unilaterally in a review of the
  release's riskiest story.
- **A cache-served drain counts as `Translated`**, so it clears the auto-stop streak and the
  back-off although it may have sent nothing. Pre-existing with E4 (a cache-served ordinary tick does
  the same) and it is E5.S2's still-open "for Winston" item; the drain adds one more instance.
- **A partially-cached read is not served while paused.** `CachingTranslator` asks its inner
  translator for the misses without catching, so one miss loses the hits — E5-g's "the cache serves
  what it can" is exactly true only for a **fully** cached read, which is what its new test covers.
- **One give-up sentence for five reasons.** A Stop mid-drain, a timeout and a spent quota all render
  `(not translated — the engines did not come back)`. Deliberate (the row's job is to stop implying
  that something is coming; the reason was on the status line) but it is copy, and copy is **E7.S1**'s.
- **E5-e / E5-f / E5-g are not in `README.md`'s rulings table.** They arrive here as decided and are
  applied as such, but the table still shows only E5-a, so a later reader cannot find the ruling
  text. The rows belong there, together with the amendment E5-g owes **E5.S4 AC 3**,
  `architecture-cible.md` §9.4 and `test-plan.md` TP-ONCE-04 — all three still say a paused read
  creates **no rows**, which is no longer true and is the ruling's whole point.
- **`TP-ONCE-04` no longer drives read-once.** Its rewrite exercises `ChainTranslator` +
  `ReadOnceSummary` directly; the new behaviour (a paused read appends rows) has a source scan but no
  behavioural pin, because the window cannot be built headlessly.
