> or one request per *line*.

## Story

As the architect,
I want to know whether a `\n`-joined multi-line query comes back with its newlines intact,
So that the LIVE request volume of the whole design is a measured number and not a hope.

## Acceptance Criteria

_Copied verbatim from `epics.md` § Story E3.S1. Do not weaken._

1. **Given** U1 is "the single most important [UNKNOWN] in this document" (§7.1)
   **When** **one** request is sent, on a branch and with the owner's explicit go, carrying a `\n`-joined `q` of
   three known lines to `clients5.google.com/translate_a/t?client=dict-chrome-ex`
   **Then** the raw response is frozen as a test fixture in `tests/PWRUHelper.Tests` and recorded in this folder
   with its date and the network it came from.
2. **Exit criterion (measurable).** The response either contains **exactly two `\n` separators between three
   translated segments**, or it does not.
3. **Go / no-go.**
   - **Go — newlines survive:** batching stays one request per group, as today.
   - **No-go — newlines lost:** **OQ-A is already settled by the owner: one request per line.** The per-line path
     is bounded by `PerLineCap` (E3.S8), by the rate ceiling and by the gate; the expected cost is ≈2× the LIVE
     request volume, still far below today's. **Multi-`q=` remains a declined non-feature and is not to be
     proposed.**
4. **Given** ground rule 2 and the Phase-1 incident (`SYNTHESE.md` §5)
   **When** this spike runs
   **Then** it sends **one** request, from a connection the owner nominates, and nothing else.

## Dev Notes

### This story writes no production code

Branch only. No file under `Services/` or `MainWindow.*` is touched. The two artefacts are a fixture and a
paragraph of recorded evidence.

### If U1 never happens (the owner never designates a connection)

**E3 is not blocked.** OQ-A is already settled — *one request per line* — and it is the **safe default**: it is
correct whether or not newlines survive, it costs ≈2× the LIVE request volume of the join path, and that is still
far below today's volume. So the shipped rule is:

> **Per-line unless a batch is proven.** `GoogleDictTranslator.TranslateLinesAsync` sends one request per line
> until `Fixtures/google-dict-batch.txt` exists and proves the join survives.

E3.S4 implements exactly that. U1 is then an *optimisation* that halves LIVE request volume, not a gate. Say so
to the owner in those terms — it is a much smaller ask than "the epic is stuck".

### The request budget is the whole risk

`SYNTHESE.md` §5 records what happened the last time this rule was loose. One request. The endpoint is
`benchmark…` §3.2's own evidence base (20/20 HTTP 200 at ~2.5 req/s), so a single request is not what would break
it — the discipline is what stops a "quick second look" from becoming twenty.

### Do not propose multi-`q=`

`benchmark…` §3.2 measured `two q= params → ["Hello","How are you"]` and says in the same paragraph that it does
**not** propose adopting it. `project-context.md` lists multi-`q=` Google batching among the **deliberate
non-features**, and the owner's OQ-A answer re-confirmed it. It is not an option this spike may reopen.
