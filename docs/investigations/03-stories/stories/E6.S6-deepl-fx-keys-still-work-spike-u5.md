# Story E6.S6: Establish whether existing DeepL `:fx` keys still work 🔬 spike (U5)

Status: **blocked-owner (Phase 4 — needs a real `:fx` key or a DeepL support answer)**

_Epic E6 (F) — Bring your own key: Azure · increment 5 · **Release B.1** · the owner's Phase-4 go was given
2026-09-06 (`README.md` § Phase 4). Like E6.S1, this blocks **copy**, not code._

> **Why the question exists.** `benchmark-fournisseurs.md` records that DeepL's API Free/Pro plans stopped being
> purchasable in **July 2026**, and that the current free offer is a one-time **1 M-character "Developer"
> allowance** rather than a monthly one — which is the reason the owner's Phase-2 decision 5 added Azure F0 as a
> second key slot *"alongside DeepL"* in the first place. What nobody has checked is whether an **already-issued**
> `:fx` key still authenticates and translates.
>
> **Why it does not block any code.** If old keys are dead, the app's behaviour is already correct: DeepL 401s,
> `ProviderErrorMapper` classifies `AuthFailed` (guarded on `keyWasSent`, ruling E2-g), the gate opens, and
> `ChainTranslator` falls through to the free tiers. `epics.md` says it in as many words — *"an existing user's
> DeepL tier becomes an `AuthFailed` gate-open on first use — which is exactly the right behaviour."* The only
> thing that changes is a **sentence**.

## Story

As a player who set up DeepL last year,
I want the app to tell me the truth about my old key,
So that I am not left guessing why the tier I paid attention to went quiet.

   **Then** the result is recorded in this folder with its date.

**Exit criterion (measurable).** A yes/no on "an existing `:fx` key still authenticates and translates".

**Go / no-go.** **Go — old keys work:** the DeepL settings row keeps today's copy. **No-go — old keys are dead:**
an existing user's DeepL tier becomes an `AuthFailed` gate-open on first use — which is exactly the right
behaviour — and the settings row must say so, with the `✕ DeepL refused this key…` sentence of §3.7 extended to
name the plan change.

### There are three outcomes, not two

The go/no-go is written as a binary; the `/v2/usage` body can return a third:

1. **Works** — 200, `character_count < character_limit`. Copy unchanged.
2. **Authenticates, allowance spent** — 200, `character_count >= character_limit` (or a 456 on translate). That
   is **`QuotaExhausted`**, not `AuthFailed`, and `UserMessages.QuotaExhausted` already says
   *"Your free translation quota is used up for this month"* — which for a **one-time** 1 M Developer allowance
   is **wrong**: nothing resets. If this is the outcome, flag the sentence for **E7.S1** (the copy pass) — it is
   a deck row, not a §3.7 row, and it is the kind of inherited half-truth E7.S1 exists to catch.
3. **Dead** — 401/403. The no-go branch above.

### What the code already does, whichever way it lands

- 401 → `AuthFailed` **only because a key was sent** (`ProviderErrorMapper.cs:108`, ruling **E2-g**). A keyless
  401 is `Blocked`. DeepL sets `KeyWasSent: true` (`DeepLTranslator.cs:59`).
- 456 → `QuotaExhausted` (`ProviderErrorMapper.cs:123` — DeepL's own code).
- `AuthFailed` opens the gate to the `MaxValue` sentinel, **never persisted** (ruling **E2-a**), and the way back
  is re-saving the key (`ClearAuthBlock`, ruling E2-i) — which for a retired key means *clearing* it, and the
  copy has to make that the obvious action.
- `ChainTranslator` then skips the tier while `BlockedUntil > Now()` (ruling **E3-a**) and the write path falls
  to Azure/Google. **A user with a dead DeepL key loses nothing but a tier.**

### What must NOT happen

- **No probe from the dev box or this session.** `README.md` § ⚠ Incident record exists for that reason. This is
  the owner's key, the owner's request.
- **No code.** `epics.md`: *"No code. Feeds the copy in E6.S5 and E7.S8."*
- **The key is never written into the spike note, a log, or a commit.** I11.
